# Changelog

All notable changes to this project will be documented in this file.

## [Unreleased]

### Added
- **Brand assets** — the justpdf logo under `logo/`, shown at the top of every README and as the docs.rs logo and favicon
- `writer::embed_rgb` (also `justpdf::embed_rgb`) — embed 8-bit RGB pixels as a Flate-compressed image XObject, for `PageBuilder::add_image` / `draw_image` (#88)
- **CLI `compress` subcommand** — `justpdf compress <file> --preset low|medium|high|extreme -o <out>` (#10)
- **CLI `compress` options** — per-knob overrides on top of `--preset` (`--jpeg-quality`, `--max-dpi`, `--no-strip-metadata`, …) (#11), `--password` for encrypted input (output is unencrypted) (#13), `--analyze` preview (#12), `--verbose` breakdown (#14)
- **Release workflow** — pushing a `v*` tag builds CLI binaries for Linux, macOS (x86_64, aarch64) and Windows and attaches them to the GitHub release (#15)
- `crypto::random_file_id` — a random 16-byte file identifier for a newly written file (#31)
- `DocumentModifier::set_encryption` — `build` then writes the document encrypted, keeping `/Info`; the trailer `/ID` keeps the source's first element and gets a new second element (#75)
- `ContentOp` is now `PartialEq` (#29)
- `DocumentModifier::preserve_encryption` (also `justpdf::Modifier::preserve_encryption`) — `build` writes an encrypted source document encrypted as it was, with its `/Encrypt` dictionary and file key, so both of its passwords open the output although only one was used to open it; the trailer `/ID` keeps the source's first element. Of `preserve_encryption` and `set_encryption`, the later call wins; `build_with_xref_stream` refuses it for an encrypted source, and `incremental_save` accepts it (#102)
- `DocumentModifier::pack_object_streams` — pack eligible objects into object streams for `build_with_xref_stream`, leaving objects at a generation other than 0 unpacked and numbering each object stream above every number the source uses, as ISO 32000-1 §7.5.7 requires (#106)
- `Document::from_bytes_with_password`, `open_with_password` and `open_mmap_with_password` (`mmap` feature) — open an encrypted document with its user or owner password (#99)

### Changed
- **`justpdf_render::glyph_cache::GlyphCache::get_or_insert` takes the font program's hash, not its bytes** — `get_or_insert(font_hash: u64, glyph_id, build_fn)`; compute the hash once per font program with the new `glyph_cache::font_hash` (#163)
- **`justpdf_render::graphics_state` holds the selected font and pattern, not their names** — `TextState::font_name: Vec<u8>` is now `font: Option<FontKey>`, and `GraphicsState::fill_pattern_name`/`stroke_pattern_name: Option<Vec<u8>>` are now `fill_pattern`/`stroke_pattern: Option<PatternSelection>`. `Tf` and `scn`/`SCN` resolve the name when they run, so a Form XObject or pattern tile that inherits the font or pattern keeps the object its caller chose instead of whatever the same name means in its own `/Resources` (#127)
- **`JustPdfError` has a new variant, `LimitExceeded { obj_num, gen_num }`** — a tree walk that revisits shared nodes past its budget fails with it; a `match` over `JustPdfError` without a wildcard arm needs a new arm (#120)
- **`JustPdfError` has a new variant, `PageOutOfRange { index, count }`** — `page::get_page` returns it, where it returned `InvalidObject`, for an index at or past the page tree's `/Count`, or past the last page when the tree has no `/Count`; an index below a `/Count` that overstates the tree is still `InvalidObject`; a `match` over `JustPdfError` without a wildcard arm needs a new arm (#134)
- **`justpdf-render` reports a page index out of range as `RenderError::Core(JustPdfError::PageOutOfRange { .. })`** — `render_page`, `render_page_to_pixmap`, `render_page_to_svg` and `render_pages_parallel` returned `RenderError::InvalidDimensions` for it (#134)
- **Subsetted fonts are much smaller** — `subset_font` (and so `compress_pdf` with `font_subsetting`) copied the font's `cmap` and `post` tables whole, which made up most of a subset: Noto Sans subsetted for "Hello" was 29,201 bytes Flate-compressed. `cmap` now keeps every subtable but only the entries that reach kept glyphs, and a format 2 `post` keeps only the kept glyphs' names; glyph IDs are unchanged. The same subset is now 1,822 bytes. `cmap` formats other than 0, 4, 6 and 12, other `post` formats, and `name` are still copied as they are (#69)
- **`DocumentModifier::catalog_ref` returns the reference by value** (`IndirectRef` instead of `&IndirectRef`), at the generation `build` writes the catalog at — the trailer's `/Root`. Before, it returned the reference read from the source, whose generation differed from the written one once the catalog was set again at a number the modifier no longer held (#112)
- `justpdf-special`: `justpdf-render` is now optional and only pulled in by the `ocr` feature (#1)
- `justpdf-formats`: `justpdf-render` is now optional and only pulled in by the `plaintext`, `mobi` and `fb2` features (#2)
- **`incremental_save` appends only what changed** — it takes the source document instead of its bytes (`incremental_save(&doc, modifier)`, where `doc` is the document the modifier was created from). It appends only the objects whose value differs from the document's and the new ones, marks the objects the modifier removed as free (`65535 f`), and returns the original bytes unchanged when nothing changed; before, every object was appended again (#25)

### Fixed
- **`justpdf text --page 0`, `render --page 0` and `split --pages 0-…` panicked** — each subtracted 1 from the 1-based page number without rejecting `0`. `--page 0` is now refused as an invalid value and a range starting at `0` as out of range; `text --page` past the last page now reports the 1-based page (`Page 99 out of range (total: 1)`) instead of core's 0-based index (#149)
- **`justpdf-formats` did not compile with only the `epub` or `office` feature** — their page preview used the `plaintext` module, which exists only under the `plaintext` feature. Both now compile on their own; without `plaintext` their `render_page` and `render_page_png` return `FormatError::Format` (after the index check), and with it the preview is unchanged. CI now compiles `justpdf-formats` with each feature alone, reading the list from the manifest (#35, #200)
- **`justpdf convert` rejected MOBI and FB2 input** — `.mobi`, `.prc` and `.fb2` were detected but failed with `unsupported input format`; they now convert to PDF, or to a PNG of the first page, like the other document inputs (#49)
- **`justpdf-special` barcodes other than QR and Code39 did not scan** — DataMatrix, PDF417 and Aztec had no error correction and no standard module placement; Code128 used 18 of its 107 patterns, so no symbol was valid; EAN-13 ignored the leading digit's parity, so only codes starting with 0 scanned. Code128, EAN-13, Code39, DataMatrix, PDF417 and Aztec are now encoded by the `rxing` crate (Apache-2.0 only), and every symbology is tested by decoding the generated image. Every symbol except QR now carries its standard minimum quiet zone, so images are wider than before; EAN-13 rejects a wrong check digit; input a symbology cannot encode (for example non-ASCII text in Code128) returns an error instead of a wrong symbol (#55, #242)
- **`generate_barcode` with `BarcodeType::DataMatrix` returned an image ten times too large** — it used the larger of `width` and `height` as the module size; DataMatrix, PDF417 and Aztec now fit within `width` x `height` with square modules (#242)
- **The renderer could draw a glyph from another font's program** — the glyph cache identified a font by the address of a copy of its program that was made and dropped for every text-showing operator, so a later font whose copy landed at the same address drew the earlier font's outlines, and by a hash of only the program's length and first 256 bytes, so two programs that agree there shared outlines too. Which glyphs were wrong depended on allocation order: two builds differing only in unrelated code drew different glyphs on the same pages. Each font program is now identified by a hash of all of its bytes, computed once when the font is loaded (#163)
- **Concurrent OCR calls read each other's page** — `ocr_pdf_page` and `make_searchable_pdf` wrote the rendered page to `justpdf_ocr_{pid}.png` (`_{pid}_{i}` per page) in the temp directory, so two calls at once in one process shared the file: one OCRed the other's page or found the file already deleted. The page now reaches tesseract on stdin and nothing is written to disk. This needs tesseract 3.04 or newer (#184)
- **`justpdf sign` exited with code 0 without signing** — it printed a notice and reported success, so a script could not tell that nothing was signed. It now writes nothing and exits with code 1 (`Error: digital signing is not implemented yet`) until signing is wired up (#37, #181)
- **Opening a document with a large object stream took time quadratic in its object count, and a crafted `/N` could abort the process** — every first load of an object from an object stream re-read the stream's whole index, so 16,000 pages in one object stream took 74.6 s for `justpdf text` (now 0.15 s, the same as plain objects), and the index was allocated at the size the stream's `/N` declared, so `/N 1099511627776` aborted with a failed 17.6 TB allocation. The index is now read once per object stream and sized by the pairs actually present. An index entry whose offset is negative or outside the stream's data is now an `InvalidObject` error; before, a debug build panicked and a release build read a different object. A byte that is not a valid token among the index pairs now ends the index like any other non-integer, so the objects before it load; before, every object in that object stream failed with `InvalidToken` (#132)
- **Font subsetting emptied glyphs of fonts that share one font program** — `compress_pdf` with `font_subsetting` subsetted the FontFile2 stream once per font dictionary, so when two font dictionaries reached the same stream, the second cut the already-cut program again: text drawn with both fonts lost the glyphs of each (Ghostscript rendered "Hello" + "world" as `llo  o l`), and a font left whole on purpose (for example one shown with `"`) lost its glyphs when a sibling was subsetted. Each FontFile2 stream is now subsetted once, keeping the glyphs of every font that reaches it, and is left whole when any of those fonts would be, or when something other than those fonts references the stream or its FontDescriptor. `CompressStats::fonts_subsetted` now counts subsetted font programs, so a shared program counts once (#117)
- **The C and Python bindings reported every page lookup error as an index out of range** — `justpdf_extract_page_text` and `justpdf_page_size` returned `JUSTPDF_ERR_OUT_OF_RANGE`, and `Document.page` and `Document.page_text` raised `IndexError`, for a page tree cycle, a tree walk past its budget, a malformed page tree and an unauthenticated encrypted document alike. They now return `JUSTPDF_ERR_OUT_OF_RANGE` / raise `IndexError` only for an index past the last page; an unauthenticated encrypted document returns `JUSTPDF_ERR_ENCRYPTED` / raises `RuntimeError`, and any other error returns `JUSTPDF_ERR_PARSE` / raises `RuntimeError`. `justpdf_render_page_png` returned `JUSTPDF_ERR_RENDER` for every error; it now sorts the core errors the same way — `JUSTPDF_ERR_OUT_OF_RANGE`, `JUSTPDF_ERR_ENCRYPTED` or `JUSTPDF_ERR_PARSE` — and returns `JUSTPDF_ERR_RENDER` for the rest. `Document.render_page` raises `IndexError` rather than `RuntimeError` for an index past the last page (#134)
- **The renderer resolved names inside Form XObjects, pattern tiles, soft mask forms and annotation appearances in the page's `/Resources`** — a name only the stream's own `/Resources` held was not drawn, and a name the page also held drew the page's object. `Do`, `scn`/`SCN`, `sh`, `gs` and `Tf` now resolve in the stream's own `/Resources`, then each enclosing stream's, then the page's, in both `render_page_to_pixmap` and `render_page_to_svg` (#127)
- **Linearization, `clean_objects` and object stream packing could leave references at a generation the file does not define** — `linearize_pdf` wrote every object copied from the source as `N 0 obj` with a generation-0 xref entry while the document's references still read `N g R`; it now writes each at its source generation. `clean_objects` renumbered objects without changing the generation of the references to them, so `K 1 R` pointed at an object written as `K 0 obj`; it now writes every reference to an object it holds at generation 0, the generation `serialize_pdf` writes. `build_with_xref_stream` now refuses, with an `InvalidObject` error, an object stream or a compressed object at a generation other than 0 — such as a source object at generation 1 packed with `pack_object_streams`, which every reference to it would read as null (#106)
- **`pack_object_streams` panicked when `max_objects_per_stream` was 0** — it now returns an `InvalidObject` error, as does `DocumentModifier::pack_object_streams` (#106)
- **A cyclic page tree, field tree, outline, number tree or name tree crashed the process** — the tree walkers followed `/Kids` (and `/First`/`/Next` for outlines) with no cycle check, so a damaged or crafted file whose tree leads back to an ancestor overflowed the stack; `get_page` could instead return the same page at a second index. `collect_pages`, `get_page`, `parse_acroform`, `detect_signatures` and `read_outlines` now fail with `CircularReference` — and so does `justpdf::Document::open` on such a page tree. `read_page_labels`, `read_embedded_files` and `read_named_destinations` skip the kid that leads back and return the rest. A node listed twice without leading back to an ancestor is still read twice (#52)
- **A small file that lists the same kid twice on every level of a tree took seconds to open and returned millions of entries** — a node listed twice is read twice, so a tree of k such levels was read 2^k times: a 2 KB page tree of 22 levels took 9.3 s in `collect_pages` (and in `justpdf::Document::open`) and returned 4,194,304 pages, and an outline whose sibling items share one `/First` child grew the same way. Each walk now charges every node it reads by the node's size — the array elements and dictionary values it holds — and stops before its charge passes four times the summed size of the distinct nodes it has read, so a large node shared by many small ones is not read over and over either: `collect_pages`, `get_page`, `parse_acroform`, `detect_signatures` and `read_outlines` fail with the new `JustPdfError::LimitExceeded`, and `read_page_labels`, `read_embedded_files` and `read_named_destinations` skip the kids past that point and return the rest. A tree with no node listed twice is read in full whatever its size (#120)
- **`get_page` panicked in debug builds, or missed a page, on a negative `/Count`, and missed pages under a `/Pages` node without `/Count`** — a negative `/Count` was read as a huge page count and overflowed the page counter, and a missing one as 0, which skipped a subtree `collect_pages` reads. `get_page` now skips a subtree only by a non-negative `/Count`, and `page_count` returns 0 for a negative `/Count` as it did for a missing one (#120)
- **Rendering a tiling pattern whose tile fills a path crashed the process** — the tile ran with the page's pattern still selected, so a fill inside it drew the same tile again until the stack overflowed, even in an ordinary file; `rg`, `g` and `k` (and `RG`, `G`, `K`) did not leave the Pattern colour space either, so a device colour set after `scn` was ignored. The renderer now keeps the Form XObjects, tiling patterns and soft mask forms it is running and skips one that is already running: a tile that fills with its own pattern fills with the fill colour, a soft mask form that applies its own `gs` leaves the mask as it was (it overflowed the stack before), and a Form XObject that draws itself is drawn once instead of eleven times — a form that drew itself k times ran k^11 times. The device colour operators now replace the pattern, and a tile is drawn without the page's soft mask. `render_page_to_svg` skips a running Form XObject the same way. A form drawn twice by its parent is still drawn twice (#119)
- **The trailer could point at a rewritten `/Info` or catalog at a generation it no longer had** — `DocumentModifier` wrote the trailer's `/Root` and `/Info` with the generation it read from the source, while an object set again at a number the modifier no longer held (`set_info` rebuilding a missing `/Info`) is written at generation 0, so the trailer pointed at an object the file does not define and readers found no `/Info` or catalog. `build`, `build_with_xref_stream` and `incremental_save` now write both at the generation their objects are written at, and `incremental_save` appends an object whose generation changed even when its value did not. `PdfWriter::write_to_bytes` writes `/Root` the same way, whatever generation the reference passed to it has (#110)
- **A reference to an object number missing from the cross-reference table was an error** — `PdfDocument::resolve` returned `ObjectNotFound`, and the readers that propagate it failed as a whole on one such reference: `outline::read_outlines` for an `/Outlines` pointing at no object, `annot::get_all_annotations` for an `/Annots` entry pointing at none. Such a reference now resolves to null, as ISO 32000 §7.3.10 requires and as a free entry or a reference at the wrong generation already did (#108)
- **A reference at the wrong generation resolved to the object** — `PdfDocument::resolve` never compared a reference's generation with the one its xref entry defines, so `N 1 R` returned the object defined as `N 0 obj`, and in an encrypted document decrypted it with a key made from the reference's generation: garbage with RC4, a padding error with AES-128. Such a reference now resolves to null, as ISO 32000 §7.3.10 treats a reference to an undefined object; an object in an object stream is generation 0 (#98)
- **Objects with a generation number other than 0 were rewritten at generation 0** — `DocumentModifier` (`build` with or without encryption, `build_with_xref_stream`, `incremental_save`), and so everything built on it (CLI `encrypt`, `decrypt` and `compress`, annotations, forms, …), wrote each object copied from the source as `N 0 obj` with a generation-0 xref entry and, for RC4 and AES-128, an object key derived from generation 0, while the document's references still read `N g R`. Other readers found no such object: qpdf read the reference as null, and after an incremental save it read the object as it was before the change. Objects copied from the source are now written at their source generation; objects added or set at a number the modifier does not hold are generation 0. Stream deduplication in `compress` points merged references at the generation of the stream it keeps, and `clean_objects` at generation 0. `serialize_pdf`, `serialize_pdf_encrypted` and `serialize_pdf_with_xref_stream` still write every object at generation 0 (#72)
- **Cross-reference table entries were 21 bytes** — every classic xref table justpdf wrote (`DocumentBuilder`/`DocumentModifier` `build`, `incremental_save`, linearization, signing) ended each entry with a space and CR LF, one byte more than the 20 ISO 32000-1 §7.5.4 requires. qpdf reported every such file as damaged and reconstructed the table to open it. Entries now end with a space and LF, as qpdf writes them (#102)
- **`justpdf::Document` could not open a file with a user password** — `open`, `from_bytes` and `open_mmap` collect the pages while opening, which fails with `EncryptedDocument` before `authenticate` can be called, so such a file could not be opened at all. Open it with the new `*_with_password` constructors; `open`, `from_bytes` and `open_mmap` are unchanged. `Document::modify` now works on the document itself instead of parsing its bytes again, so a document opened with a password can be modified; as before, the modifier writes an encrypted document without encryption unless encryption is set through `inner_mut()` (#99)
- **Strings in an object stream of an encrypted file** — an object stored in an object stream was decrypted twice: once with the object stream and again with its own number, although ISO 32000 says strings in an object stream are not separately encrypted. With RC4 the strings (such as `/Info` values) came out as garbage; with AES, resolving the object failed, and `DocumentModifier` — and so CLI `decrypt` — silently left the object out of the file it wrote. Such an object is now decrypted only with its object stream (#32)
- **A `/Crypt` stream filter without a `/Name`** — decrypted the stream with the document's default stream method; ISO 32000-1 says the name defaults to `/Identity`, so the data is not encrypted. Such a stream is now read as written, as MuPDF does
- **`/EncryptMetadata false` was ignored** — reading decrypted the document's XMP metadata stream although such a file leaves it unencrypted (with AES it failed to resolve), and writing with `EncryptionConfig { encrypt_metadata: false }` encrypted it anyway. The catalog's `/Metadata` stream is now read as written, as qpdf does, and written plain behind an Identity crypt filter (ISO 32000-1 §7.6.5's example); RC4 still encrypts it
- **A stream with an Identity crypt filter lost its data when re-encrypted** — reading kept `/Crypt /Identity` in the stream's filters, so writing the document encrypted again produced ciphertext labelled as unencrypted. Reading now drops the `/Crypt` filter as it does for the other crypt filters
- **Integer text beyond the 64-bit range** — the tokenizer rejected an integer such as `100000000000000000000` as an invalid token, so justpdf could not open files other tools wrote with one, and the content stream parsers silently read it as `0`. Both now read it as the nearest real, as pdf.js does (#84)
- **Generated content wrote NaN and infinity** — `PageBuilder` (coordinates, colors, font size), the form-field, annotation and signature appearance streams and the redaction overlay wrote numbers with Rust's float formatting, so a NaN or infinite input came out as `NaN`/`inf` (read as an operator) and an integer value beyond the 32-bit range as a long integer. They now write NaN as `0`, infinity as `±f32::MAX`, integer values within the 32-bit range as integers and other values as reals; ordinary output is unchanged (#90)
- **CBZ, SVG and OCR output drew their page image as a 1-point dot** — `to_pdf` for CBZ and SVG and `make_searchable_pdf` put the page raster in the content stream as an inline image without scaling it, so it covered 1×1 pt (a CBZ page rendered blank), and pixel data holding whitespace + `EI` + whitespace cut the image short. They now embed the raster as an image XObject with `embed_rgb` and draw it over the whole page (#88)
- **Redaction and grayscale corrupted the page content they kept** — both rewrite a page's content stream after parsing it, each with its own writer. Redaction wrote a string holding one unbalanced parenthesis (a list item `1)`) without escaping it, so the text changed; both lost every inline image (redaction wrote the text `<inline-image>`, grayscale only `BI`); names with a space or other delimiter split into two operands; reals beyond the 64-bit integer range read back as other numbers, and grayscale rounded every real to four decimals. Both now go through one writer that uses the same rules as `PdfObject`'s `Display` and writes inline images back byte for byte; the gray values grayscale writes are rounded to four decimals and no longer come out as `inf`/`NaN`. `ContentOp`'s `Display` shows that writer's output. Because inline images now survive, redaction removes the ones that overlap a redaction area, judged like image `Do` operations (by the last `cm`). The content parser read an inline image's dictionary value `<< … >>` as a hex string and `null` as a name, so `/DP << /Predictor 15 … >>` came out as garbage; it now reads them as a dictionary and null (#29)
- **Content stream parser kept carriage returns in literal strings** — an unescaped CR or CRLF inside a literal string was read as-is, while ISO 32000-1 §7.3.4.2 reads it as a line feed (as the file tokenizer already did), so text extraction and rendering saw bytes other readers do not. Both content parsers (the default and `arena`) now read it as a line feed (#87)
- **Other hand-written PDF syntax did not escape** — `PageBuilder::set_font`, `draw_image` and `draw_inline_image` wrote resource names unescaped; the form-field, signature and stamp appearance streams and `sign_pdf`'s `/Name`, `/Reason` and `/Location` wrote carriage returns raw (read as a line feed); `sign_pdf` wrote the widget's `/Rect` and the appearance dictionary's `/BBox` with Rust's float formatting, so a NaN or infinite `appearance_rect` produced `NaN`/`inf` there; `add_embedded_file` escaped the MIME type's `/` and the serializer escaped it again, so other readers saw `application#2Fpdf`. All of these now use `PdfObject`'s rules. Strings holding bytes outside printable ASCII — `PageBuilder::show_text`, the appearance streams' text and the signature's `/Name`, `/Reason` and `/Location` — are now written as hex strings (the same bytes). Reals inside the generated content streams (coordinates and colors of `PageBuilder` and the appearance streams) are still written as before. MIME types written twice-escaped by earlier versions still read as `application/pdf` (#29)
- **Grayscale compression panicked on some images** — `compress_pdf` with `grayscale` converts pixels by the component count the image decoder reports, which is right only when `/ColorSpace` is a name; an image whose color space is a reference or an array (an Indexed palette, an ICCBased profile) came out with too few or too many gray pixels, and the JPEG encoder panicked on the length. Such an image is now left as it is (#89)
- **Written values that read back differently** — objects written by `PdfObject`'s `Display` (every non-stream object `serialize_object` writes) did not always read back as the same value. A carriage return in a literal string was written raw and read back as a line feed, so encrypting a document whose `/ID` contained one produced a file neither justpdf nor qpdf could open. An integer-valued real (`1.0`, `-0.0`) was written without a decimal point and read back as an integer, and one beyond the 64-bit integer range (`1e20`) read back as a parse error. NaN and infinity were written as `NaN`/`inf`, which is not PDF. Carriage returns are now written as `\r`, reals always carry a decimal point, NaN is written as `0.0` and infinity as `±f32::MAX` (#28)
- **Stream deduplication merged streams that were not equal** — `compress_pdf`'s stream dedup (the `structural` step, on in every preset) compared only stream data, so two streams with the same bytes but different dictionaries (for example `/Width`, `/Height`, `/Filter` or `/ColorSpace`) were merged into one. It now merges only streams whose dictionary (apart from `/Length`, which the writer recomputes) and data are both equal, repeating until no merge makes further streams equal. `clean_objects` judged identity by the objects' `Display` text, which leaves out stream data and prints `Real(1.0)` and `Integer(1)` alike; it now compares values (#27)
- **Strings in stream dictionaries were not encrypted** — encryption and decryption skipped the strings in a stream's dictionary, which ISO 32000-1 §7.6.1 encrypts like any other string: justpdf wrote them in plaintext (qpdf read them as garbage) and read third-party encrypted files' values as ciphertext. Both directions now handle them with the string method; cross-reference streams stay unencrypted (§7.5.8.2). A stream-dictionary string that does not decrypt is kept as written instead of failing the stream. Encrypted files written by earlier justpdf versions can now read such strings (for example an attachment's `/Params /ModDate`) as garbage, as other readers already did
- **`PdfWriter::set_object` at a new number** — later `add_object` calls could hand out the same number again, so a document carried two objects with one number; when `DocumentModifier` encrypted such a document, the `/Encrypt` dictionary took the number and the other object was written in plaintext. `set_object` now moves the next free number above the one it sets (#75)
- **CLI `encrypt` lost `/Info` and the changing `/ID`** — the command assembled the encrypted file itself, passing no `/Info` and writing the source's first `/ID` element twice. It now goes through `DocumentModifier::set_encryption`, so the document information dictionary survives and the second `/ID` element is new (#75)
- **`DocumentModifier::from_document` on encrypted documents** — an encrypted document that had not been authenticated lost nearly every object silently (every resolve failed), so CLI `encrypt` on an encrypted input exited successfully with a file no reader could open; it is now refused with `EncryptedDocument`. An authenticated one had its old `/Encrypt` dictionary copied along, so `justpdf decrypt` output still carried the old `/O`/`/U` values in plaintext; the dictionary is no longer copied (#75)
- **Encryption randomness and file identifiers** — AES IVs, the AES-256 file key and the R6 salts were derived from the system clock, the random bytes of R6 `/Perms` were zeros, and every encrypted document (`DocumentBuilder` and CLI `encrypt`) got the same `/ID`, so RC4/AES-128 documents with the same passwords and permissions shared one file key. All of these now come from the operating system's random source; `DocumentBuilder` writes a random `/ID`, and CLI `encrypt` keeps the input's first `/ID` element when it has one (#31)
- **Incremental save and signing lost the trailer's document keys** — the new trailer only carried `/Size /Root (/Info) /Prev`, and readers (justpdf, pdf.js, MuPDF) read only the newest trailer, so `/Encrypt`, `/ID` and — when signing — `/Info` disappeared; an encrypted document came back unencrypted with its old objects unreadable. The update trailer now carries every key of the previous trailer. `incremental_save` encrypts the appended objects with the document's key (the modifier must come from an authenticated document) and writes them through the serializer instead of `Display`, which corrupted streams; `sign_pdf` refuses encrypted input (#26, #25 in part)
- **AES-256 R5 password check** — `verify_password_r5` computed the hash and returned `true` without comparing it, so any password "authenticated". Because opening a document tries the empty password first, an R5 file with a user password was locked to a garbage key on open and could not be read even with the correct password. The hash is now compared with `/U` / `/O` (#30)
- **Font subsetting dropped the glyphs it was meant to keep** — `compress_pdf` with `font_subsetting` (medium, high and extreme presets) picked glyphs by treating each character code as a glyph ID, then renumbered them while leaving the font's `cmap` and the PDF's `/CIDToGIDMap` pointing at the old numbers, so embedded TrueType text rendered as blanks even though text extraction still worked. `subset_font` now keeps every glyph ID (unused glyphs become empty; `gid_map` is the identity), glyphs are chosen through the font's own lookup paths, and a font is left whole when its use cannot be fully collected — referenced from a form XObject, an annotation appearance or inherited `/Resources`, or shown with `"` (#51)
- **CI feature-isolation check** — `cargo tree` prints ASCII glyphs on CI, so the script's checks were failing or vacuous; they now match dependency names directly (#62)
- **Encryption round-trip** — binary strings with bytes ≥ 0x7F (e.g. `/O`, `/U`) were written as literal strings and corrupted, so some password pairs produced files that could not be opened. Such strings are now hex-encoded (#20)

## [0.1.4] - 2026-05-08 (justpdf-core)

### Fixed
- **ObjStm `/First` off-by-one** — `load_compressed_object` inferred the
  data-section start from `tokenizer.pos()` after consuming the index
  pairs, which was off by the whitespace padding before the first
  object. Compressed objects' `abs_offset` landed one byte short
  (typically on the previous object's closing `>`), producing an
  `unexpected '>'` parse error. Affected PDFs that use object streams
  with whitespace padding before the data section — common in files
  with incremental updates. Now reads `/First` and `/N` from the dict.
