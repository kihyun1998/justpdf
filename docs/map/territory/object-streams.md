# Object streams (ObjStm)

## What it is
`/Type /ObjStm` 스트림에 작은 비스트림 객체들을 묶는 포맷. 읽기 쪽은 xref 타입 2 엔트리를 해석해 스트림을 복호화·디코드·캐시하고 `/First + offset`에서 객체를 파싱한다. 쓰기 쪽은 적격 객체를 `num off … 데이터` 레이아웃으로 묶고 타입 2 엔트리 정보를 돌려준다. 한 포맷을 두 사이트가 서로 호출 없이 공유한다.

## Governing decisions
**None.**

## Design model
- **`/First`가 권위다.** 인덱스 쌍을 다 읽은 뒤의 토크나이저 위치로 데이터 시작을 추론하면 공백 패딩만큼 어긋난다 — `load_compressed_object`의 주석이 이 규칙을 적고 있고, 쓰기 쪽 `build_object_stream`이 바로 그 패딩(데이터 앞 공백)을 낸다.
- 쓰기 쪽 적격 규칙: 스트림, catalog, pages 루트, 암호화 사전, `/Type /XRef`, Null은 묶지 않는다.
- 읽기 쪽은 쌍의 객체 번호를 무시하고 인덱스만 쓴다. 스트림은 항상 세대 0으로 조회한다.
- **The offset table is built once per stream.** The reader parses the index pairs right after decoding and caches them as an `ObjStm` (decoded bytes plus the absolute offset of each index); loading an object only looks the table up. Before #132 the cache held `/N` instead, and every first load of a compressed object re-tokenized the pairs from byte 0, so loading N objects from one stream was O(N²) — *inferred* from the code, and *measured* by `justpdf text` on a generated file with every page in one object stream, single runs: 10.1 s → 97 ms at 8,000 pages, 74.6 s → 286 ms at 16,000 (release, 2026-09-30); after the fix the same pages as plain objects and in an object stream take the same time (min of 5 runs, 16,000 pages: 156 ms vs 153 ms).
- **`/N` does not size an allocation.** `/N` only bounds how many pairs are parsed; the table grows by the pairs actually read, so it is bounded by the decoded data. Before #132 it was `Vec::with_capacity(/N)`: `/N 2^40` aborted the process trying to allocate 17.6 TB (*measured* 2026-09-30, `justpdf info`, exit 127), and `/N 1e8` allocated 1.6 GB (reported in #132, not re-measured).
- **The table stops at the indices an xref entry can address.** `XrefEntry::Compressed::index_within` is a `u16`, so the table holds at most 65,536 entries (`OBJ_STREAM_ADDRESSABLE_INDICES`, 1 MiB at 16 B each) and is shrunk to fit; pairs past that could never be looked up. Without the cap the table was retained for the document's lifetime at up to ~4.2× the decoded bytes (16.8 B per shortest pair `"1 2 "`): a 62.6 KB Flate stream of 16M pairs retained 335.5 MB. With the cap the same file retains 68.2 MB against 67.2 MB on master, and peaks at 68.3 MB against master's 323 MB (*measured* 2026-09-30 with an allocation-counting probe linked against each tree). The cap follows the width of `index_within`: widening that field (see the xref reader's `as u16`, which silently wraps index 65,536 to 0) has to move it too.
- When the pairs run out before `/N` (a token that is not an integer, or one that fails to tokenize), parsing stops and the pairs read so far are used; an index past them is `ObjectNotFound`. The table is cached either way, so a broken index is still parsed once (*measured* by `test_objstm_index_that_fails_to_tokenize_keeps_the_pairs_before_it`).
  - **Maintainer call (2026-09-30, #132 check-it)**: a pair that fails to tokenize ends the index like a non-integer token, so the pairs before it resolve. Before #132 such an index failed every object in the stream with `InvalidToken` (*measured* by the lens reader: `justpdf info` on index `2 0 1 37 > `, `/N 3` — master exit 1, this change exit 0). Shown: those two behaviours; that the non-integer leniency and the tokenize-error strictness differed only by `?` versus `_ => break`, which nobody had decided; and that MuPDF errors the whole stream in both cases. The alternative was to keep the error and cache the failure. This call did not cover what to do when decoding the stream or reading `/First` fails (not cached; carried as a candidate).
- **Offset check.** When `/First` plus a pair's offset is negative, overflows, or lands outside the decoded data, that index alone is an `InvalidObject` error; other indices of the same stream are unaffected. A negative `/First` makes every index an error. Before #132, `as usize` wrapped negatives: a debug build panicked on `first + offset` overflow, and a release build read another object (both *measured* 2026-09-30: the panic by `test_objstm_negative_offset_is_an_error` against the old code, the misread as `justpdf info` failing with "catalog has no /Pages"; that the object read was the Pages dictionary is *inferred* from the offsets).
  - **Maintainer call (2026-09-30, #132 read-it)**: include the offset check in #132. Shown: the release misread (reproduced), the debug panic (then inferred, observed later by the test), and that it is the same code that builds the table. The alternative was to carry it as a separate follow-up. This call did not cover checking a pair's object number against the xref (tracked in #109).
- **암호화**: 읽기 쪽은 ObjStm 전체를 스트림 번호로 복호화하고, 꺼낸 객체는 [객체 복호화](object-decryption.md)를 다시 받지 않는다(ISO 32000-1 §7.5.7). 쓰기 쪽 패킹은 암호화를 받지 않는다.
- **세대**: object stream과 그 안 객체는 세대 0이고, 세대 ≠ 0 객체는 넣지 않으며, 새 object stream은 해제된 번호가 아닌 새 번호를 받는다(ISO 32000-1 §7.5.7). 쓰기 쪽은 두 벌이다. `DocumentModifier::pack_object_streams`는 writer의 세대가 0인 객체만 넣고, 컨테이너 번호를 writer의 `next_obj_num`(원본의 모든 번호 위)에서 받는다. 공개 `pack_object_streams`는 번호·객체 슬라이스만 받으므로 모든 객체를 세대 0으로 보고, 컨테이너를 가장 큰 번호 위에 매긴다. 둘은 `pack_objects`(적격 판정·번호 할당을 주입받음)를 공유한다. writer 쪽 xref 스트림 직렬화(`serialize_writer_with_xref_stream`)는 세대 ≠ 0인 압축 객체·컨테이너를 `InvalidObject`로 거부한다 — 공개 함수로 writer의 객체를 패킹해도 조용히 null 참조를 쓰지 않는다.
  - **메인테이너 판단(2026-09-29, #106)**: writer를 쥔 새 진입점 + 직렬화 가드(B+F). 보여 준 것: lens의 선택지 표 — 공개 시그니처에 세대 맵 추가(A: 깨지는 변경, 외부 호출자는 진짜 맵을 얻을 수 없음), 새 진입점(B), 비활성 내부 패커만 고침(C: 공개 경로가 열린 채), 문서화만(D), 그리고 가드(F). 컨테이너 번호가 GC로 지운 원본 번호의 세대를 물려받을 수 있다는 판정 보류 항목(F2)도 함께 보였다. 공개 슬라이스 함수의 시그니처는 바꾸지 않았다. 이 판단은 적격 규칙의 나머지(`/Info` 제외 여부, `/Length` 값 객체)를 다루지 않았다.
- `max_objects_per_stream`이 0이면 `pack_objects`가 `InvalidObject`로 거부한다 — 전에는 `chunks(0)`이 panic했다(#106).
- 쓰기 쪽 패킹은 [압축 파이프라인](compress-pipeline.md)에서 꺼져 있다(`pack_into_object_streams`는 dead code이고 `DocumentModifier::pack_object_streams`를 부른다).

## Reference behaviour
ISO 32000-1:2008 §7.5.7 원문(Adobe 무료 사본, 2026-09-27)과 대조한 것은 암호화 문장 "strings occurring anywhere in an object stream shall not be separately encrypted"뿐이다 — 읽기 쪽 복호화가 이를 따른다([객체 복호화](object-decryption.md)). 2026-09-29(#106)에 같은 사본(pdftotext)으로 세대 문장을 대조했다: 넣지 않는 객체 목록의 "Objects with a generation number other than zero", "The generation number of an object stream and of any compressed object shall be zero", 새 object stream과 압축 객체는 "new object numbers, not old ones taken from the free list". MuPDF `pdf-write.c`의 `objstm_gather`도 세대 ≠ 0 객체를 뺀다. On 2026-09-30 (#132) the index wording was compared against the same copy (pdftotext): the stream data holds "N pairs of integers separated by white space" (object number, then byte offset "relative to the first object"), "The offsets shall be in increasing order", and "A conforming reader shall rely on the First entry in the stream dictionary to locate the first object". The reader follows `/First`; it does not check that offsets increase, and it bounds nothing by the next offset (*inferred* from the code). MuPDF `pdf_load_obj_stm` (`vendor/mupdf-reference/source/pdf/pdf-xref.c`, *inferred* from its source) differs in four ways: it parses a stream once by parsing every object in it into the xref entries on first access; it rejects `/N` above `PDF_MAX_OBJECT_NUMBER` (8388607) and preallocates that many; it treats a non-integer token among the pairs as an error for the whole stream; and it finds an object by the pair's object number and bounds it by the next offset. The eligibility rules and ISO 32000-2 §7.5.7 were not compared.

## Cross-cutting invariants
- [원본 세대](../invariant/source-generation.md) — object stream 안 객체는 세대 0이어야 한다(ISO 32000-1 §7.5.7). `/First` 규칙은 두 사이트가 공유하지만 한 포맷에 속한 설계 규칙이므로 여기 Design model에 둔다.

## Blast radius
- [xref](xref.md) — 타입 2 엔트리의 출처. xref 스트림 쓰기(`write_xref_stream`)와 짝을 이룬다.
- [객체 복호화](object-decryption.md) — 압축 객체는 ObjStm 복호화만 받는다.
- [압축 파이프라인](compress-pipeline.md) — 패킹을 다시 켜는 곳. 켜면 뷰어 호환성 문제(주석 사유)를 다시 검증해야 한다.
- [파일 직렬화](file-serialization.md) — `serialize_pdf_with_xref_stream`이 패킹 결과를 받는다.
- [문서 접근](document-access.md) — 디코드된 스트림 캐시를 소유한다.

## Known holes / open
