# Object streams (ObjStm)

## What it is
A format that packs small non-stream objects into a `/Type /ObjStm` stream. The reading side interprets xref type 2 entries, decrypts, decodes and caches the stream, and parses an object at `/First + offset`. The writing side packs eligible objects in the `num off … data` layout and returns the type 2 entry information. Two sites share the one format without calling each other.

## Governing decisions
**None.**

## Design model
- **`/First` is authoritative.** Inferring where the data starts from the tokenizer position after reading all the index pairs is off by the whitespace padding — the comment in `load_compressed_object` states this rule, and the writing side's `build_object_stream` emits exactly that padding (whitespace before the data).
- Writing-side eligibility rule: streams, the catalog, the pages root, the encryption dictionary, `/Type /XRef` and Null are not packed.
- The reading side ignores the pair's object number and uses only the index. The stream is always looked up at generation 0.
- **The offset table is built once per stream.** The reader parses the index pairs right after decoding and caches them as an `ObjStm` (decoded bytes plus the absolute offset of each index); loading an object only looks the table up. Before #132 the cache held `/N` instead, and every first load of a compressed object re-tokenized the pairs from byte 0, so loading N objects from one stream was O(N²) — *inferred* from the code, and *measured* by `justpdf text` on a generated file with every page in one object stream, single runs: 10.1 s → 97 ms at 8,000 pages, 74.6 s → 286 ms at 16,000 (release, 2026-09-30); after the fix the same pages as plain objects and in an object stream take the same time (min of 5 runs, 16,000 pages: 156 ms vs 153 ms).
- **`/N` does not size an allocation.** `/N` only bounds how many pairs are parsed; the table grows by the pairs actually read, so it is bounded by the decoded data. Before #132 it was `Vec::with_capacity(/N)`: `/N 2^40` aborted the process trying to allocate 17.6 TB (*measured* 2026-09-30, `justpdf info`, exit 127), and `/N 1e8` allocated 1.6 GB (reported in #132, not re-measured).
- **The table stops at the indices an xref entry can address.** `XrefEntry::Compressed::index_within` is a `u16`, so the table holds at most 65,536 entries (`OBJ_STREAM_ADDRESSABLE_INDICES`, 1 MiB at 16 B each) and is shrunk to fit; pairs past that could never be looked up. Without the cap the table was retained for the document's lifetime at up to ~4.2× the decoded bytes (16.8 B per shortest pair `"1 2 "`): a 62.6 KB Flate stream of 16M pairs retained 335.5 MB. With the cap the same file retains 68.2 MB against 67.2 MB on master, and peaks at 68.3 MB against master's 323 MB (*measured* 2026-09-30 with an allocation-counting probe linked against each tree). The cap follows the width of `index_within`: widening that field (see the xref reader's `as u16`, which silently wraps index 65,536 to 0) has to move it too. Measured 2026-10-07: 65,537 objects with the catalog at index 65,536 fail with `catalog is not a dict`; 65,536 open. Decided in #158: widen the index to `u32` and keep the table bounded by storing each offset in 4 bytes and reading at most `min(/N, decoded.len() / 4)` pairs, so it never exceeds the decoded data (#161 bounds that). Dropping the cap without shrinking the entries brings back the 335.5 MB case above.
- When the pairs run out before `/N` (a token that is not an integer, or one that fails to tokenize), parsing stops and the pairs read so far are used; an index past them is `ObjectNotFound`. The table is cached either way, so a broken index is still parsed once (*measured* by `test_objstm_index_that_fails_to_tokenize_keeps_the_pairs_before_it`).
  - **Maintainer call (2026-09-30, #132 check-it)**: a pair that fails to tokenize ends the index like a non-integer token, so the pairs before it resolve. Before #132 such an index failed every object in the stream with `InvalidToken` (*measured* by the lens reader: `justpdf info` on index `2 0 1 37 > `, `/N 3` — master exit 1, this change exit 0). Shown: those two behaviours; that the non-integer leniency and the tokenize-error strictness differed only by `?` versus `_ => break`, which nobody had decided; and that MuPDF errors the whole stream in both cases. The alternative was to keep the error and cache the failure. This call did not cover what to do when decoding the stream or reading `/First` fails (not cached; carried as a candidate). Measured 2026-10-07: a Flate stream that inflates to 32 MB and then fails costs about 100 ms on every object load (64 loads: 5.7 s); a missing `/First` costs 0.07 ms per load. Decided in #159: record the failure per stream (rebuilding data-only error variants, otherwise `InvalidObject` with the message), never record `CircularReference` (it depends on the entry path), and clear recorded failures with the cache on `authenticate`.
- **Offset check.** When `/First` plus a pair's offset is negative, overflows, or lands outside the decoded data, that index alone is an `InvalidObject` error; other indices of the same stream are unaffected. A negative `/First` makes every index an error. Before #132, `as usize` wrapped negatives: a debug build panicked on `first + offset` overflow, and a release build read another object (both *measured* 2026-09-30: the panic by `test_objstm_negative_offset_is_an_error` against the old code, the misread as `justpdf info` failing with "catalog has no /Pages"; that the object read was the Pages dictionary is *inferred* from the offsets).
  - **Maintainer call (2026-09-30, #132 read-it)**: include the offset check in #132. Shown: the release misread (reproduced), the debug panic (then inferred, observed later by the test), and that it is the same code that builds the table. The alternative was to carry it as a separate follow-up. This call did not cover checking a pair's object number against the xref (tracked in #109).
- **Encryption**: the reading side decrypts the whole ObjStm with the stream's number, and objects taken out of it do not go through [Object decryption](object-decryption.md) again (ISO 32000-1 §7.5.7). Writing-side packing does not get encryption.
- **Generation**: an object stream and the objects in it are at generation 0, objects at generation ≠ 0 are not packed, and a new object stream gets a new number, not a freed one (ISO 32000-1 §7.5.7). The writing side has two copies. `DocumentModifier::pack_object_streams` packs only objects whose writer generation is 0, and takes container numbers from the writer's `next_obj_num` (above every source number). The public `pack_object_streams` takes only a slice of numbers and objects, so it treats every object as generation 0 and numbers containers above the largest number. The two share `pack_objects` (with the eligibility check and number allocation injected). The writer-side xref stream serialization (`serialize_writer_with_xref_stream`) refuses a compressed object or container at a generation ≠ 0 with `InvalidObject` — packing the writer's objects through the public function does not silently write a null reference.
  - **Maintainer decision (2026-09-29, #106)**: a new entry point holding the writer + a serialization guard (B+F). Shown: lens's table of options — add a generation map to the public signature (A: a breaking change, and external callers cannot get the real map), a new entry point (B), fix only the inactive internal packer (C: leaves the public path open), document only (D), and the guard (F). A verdict-withheld item (F2), that a container number can inherit the generation of a source number GC deleted, was shown too. The public slice function's signature was not changed. This decision did not cover the rest of the eligibility rules (whether to exclude `/Info`, `/Length` value objects).
- When `max_objects_per_stream` is 0, `pack_objects` refuses with `InvalidObject` — before, `chunks(0)` panicked (#106).
- Writing-side packing is disabled in the [Compress pipeline](compress-pipeline.md) (`pack_into_object_streams` is dead code and calls `DocumentModifier::pack_object_streams`).

## Reference behaviour
The only sentence checked against the ISO 32000-1:2008 §7.5.7 text (Adobe's free copy, 2026-09-27) is the encryption one, "strings occurring anywhere in an object stream shall not be separately encrypted" — reading-side decryption follows it ([Object decryption](object-decryption.md)). On 2026-09-29 (#106) the generation sentences were checked against the same copy (pdftotext): "Objects with a generation number other than zero" in the list of objects not to pack, "The generation number of an object stream and of any compressed object shall be zero", and new object streams and compressed objects get "new object numbers, not old ones taken from the free list". MuPDF `pdf-write.c`'s `objstm_gather` also leaves out objects at a generation ≠ 0. On 2026-09-30 (#132) the index wording was compared against the same copy (pdftotext): the stream data holds "N pairs of integers separated by white space" (object number, then byte offset "relative to the first object"), "The offsets shall be in increasing order", and "A conforming reader shall rely on the First entry in the stream dictionary to locate the first object". The reader follows `/First`; it does not check that offsets increase, and it bounds nothing by the next offset (*inferred* from the code). MuPDF `pdf_load_obj_stm` (`vendor/mupdf-reference/source/pdf/pdf-xref.c`, *inferred* from its source) differs in four ways: it parses a stream once by parsing every object in it into the xref entries on first access; it rejects `/N` above `PDF_MAX_OBJECT_NUMBER` (8388607) and preallocates that many; it treats a non-integer token among the pairs as an error for the whole stream; and it finds an object by the pair's object number and bounds it by the next offset. The eligibility rules and ISO 32000-2 §7.5.7 were not compared.

## Cross-cutting invariants
- [Source generation](../invariant/source-generation.md) — objects inside an object stream must be at generation 0 (ISO 32000-1 §7.5.7). The `/First` rule is shared by two sites, but it is a design rule of one format, so it lives here in the Design model.

## Blast radius
- [xref](xref.md) — the source of type 2 entries. It pairs with xref stream writing (`write_xref_stream`).
- [Object decryption](object-decryption.md) — compressed objects get only the ObjStm decryption.
- [Compress pipeline](compress-pipeline.md) — where packing would be turned back on. Turning it on means re-checking the viewer compatibility problem (the reason given in the comment).
- [File serialization](file-serialization.md) — `serialize_pdf_with_xref_stream` receives the packing result.
- [Document access](document-access.md) — owns the decoded stream cache.

## Known holes / open
- Packing is implemented but disabled in the compression pipeline (the CHANGELOG 0.1.3 entry and the design doc record this state).
