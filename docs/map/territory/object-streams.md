# Object streams (ObjStm)

## What it is
A format that packs small non-stream objects into a `/Type /ObjStm` stream. The read side turns an xref type-2 entry into an object: it loads, decrypts and decodes the container, caches it with its offset table, and parses the object at `/First` plus the pair's offset. The write side packs eligible objects in the `num off … data` layout and returns the type-2 entry information. The two sides share the one format and do not call each other.

## Governing decisions
**None.** The maintainer calls below were made on issues (#106, #132), not in a record.

## Design model
Read side, `justpdf-core/src/parser.rs` (*inferred* from the code unless marked):
- **`/First` is authoritative.** Inferring where the data starts from the tokenizer position after the index pairs is off by the whitespace padding; the comment in `load_compressed_object` states this rule, and the writer's `build_object_stream` emits exactly that padding. Pinned by `test_objstm_first_padding_regression`.
- **The offset table is built once per stream.** Right after decoding, `parse_obj_stream_offsets` reads the index pairs into an `ObjStm` (decoded bytes plus the absolute offset of each index), cached in `decoded_obj_streams`; loading an object only looks the table up (`test_objstm_offsets_are_parsed_once_per_stream`). Before #132 the cache held `/N` and every first load re-tokenized the pairs from byte 0: O(N²) for N objects. *Measured* by `justpdf text` on a generated file with every page in one object stream, single runs: 10.1 s → 97 ms at 8,000 pages, 74.6 s → 286 ms at 16,000 (release, 2026-09-30). After the fix the same pages as plain objects and in an object stream take the same time (min of 5 runs, 16,000 pages: 156 ms vs 153 ms).
- **`/N` does not size an allocation.** It only bounds how many pairs are read (`n.min(OBJ_STREAM_ADDRESSABLE_INDICES)`); the table grows by the pairs actually read (`test_objstm_huge_n_resolves_the_pairs_present`). Before #132 it was `Vec::with_capacity(/N)`: `/N 2^40` aborted the process trying to allocate 17.6 TB (*measured* 2026-09-30, `justpdf info`, exit 127), and `/N 1e8` allocated 1.6 GB (reported in #132, not re-measured).
- **The table stops at the indices an xref entry can address.** `XrefEntry::Compressed::index_within` is a `u16`, so the table holds at most 65,536 entries (`OBJ_STREAM_ADDRESSABLE_INDICES`, 1 MiB at 16 B each) and is shrunk to fit (`test_obj_stream_offsets_stop_at_the_indices_an_xref_entry_can_address`). Without the cap the table lived for the document's lifetime at up to ~4.2× the decoded bytes (16.8 B per shortest pair `"1 2 "`): a 62.6 KB Flate stream of 16M pairs retained 335.5 MB. With the cap the same file retains 68.2 MB against 67.2 MB on master, and peaks at 68.3 MB against master's 323 MB (*measured* 2026-09-30 with an allocation-counting probe linked against each tree). The cap follows the width of `index_within`; widening that field ([Xref](xref.md)) has to move the cap too. *Measured* 2026-10-07: 65,537 objects with the catalog at index 65,536 fail with `catalog is not a dict`; 65,536 open.
- When the pairs run out before `/N` (a token that is not an integer, or one that fails to tokenize), reading stops and the pairs read so far are used; an index past them is `ObjectNotFound` (`test_objstm_n_above_the_pairs_present_resolves_them`, `test_objstm_n_below_the_pairs_present_leaves_later_indices_unfound`). The table is cached either way, so a broken index is read once (`test_objstm_index_that_fails_to_tokenize_keeps_the_pairs_before_it`).
  - Maintainer call (2026-09-30, #132 check-it): a pair that fails to tokenize ends the index like a non-integer token, so the pairs before it resolve. Before #132 such an index failed every object in the stream with `InvalidToken` (*measured* then: `justpdf info` on index `2 0 1 37 > `, `/N 3` — master exit 1, the change exit 0). Shown: those two behaviours; that the non-integer leniency and the tokenize-error strictness differed only by `?` versus `_ => break`, which nobody had decided; and that MuPDF errors the whole stream in both cases. The alternative was to keep the error and cache the failure. The call did not cover a stream whose decoding or `/First` fails (see Known holes, #159).
- **Offset check.** When `/First` plus a pair's offset is negative, overflows, or lands outside the decoded data, that index alone is an `InvalidObject` error; other indices of the stream are unaffected. A negative `/First` makes every index an error (`test_objstm_negative_offset_is_an_error`, `test_objstm_offset_past_the_data_is_an_error`, `test_objstm_negative_first_is_an_error`). Before #132, `as usize` wrapped negatives: a debug build panicked on `first + offset` overflow and a release build read another object (both *measured* 2026-09-30; that the object read was the Pages dictionary is *inferred* from the offsets).
  - Maintainer call (2026-09-30, #132 read-it): include the offset check in #132, rather than carry it as a follow-up. Shown: the release misread (reproduced), the debug panic, and that it is the same code that builds the table.
- The pair's object number is read and discarded; only the index is used. The container is loaded at generation 0 through `load_object_raw`, so it skips the `defines` check of [Document access](document-access.md). An object is parsed with `parse_object` from its offset; nothing bounds it by the next pair's offset.
- **Encryption:** the container is decrypted as a whole with its own number and generation 0, and objects taken out of it skip [Object decryption](object-decryption.md) (`load_object` returns early for a `Compressed` entry), per ISO 32000-1 §7.5.7. Write-side packing does no encryption.
- **Input bound:** the table is bounded by the decoded data and by 65,536 entries. The decoded data itself has no bound ([Stream filters](stream-filters.md), #161). Every decoded container stays in `decoded_obj_streams` for the document's lifetime, with no eviction; only `authenticate` clears it.

Write side, `justpdf-core/src/writer/` (*inferred* unless marked):
- **Eligibility** (`is_eligible`): streams, the catalog, the pages root, the encryption dictionary, a `/Type /XRef` dictionary and `null` are not packed.
- **Generation:** an object stream and the objects in it are at generation 0, objects at generation ≠ 0 are not packed, and a new object stream takes a new number, not a freed one (ISO 32000-1 §7.5.7). There are two entry points. `DocumentModifier::pack_object_streams` packs only objects whose writer generation is 0 and takes container numbers from the writer's `next_obj_num`, above every source number. The public `pack_object_streams` takes a slice of numbers and objects, so it treats every object as generation 0 and numbers containers above the largest number given. Both share `pack_objects`, with the eligibility check and number allocation passed in. `serialize_writer_with_xref_stream` refuses a compressed object or container at a generation ≠ 0 with `InvalidObject`, so packing the writer's objects through the public function cannot silently write a reference that reads as null.
  - Maintainer decision (2026-09-29, #106): a new entry point on the writer plus a serialization guard (options B+F). Shown: lens's table of options — add a generation map to the public signature (A: breaking, and external callers cannot get the real map), a new entry point (B), fix only the inactive internal packer (C: leaves the public path open), document only (D), and the guard (F). A withheld item (F2) was shown too: a container number can inherit the generation of a source number that GC deleted. The public slice function's signature did not change. The decision did not cover the rest of the eligibility rules (whether to exclude `/Info`, or objects that are `/Length` values).
- `max_objects_per_stream == 0` is refused with `InvalidObject` by `pack_objects`; before #106 `chunks(0)` panicked (`test_pack_object_streams_refuses_zero_objects_per_stream`).
- Packing is not reached from product code: in `compress_pdf` the call is commented out ("compatibility issues with some PDF viewers"), and `pack_into_object_streams` is `#[allow(dead_code)]`. The CHANGELOG 0.1.3 entry records the same state.

## Reference behaviour
- ISO 32000-1:2008 §7.5.7, Adobe's free copy, read with pdftotext:
  - 2026-09-27: "strings occurring anywhere in an object stream shall not be separately encrypted". The read side follows it ([Object decryption](object-decryption.md)).
  - 2026-09-29 (#106): "Objects with a generation number other than zero" are in the list of objects not to pack; "The generation number of an object stream and of any compressed object shall be zero"; new object streams and compressed objects get "new object numbers, not old ones taken from the free list".
  - 2026-09-30 (#132): the stream data holds "N pairs of integers separated by white space" (object number, then byte offset "relative to the first object"); "The offsets shall be in increasing order"; "A conforming reader shall rely on the First entry in the stream dictionary to locate the first object". The reader follows `/First`; it does not check that offsets increase and bounds nothing by the next offset (inferred from the code).
- MuPDF `pdf-write.c` `objstm_gather` also leaves out objects at a generation ≠ 0 (#106, 2026-09-29).
- MuPDF `pdf_load_obj_stm` (`source/pdf/pdf-xref.c`, read from its source for #132, 2026-09-30) differs in four ways: it parses every object of a stream into the xref on first access; it rejects `/N` above `PDF_MAX_OBJECT_NUMBER` (8388607) and preallocates that many; it treats a non-integer token among the pairs as an error for the whole stream; and it finds an object by the pair's object number and bounds it by the next offset.
- Not compared: the eligibility rules, and ISO 32000-2 §7.5.7.

## Cross-cutting invariants
- [Source generation](../invariant/source-generation.md) — objects inside an object stream must be at generation 0, and packing must not write a reference at another generation. The `/First` rule is shared by the read and write sides, but it is one format's rule, so it lives in this note's Design model.
- [Encryption identity](../invariant/encryption-identity.md)

## Blast radius
- [Xref](xref.md) — the source of type-2 entries. The `u16` width of `index_within` is also this table's cap; the two move together. The writer's xref stream (`write_xref_stream`) carries the entries packing returns.
- [Object decryption](object-decryption.md) — compressed objects get only the container's decryption. If either side changes who decrypts, strings are decrypted twice or not at all.
- [Compress pipeline](compress-pipeline.md) — where packing would be turned back on. Doing so means re-checking the viewer compatibility problem given in the comment.
- [File serialization](file-serialization.md) — `serialize_pdf_with_xref_stream` and `serialize_writer_with_xref_stream` take the packing result. The generation guard lives there.
- [Document access](document-access.md) — owns the container cache, its clearing on `authenticate`, and the `load_object_raw` path that skips `defines`.
- [Stream filters](stream-filters.md) — containers are decoded with `decode_stream`; a decoded-size limit there (#161) is what bounds this table's input.

## Known holes / open
- The pair's object number is not compared with the requested one, so a wrong xref index returns another object. Decided in #109: compare them, and on a mismatch use the slot whose pair names the requested number (as pdf.js does), then the file-wide header index, then `Null`. Tracked: #109
- A container whose decoding fails, or that lacks `/First`, is not cached, so every object in it re-reads and re-decodes it. *Measured* 2026-10-07: a Flate stream that inflates to 32 MB and then fails costs about 100 ms per object load (64 loads: 5.7 s); a missing `/First` costs 0.07 ms per load. Decided in #159: record the failure per stream (rebuilding data-only error variants, otherwise `InvalidObject` with the message), never record `CircularReference` (it depends on the entry path), and clear recorded failures with the cache on `authenticate`. Tracked: #159
- Widening `index_within` to `u32` was decided in #158, keeping the table bounded by storing each offset in 4 bytes and reading at most `min(/N, decoded.len() / 4)` pairs, so it never exceeds the decoded data (#161 bounds that). Dropping the cap without shrinking the entries brings back the 335.5 MB case above. Tracked: #158
- Packing is implemented but not reachable from product code (above).
