# Font encodings (simple fonts)

## What it is
The tables and rules that connect a simple font's one-byte codes, glyph names and Unicode: the base encodings (Standard, MacRoman, WinAnsi, PDFDoc, Identity), `/Differences`, the Adobe Glyph List, and the choice of a TrueType or bare-CFF glyph for a code. Text extraction decodes through it when ToUnicode has no answer; the renderer and font subsetting pick glyphs through it; the writing side encodes through its inverse (`encode_winansi`, the Symbol and ZapfDingbats tables, and `FontEncoder` for a font a document already holds). The PDF text-string decoder (`decode_text`, PDFDocEncoding or a UTF-16BE/UTF-8 BOM) lives here too.

## Governing decisions
**None.** No decision record. Decisions made on issues are written below with their source. [ADR 0001](../../adr/0001-crates-split-by-dependency-layer.md) is why Type1 subsets stay refused by `FontEncoder` (#341), but it decides crate layers, not encodings.

## Design model
Status: from reading the source and the tests, plus maintainer decisions on #221, #223, #178 and #341.

- **Decoding order for a simple font** (text extraction, `CharCollector`): ToUnicode when it maps the code, else a `/Differences` glyph name through the AGL, else the base encoding's table (`FontInfo::decode_simple_code`). The base encoding is the `/Encoding` name, or an encoding dictionary's `/BaseEncoding`, else `StandardEncoding` (`parse_encoding`). A symbolic font's built-in encoding in the font program is not read for text. An indirect `/Encoding` is resolved before `parse_font_info` by `resolve_font_entries` ([Font loading](font-loading.md)); until #221 text extraction let an indirect one fall back to `StandardEncoding` (`indirect_encoding_dictionary_is_resolved`, `indirect_encoding_name_is_resolved`; measured: pass at 88b2a08, 2026-10-30).
- `decode_simple_code` takes the **last** `/Differences` entry for a code (`iter().rev()`), so a later entry wins.
- A code read two bytes at a time (Identity or Type0) goes to `decode_text` with `Encoding::Identity`, which is lossy UTF-8 of the bytes (inferred, `text/mod.rs` and `decode_text`). A simple font whose `/Encoding` is the name `Identity-H` is read two bytes at a time too (`Encoding::from_name`, `ResolvedFont::is_two_byte`; inferred).
- **One `/Differences` parser** (`parse_differences`) serves simple fonts and Type3 (`type3::parse_encoding_differences` calls it). A code outside 0–255 is skipped, and a run stops at 255 instead of wrapping.
- **Glyph name to text** follows the AGL rules (`glyph_name_to_unicode`): the part before the first `.`, split at `_`, each component looked up in the AGL or read as `uniXXXX…` / `uXXXX`–`uXXXXXX` (upper-case hex only; a value that is not a scalar, such as a surrogate, yields nothing). A name that maps to nothing (`g123`) yields no text, not the code's base-encoding letter (`unknown_glyph_name_yields_no_letter`). The whole AGL is vendored (`font/agl.rs`, 4,281 names, measured by count 2026-10-30; the BSD-3-Clause notice kept in the header). Vendoring all of it rather than the ~330 names the Annex D encodings use was the maintainer's call on #221 (2026-10-07), because `/Differences` in real files also names Cyrillic, Greek and `afii` glyphs; pdf.js and MuPDF carry the whole list too (#221).
- **StandardEncoding and MacRomanEncoding** decode through their own Annex D tables (`STANDARD_TO_UNICODE`, `MAC_ROMAN_TO_UNICODE`); a code with no glyph in the table yields nothing (`decode_table`). Until #221 both decoded through the WinAnsi table (`mac_roman_decodes_through_its_own_table`, `standard_encoding_decodes_per_annex_d`).
- **Generated tables.** `scripts/gen-font-tables.py` writes `font/agl.rs`, `font/encoding_tables.rs` (the Annex D code → Unicode tables and the `STANDARD_GLYPH_NAMES`, `MAC_ROMAN_GLYPH_NAMES`, `WIN_ANSI_GLYPH_NAMES` code → name tables) and `font/builtin_encoding_tables.rs`, from the AGL's `glyphlist.txt`, pdf.js `src/core/encodings.js`, and unicode.org's Adobe mappings `symbol.txt` and `zdingbat.txt`. It runs `rustfmt --edition 2024` on its output, so regenerating reproduces the committed files (inferred from the script; not rerun 2026-10-30, its inputs are not in the repo).
- **The WinAnsi table stays hand-written** (`WINANSI_TO_UNICODE`). The generator prints how it differs from Annex D. Measured 2026-10-07 (#221): it agrees on every code except 0x7F, 0x81, 0x8D, 0x8F, 0x90, 0x9D (pdf.js: bullet; here the code as a C1 control), 0xA0 (Annex D glyph `space`; here U+00A0) and 0xAD (`hyphen`; here U+00AD). `winansi_char` gives `None` for 0x81, 0x8D, 0x8F, 0x90 and 0x9D, but `decode_winansi` reads the table directly and gives the C1 control (inferred).
- **Writing WinAnsi.** `encode_winansi` is the inverse of `winansi_char`: ASCII as it is, any other character its Windows-1252 code, `?` when it has none, the five codes without a glyph included. justpdf's standard fonts other than Symbol and ZapfDingbats are written with `/Encoding /WinAnsiEncoding` (`standard_font_dict`, #34), so their `'` and `` ` `` extract as themselves; a file with no `/Encoding` still decodes through StandardEncoding.
- **Writing Symbol and ZapfDingbats.** Their built-in encodings run Unicode → code (`symbol_code`, `zapf_dingbats_code`, binary search over `SYMBOL_FROM_UNICODE` and `ZAPF_DINGBATS_FROM_UNICODE`, 194 and 203 entries, several Unicode values to one code; measured by count 2026-10-30). The generator asserts each entry's glyph name equals the Annex D name pdf.js gives that code (all agreed, measured 2026-10-22, #336). A standard `Font` for those two encodes through them ([CJK font embedding](cjk-font-embedding.md)). `standard_font_dict` writes no `/Encoding` for them, so text extraction decodes their codes through StandardEncoding and an `α` written as Symbol code 0x61 extracts as `a` (inferred).
- **Code to TrueType glyph.** `truetype_glyph_candidates(face, code, encoding, differences, symbolic)` returns a simple TrueType code's candidate GIDs, most preferred first. First the §9.6.6.4 choice pdf.js makes (`src/core/fonts.js`, read raw 2026-10-07, #223):
  - one `cmap` subtable (`preferred_subtable`): non-symbolic (3,1), else (1,0); symbolic (3,0), else (1,0); a (0,x) Unicode table is a candidate too;
  - for a non-symbolic font with an `/Encoding` and a (3,1) or (1,0) table, the code's glyph name (`/Differences`, else a MacRoman or WinAnsi base, else Standard) read as Unicode through the AGL, or as its MacRoman code;
  - for (3,0), the code in `0xF0xx`; otherwise the code itself;
  - then `post` by name (`/Differences` or a MacRoman/WinAnsi base name), forced first for a (0,x) table.

  Then the fallbacks: every subtable with the code and its `0xF000`/`0xF100`/`0xF200` prefixes, the names through any Unicode subtable and `post`, the code's WinAnsi character, and the code as a GID. `encoding` is `None` when the font has no `/Encoding`, and then even (3,1) is read with the raw code, as pdf.js does. One function with two callers (the renderer draws the first candidate, subsetting keeps all) was the maintainer's call on #223 (2026-10-07).
- **Code to bare-CFF glyph.** `cff_simple_glyph` takes the code's glyph name from `encoding_glyph_name` (the `/Differences` name, else the name in `explicit_base_encoding`, the base the dictionary itself names) and looks it up by name; with no name it uses the program's built-in encoding. `cff_cid_to_gid` maps CIDs to GIDs through a CID-keyed program's charset, `None` for a name-keyed one. `cff_has_glyph`: GID ≠ 0, below the glyph count, and an outline or an advance. All are in core (`font/glyph_select.rs`) and shared by the renderer and `FontEncoder` (#341).
- **Encoding into a font a document already holds** (`FontEncoder`, `font/encoder.rs`, #178), used by form appearances for a `/DA` font from `/DR`. It is the inverse of how text extraction decodes that font (`content::interpret::load_font` and `CharCollector`), so decoding what it writes gives back the text. Each character gets the first code whose decoded text is exactly that one character:
  - a simple font: its 256 codes in order, each through its ToUnicode CMap, else `decode_simple_code`;
  - a Type0 font: its ToUnicode codes (`ToUnicodeCMap::entries`, sorted by code, so the lowest code wins; ranges walked for at most 2^20 codes, `MAX_RANGE_CODES`), each written at the byte length that is one whole code of the encoding CMap's codespace (`code_bytes`, `EncodingCMap::is_whole_code`).
- **What `FontEncoder` refuses (`None`)**, corrected 2026-10-30 from the code:
  - a Type0 font without ToUnicode, or whose `/Encoding` is a name other than `Identity-H`/`Identity-V` (#306);
  - a subset font (six-letter `+` tag) with neither a `FontFile2` nor a `FontFile3` stream, so a Type1 (`FontFile`) subset (`a_subset_type1_font_gives_no_appearance`);
  - **any** font, subset or not, whose `FontFile2` does not parse as TrueType (`Face::parse(…).ok()?`) or whose `FontFile3` does not parse as bare CFF (`cff::Table::parse(…)?`), so a `/FontFile3 /Subtype /OpenType` (CFF in an sfnt) is refused (inferred, read from `FontEncoder::new`; the old note limited this to subsets). Tracked: #361.
  - A non-subset font with no embedded program, or with only a Type1 `FontFile`, is accepted without a glyph check.
- Decisions on the refusals:
  - Maintainer decision (2026-10-22, #178): only TrueType programs were checked for glyphs; CFF and Type1 subsets were refused rather than trusted, on the ground that "core has no Type1 parser and only a CFF charset reader".
  - #341 revisited the CFF half: core's own `ttf-parser` 0.25 already parses bare CFF (`cff::Table`), and the renderer drew `/FontFile3` with it, so that half of the call was untested rather than settled (#341 triage, 2026-10-23).
  - Maintainer decisions (2026-10-23, #341): CFF subsets are checked through `cff::Table`, with no new dependency. Type1 subsets stay refused, since moving `hayro-font` into core would change ADR 0001's layers.
- **Which codes count.** Where the font embeds `FontFile2`, a code counts only if the glyph it draws is in the program: for a simple font the first of `truetype_glyph_candidates` (the glyph the renderer draws), for a Type0 font the CID through `/CIDToGIDMap` (a stream, or Identity when it is not one). A glyph is there when it is not GID 0, is below `numGlyphs`, and has an outline or an advance (`has_glyph`; technical decision). A subset that keeps glyph IDs, `subset_font` among them, leaves a dropped glyph with an empty outline and a zero advance (read from `build_subset_hmtx`; `a_simple_truetype_subset_encodes_only_the_glyphs_it_kept`). justpdf's own Type0 fonts map every CID in ToUnicode, also those drawn as `.notdef`, so following `/CIDToGIDMap` is what keeps such a character out (`a_justpdf_type0_font_does_not_encode_what_it_drew_as_notdef`). For a CFF program the same bar is `cff_has_glyph`, so a space still encodes; "a non-empty outline", which the #341 brief said, would refuse spaces (derivation, #341). Measured: the 14 tests in `tests/form_da_font.rs` pass at 88b2a08 (2026-10-30).
- **`FontEncoder` also measures** (#325): each code keeps its width, from a simple font's `/Widths` (or the Standard 14 table `parse_font_info` fills in) by code, or from a Type0 descendant's `/W` by CID. `width(text)` is their sum in 1/1000 units. `ascent_descent()` gives the descriptor's ascent and descent magnitude unless both are 0 (the descendant's for a Type0 font), else `standard14_ascent_descent`. The Type0 width path has no test of its own (inferred). Tracked: #360.
- **PDF text strings.** `decode_text` handles a UTF-16BE BOM (surrogate pairs joined, an unpaired one dropped) and a UTF-8 BOM before the encoding's table. The annotation, outline, form and signature readers do not use it; they use `from_utf8_lossy` (inferred, `git grep`) — [Text string encoding](../invariant/text-string-encoding.md).
- **Input bounds.** Codes are one byte, so every table lookup is bounded by 256. `/Differences` is as long as its array; nothing else bounds it (inferred).

## Reference behaviour
- ISO 32000-2 Annex D tables as transcribed by pdf.js (`src/core/encodings.js`), and the Adobe Glyph List (`adobe-type-tools/agl-aglfn` `glyphlist.txt`) — the generator's inputs. The tests check #221's measurements: `/Differences [65 /B]` `(A)` → `B`, `/MacRomanEncoding` `<8E>` → `é` (before #221: `A`, `Ž`).
- pdf.js `src/core/fonts.js` (read raw 2026-10-07, #223) — the §9.6.6.4 TrueType glyph choice `truetype_glyph_candidates` follows.
- unicode.org `Public/MAPPINGS/VENDORS/ADOBE/symbol.txt` and `zdingbat.txt` — the Symbol and ZapfDingbats tables, cross-checked against pdf.js's Annex D names (2026-10-22, #336).

## Cross-cutting invariants
- [Content text encoding](../invariant/content-text-encoding.md) — `encode_winansi` and the built-in tables are the writing side of these encodings.
- [Text string encoding](../invariant/text-string-encoding.md) — `decode_text` is the decoder the other readers skip.
- [Font resolution](../invariant/font-resolution.md) — text decodes with these tables; render and subsetting pick glyphs with `truetype_glyph_candidates` and `cff_simple_glyph`.

## Blast radius
- [Text extraction](text-extraction.md) — `CharCollector` decodes one-byte codes with `decode_simple_code` and two-byte codes with `decode_text`; a change to a table changes extracted text.
- [Glyph rendering](glyph-rendering.md) — draws the first `truetype_glyph_candidates` entry and the `cff_simple_glyph` result; a reorder here changes the glyph drawn.
- [Font subsetting](font-subsetting.md) — keeps every candidate; a candidate the renderer may draw that subsetting does not keep loses its outline.
- [SVG renderer](svg-renderer.md) — does not decode a simple font's `/Encoding` at all; a fix there should call `decode_simple_code` so the two agree.
- [Form appearance](form-appearance.md) — `FontEncoder` decides whether a `/DA` font can draw a value and how wide it is; a change to the decoding order or the refusals changes which fields get an appearance.
- [Type3 fonts](type3-fonts.md) — reads `/Differences` through `parse_differences`.
- [ToUnicode](tounicode.md) — the higher-priority mapping; `FontEncoder` inverts it.
- [CJK font embedding](cjk-font-embedding.md) — standard `Font`s encode through `winansi_code`, `symbol_code` and `zapf_dingbats_code`; a table change changes what they write.

## Known holes / open
- A symbolic simple font without ToUnicode decodes through StandardEncoding, not its built-in encoding (inferred). Text justpdf writes in Symbol or ZapfDingbats therefore does not extract as written (inferred).
- The SVG renderer ignores a simple font's `/Encoding`: without ToUnicode a code below 128 is emitted as itself and a code at or above 128 as a placeholder. Tracked: #297.
- `FontEncoder` refuses a `/FontFile3 /Subtype /OpenType` program (CFF in an sfnt), subset or not. Tracked: #361.
- `FontEncoder`'s Type0 width path has no test of its own. Tracked: #360.
- PDF text strings are read as lossy UTF-8 outside this file. Tracked: #33.
- Open question for the maintainer: should a non-subset font whose `FontFile2`/`FontFile3` does not parse be refused (the code does), or encoded without a glyph check like a font with no program? The #178 and #341 decisions speak only of subsets.
