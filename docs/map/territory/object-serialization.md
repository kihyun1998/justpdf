# Object serialization

## What it is
The side that turns `PdfObject` values into PDF syntax bytes. `impl Display for PdfObject` writes every object except streams, and `serialize_object` writes a stream itself, setting `/Length` to `data.len()` (inferred, `writer/serialize.rs — serialize_object`). It is the bottom layer of every path that produces a file: creation, modification, object streams, linearization, incremental save, encryption and signing all reach `serialize_object` or `serialize_dict` (inferred, `git grep -n serialize_object -- 'justpdf*/src'`).

## Governing decisions
**None.** No ADR covers write syntax. The decisions that shape it were made on issues (#28, #85) and are attributed below.

## Design model
- **The rules live in one place**: `write_name`, `write_string` and `write_real` (writing to any `fmt::Write`) are the rules (inferred, `object/types.rs`). Display, `serialize_dict` and content operator writing (`ContentOp::write_to` and `Operand::write_to` in `content/operator.rs`) call them. Into a byte buffer they write through `ByteSink`. Where a fragment string is needed, they go through `name_syntax`, `string_syntax` and `real_syntax` (inferred). Before #29 there were three copies of the name rule: Display `Name`, Display `Dict` keys and `write_escaped_name` (#29).
- **Numbers in generated content** are written with `Number`. An integral value within the 32-bit range (`i32::MIN..=i32::MAX`) is written as an integer. Any other value goes through `write_real`. NaN and ±Inf go through the same substitution as reals (inferred, `Number`). This is the generator-reals site of [Object syntax roundtrip](../invariant/object-syntax-roundtrip.md) (#90).
- **Names**: `#`, the delimiters `/ ( ) < > [ ] { } %`, every byte `<= 0x20` and every byte `>= 0x7F` are escaped as `#XX` (inferred, `write_name`). `serialize_dict` is a second copy of Display `Dict`. The only difference is that it writes stream values with `serialize_object` (inferred).
- **Strings**: a string is written as a literal `(…)` only when every byte is 0x20–0x7E or one of `\n`, `\r`, `\t`. Otherwise it is written as hex (inferred, `write_string`). In a literal, `(`, `)` and `\` are escaped, and CR is written as `\r` (#28). The [Tokenizer](tokenizer.md) turns line breaks (CR, CRLF) inside a literal into LF, as ISO 32000-1 §7.3.4.2 requires, so a raw CR would read back as LF. Before #28, encrypting a document whose source `/ID` first element held a CR changed the `/ID[0]` read back. The R3/R4 file key then went wrong, and neither justpdf nor qpdf could open the file (#28; `test_build_with_encryption_keeps_a_permanent_id_that_holds_a_carriage_return`). The hex rule exists because `b as char` on the literal path turned high bytes into UTF-8 multibyte sequences and broke binary strings such as `/O` and `/U` (commit 7be23c0, 2026-06-14; the comment in `write_string`).
- **Reals**: always written with a decimal point: `1.0`, `-0.0`, `100000000000000000000.0`, even for integral values (inferred, `write_real`; #28). A real that is not integral is written with Rust `f64` Display as is: the shortest round-trip digits, never exponent notation. NaN is written as `0.0` and ±Inf as ±`f32::MAX`, because PDF cannot express them and Display cannot fail (inferred, `finite`). NaN only arises from computation, but Inf also comes in from files. The tokenizer parses real text with `parse::<f64>` (inferred, `tokenizer/mod.rs`), so a real beyond the `f64` range (`1` followed by 400 zeros and `.0`, for example) becomes `inf` and is written back as `f32::MAX` (assay and lens probes, 2026-09-25).
  - Before #28: `Real(1.0)` → `1` → `Integer(1)`, `Real(-0.0)` → `Integer(0)`, and `Real(1e20)` → integer text past i64, so **reading back was a parse error**. NaN and inf were written as `NaN` and `inf`, which are not valid PDF (#28, 2026-09-25).
  - **Maintainer decision (2026-09-25, #28 triage)**: always write a decimal point, and write substitutes for NaN and Inf. Alternatives offered: write integral values within the i64 range as integers, as MuPDF does (harmless under ISO 32000 §7.3.3, but it reads back as `Integer`, a different value under value comparison); or make NaN and Inf a `serialize_object` error. Facts offered as grounds: the reproduction above, MuPDF `pdf-object.c` `fmt_obj` (integral reals as `%d`) and `printf.c` `fmtfloat` ("NaN to 0, +Inf to FLT_MAX, -Inf to -FLT_MAX"). The ±Inf part is superseded by #85 (Known holes).
- **Streams**: Display prints a stream in a debug format that is not PDF (`<stream dict=… len=N>`) (inferred, `impl Display for PdfObject`). A stream must be written with `serialize_object`; writing it with `"{}"` breaks the file. At HEAD, the only Display call that writes file bytes is the non-stream arm of `serialize_object` itself (inferred, `git grep -nE 'write!\([a-z_]+, *"\{\}"' -- 'justpdf*/src'`). `clean`'s `bucket_key` uses Display text as a hash key, not as output.
- **Input size**: this layer writes whatever it is handed. Nothing here bounds the length of a string, name or stream, or the nesting depth of arrays and dictionaries. Display and `serialize_object` recurse once per nesting level (inferred).

## Reference behaviour
- MuPDF `source/pdf/pdf-object.c` `fmt_obj` writes integral reals as integers. justpdf goes the other way (decision above) (#28, 2026-09-25).
- MuPDF `source/fitz/printf.c` `fmtfloat` handles NaN and Inf. justpdf followed it until #85 (#28, 2026-09-25).
- MuPDF `pdf-lex.c` `acrobat_compatible_atof` truncates an integer part of 10 or more digits to 32 bits; this is the ground for #85 (#85, 2026-10-23).
- The checks against the spec text (2026-09-25, #28) used ISO 32000-1: §7.3.4.2 (a line break inside a literal reads as 0Ah) and §7.3.3 (reals have a decimal point and no exponent notation, NOTE 1; an integer is allowed where a real is expected, NOTE 2). The ISO 32000-2 clauses (§7.3.3 numbers, §7.3.4 strings, §7.3.5 names) have not been checked.

## Cross-cutting invariants
- [Object syntax roundtrip](../invariant/object-syntax-roundtrip.md) — this note is the invariant's central site.
- [Text string encoding](../invariant/text-string-encoding.md) — serialization only preserves bytes. There is no encoder at this layer that turns a Rust `&str` into a PDF text string.

## Blast radius
- [Tokenizer](tokenizer.md), [Object model](object-model.md) — a changed write rule must still be read back as the same value. The write side assumes the read side's literal-string, name and real rules.
- [File serialization](file-serialization.md), [Incremental save](incremental-save.md), [Object streams](object-streams.md), [Linearization](linearization.md), [Signing](signing.md) — each writes its objects through `serialize_object` and assumes the bytes parse back. A rule that breaks round-tripping breaks every file they produce.
- [Object encryption](object-encryption.md), [Key derivation](key-derivation.md) — ciphertext strings and the binary `/O`, `/U`, `/OE`, `/UE` and `/Perms` values hold high bytes. They rely on the hex path to stay byte for byte; a literal path that re-encoded bytes broke authentication before (#20, commit 7be23c0).
- [Clean](clean.md), [Compress dedup](compress-dedup.md) — `bucket_key` hashes Display text. A Display change only changes which objects share a bucket, so a duplicate can be missed, never wrongly merged (merging is decided by `same_value`).
- Content writers ([Annotation appearance](annotation-appearance.md), [Form appearance](form-appearance.md), [Signature appearance](signature-appearance.md), [Document builder](document-builder.md)) — they write operator text through `Number`, `name_syntax` and `string_syntax`. A changed number or name rule changes every content stream they generate.

## Known holes / open
- A stream nested inside an array (at any depth) goes through Display and is written in the debug format. A stream that is a direct dictionary value is written in full by `serialize_dict`, but ISO 32000 requires a stream to be an indirect object, so that output is not valid PDF either (inferred, `serialize_dict`, `impl Display for PdfObject`).
- Out-of-range reals: finite values beyond the f32 range (1e300 → 301 digits) and very small values (5e-324 → 326 characters) are written as they are (#85). ISO 32000-1 Annex C.2 recommends staying within ±3.403e38. MuPDF and Acrobat read reals with an integer part of 10 or more digits truncated to 32 bits, so the `f32::MAX` written for ±Inf and `1e20` also read back as other values (MuPDF `pdf-lex.c` `acrobat_compatible_atof`, computed on #85). The maintainer decided on 2026-10-23 that reals are written within ±2147483647, that a magnitude below 1.175e-38 is written as 0, and that this applies to ±Inf too, replacing #28's ±`f32::MAX` (#85). `write_real` still writes ±`f32::MAX` at HEAD (inferred, `finite`). Tracked: #85
