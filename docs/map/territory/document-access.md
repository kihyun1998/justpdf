# Document opening, resolve and cache

## What it is
`PdfDocument` owns the source bytes (`Vec` or mmap), the merged xref, the parsed-object LRU cache, the decoded object-stream cache, the font-program cache and the encryption state, and turns references into objects with `resolve(&self)`. Every reading feature and every binding goes through this one type.

## Governing decisions
No decision record. Decided on issues:
- Maintainer decision (2026-09-29, #98): when a reference's generation differs from the one its xref entry defines, `resolve` returns `Null`, per ISO 32000-1 §7.3.10, "An indirect reference to an undefined object shall not be considered an error... it shall be treated as a reference to the null object". Shown: three options and how others behave (checked against their source: MuPDF `pdf-xref.c` looks up by number only and builds the key from the xref generation; pdf.js `xref.js` throws on a mismatch and reindexes in recovery mode; qpdf `QPDF_objects.cc` looks up by (number, generation) and silently gives null when absent); a measurement over 121 local PDFs (420,709 references) finding 0 generation mismatches and 0 objects at a generation ≠ 0, which did not decide between them; and that in #72 this leniency hid a write-side generation defect from the tests. Alternatives: (b) build the key from the xref generation and ignore the reference's, like MuPDF; (c) an error, like pdf.js. The decision did not cover checking the **object number** in the header (#109).
- A number missing from the xref resolving to `Null` (#108) is not a maintainer decision but a derivation from the same clause and #98; a better derivation can overturn it.
- Maintainer call (2026-10-08, #240): `font_program_decodes()` counts decode attempts, `#[doc(hidden)]`, for tests in other crates — chosen over a documented cache-size method (which cannot tell a cache from decoding and overwriting every time) and over core-only `#[cfg(test)]` counters (not visible to render tests).

## Design model
Rules read from the code (*inferred* unless marked).
- **Opening** (`from_pdf_data`): fewer than 8 bytes, or no `%PDF-X.Y` in the first 1024 bytes, is `NotPdf` (`parse_version`). Then [Xref](xref.md) loads the chain, and encryption is detected. `open` reads the whole file into memory; `open_mmap` (feature `mmap`) maps it.
- **Interior mutability:** the caches sit behind `RwLock`s, so `resolve` needs only `&self` and `PdfDocument` is `Sync`. No lock is held while an object is parsed.
- A cache hit takes the `write()` lock, because `LruCache::get` moves the key to the front; `LruCache::touch` finds the key by a linear scan of a `VecDeque`, so a hit costs up to the capacity (default `DEFAULT_CACHE_CAPACITY` = 2048, `set_cache_capacity`).
- **Encryption hooks:** a trailer `/Encrypt` reference is read through `load_object_raw` (no decryption); an inline `/Encrypt` dictionary is read from the trailer (`detect_encryption_inline`). Only the `Standard` security handler is accepted (`UnsupportedEncryption` otherwise). Opening tries the empty password. Before authentication, `resolve` of an uncached reference is `EncryptedDocument`. After it, `load_object` decrypts an ordinary object with its own number and generation; an object from an object stream comes back already decrypted with its container and skips this step ([Object streams](object-streams.md), [Object decryption](object-decryption.md)). The catalog's XML `/Metadata` stream is left undecrypted when `/EncryptMetadata false` applies (`is_plain_document_metadata`, `crypto::metadata_stream_left_plain`). `authenticate` clears all three caches.
- **Definition check:** for an uncached reference, `resolve` checks that the xref defines it (`defines`: the entry is in use and the reference's generation equals `XrefEntry::defined_generation`, which is the entry's generation for an in-use entry and 0 for an object in an object stream), and otherwise returns `Null`, not cached. Free entries, numbers missing from the xref and other generations are all `Null` by this one rule. So the key of a `resolve` that succeeds is always built from the xref generation. Before #98 it was built from the reference's generation: a reference at the wrong generation decrypted to garbage under RC4 and to a padding error under AES-128 (R6 keys do not depend on the generation). Before #108 a missing number was an `ObjectNotFound` error. Pinned by the `test_a_reference_*` and `test_an_object_*` tests in `tests/integration.rs`.
- The check is only in `resolve`, not in `load_object_raw`. The `/Encrypt` dictionary (read by `detect_encryption` through the trailer reference) and object-stream containers (read at generation 0) do not go through it.
- The number and generation in a parsed object header (`N g obj`) are not compared with the xref: `load_object_raw` discards them.
- The `visited` set passed through `load_object_raw` is fresh per `resolve` call. `resolve` does not follow references inside the object it returns, so the set only stops a container chain that leads back to itself.
- **Font program cache** (#240): `font_program(stream_ref)` keeps decoded font-file streams for the document's lifetime, keyed by reference, in `RwLock<HashMap<IndirectRef, Arc<OnceLock<…>>>>`. The map lock is held only to find or insert the per-key `OnceLock`, and the decode runs inside it, so two threads asking for one font decode it once while other fonts proceed. Each entry is `Arc<FontProgramData>` (`data: Arc<[u8]>`, `hash` from `font_hash`). A failure is kept when its variant carries only data (`JustPdfError::rebuilt`) and returned again without another attempt; an `Io` error or a `CircularReference` is returned and the entry removed, so the next call retries. Pinned by `tests/font_program_cache.rs`.
- **Input bound:** the parsed-object cache is bounded by its entry count, not by object size. The object-stream cache and the font-program cache are never evicted; each entry's size is bounded only by the decoded size of its stream, which nothing bounds yet ([Stream filters](stream-filters.md), #161).

## Reference behaviour
- Generation mismatch: MuPDF `pdf-xref.c`, pdf.js `xref.js` and qpdf `QPDF_objects.cc` as summarised under Governing decisions (#98, 2026-09-29, read from their source).
- Header number mismatch: MuPDF compares the object number, not the generation; qpdf resolves an absent object to null (#109, 2026-10-07).

## Cross-cutting invariants
- [Source generation](../invariant/source-generation.md) — the read side: a reference whose generation disagrees with the xref resolves to `Null`, which is what makes a write defect visible.

## Blast radius
- [Xref](xref.md) — `defines` and the decryption key trust the xref entry's generation. A wrong or narrowed entry makes `resolve` return another object or `Null`.
- [Object model](object-model.md) — `parse_indirect_object` decides what a damaged object reads as, and `resolve` caches that.
- [Object streams](object-streams.md) — the container path skips `defines` and decrypts at generation 0; a change to either hook must keep the two sides in step.
- [Object decryption](object-decryption.md), [Password authentication](password-authentication.md) — the encryption hooks above. Moving a hook means checking both notes, or strings are decrypted twice or not at all.
- [Repair](repair.md) — builds a document with `from_raw_parts`, which skips encryption detection. A field added to `PdfDocument` must be initialised there too.
- [Document modifier](document-modifier.md) — copies every object through `resolve` after checking `is_encrypted` / `is_authenticated`. What `resolve` returns for an undefined or failing object is what the modifier writes or drops (#97).
- [Compress pipeline](compress-pipeline.md), [CLI](cli.md) — refuse or prompt on encrypted documents through `is_encrypted`, which is false for a repaired document.
- [Facade](facade.md), [Language bindings](language-bindings.md) — a signature change to `open`, `from_bytes`, `open_mmap` or `authenticate` reaches them.

## Known holes / open
- When the number in an object header differs from the xref (the offset points at another object), that object is returned anyway; the same goes for an object stream's index numbers. *Measured* 2026-10-07: an xref entry for object 4 holding object 3's offset makes `resolve(4 0 R)` return object 3's Page dictionary. Decided in #109: compare the header's object number (not its generation, as MuPDF does); on a mismatch or no header at the offset, look the object up in a header index of the whole file built lazily once (the scan in `repair.rs`, which `open` never calls today), and resolve to `Null` only when the file holds it nowhere (§7.3.10, #98, qpdf). Tracked: #109
- `resolve` calls from several threads are serialised, because a cache hit takes the write lock and scans the LRU order (inferred: a candidate bottleneck for parallel rendering, not measured).
- `is_plain_document_metadata` calls `resolve` on the catalog while loading an object. If the catalog itself were an XML metadata stream under `/EncryptMetadata false`, the two calls would recurse without end (inferred from the code, not reproduced).
- The `open_mmap` unit tests in `parser.rs` run only with the `mmap` feature; in CI only the all-features test job turns it on (`.github/workflows/ci.yml`, `justpdf-core/mmap`, #187). They create their file in a `tempfile::tempdir()` declared before the document, so on Windows the mapping is dropped before the directory is removed.
- The font-program and object-stream caches have no eviction; their memory waits on the decoded-size limit. Tracked: #161
