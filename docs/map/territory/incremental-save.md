# Incremental save

## What it is
A way of saving that leaves the original bytes untouched and appends the changed objects, a new xref and a trailer carrying `/Prev` to the end of the file. Signing needs the original bytes preserved, so it uses the same approach, but the signing side has its own implementation ([Signing](signing.md)).

## Governing decisions
**None.**

## Design model
- Appended objects are written with `serialize_object` (before #26 they went through Display, so streams broke into a debug format — the serialization part of #25).
- `incremental_save(doc, modifier)` writes only the changes (#25). It resolves the original `doc` again and compares it with the modifier's objects by value (`PdfObject: PartialEq`) and by **generation** (the source xref's `defined_generation` against the writer's `generation`), and appends only numbers where either differs or that the source did not have. Generation is compared because of an object the writer did not hold, put back at that number with the same value as the source (generation 0) — looking only at the value, it was not appended, so the file kept it at source generation g while the trailer pointed at it with writer generation 0, and it became `Null` (found and reproduced while implementing #110). Changes are not tracked through `set_object`/`add_object` calls — because the compress pipeline and others edit `writer().objects` directly (`test_incremental_save_appends_an_object_edited_in_place`).
- Deletion: of the objects `from_document` copied (`source_objects` — resolve succeeded, `/Encrypt` excluded), only those missing from the modifier are written to the new xref as `0000000000 65535 f`. Objects that failed to resolve and were not copied, and the `/Encrypt` object, are not freed — copying and the deletion check share the same `source_objects`.
  - Exception: an object stream (ObjStm) container that an **unchanged** object points at as `Compressed` in the source xref is not freed even if it is missing from the modifier. A container is not referenced as `N 0 R` and is reached only through xref entries, so `garbage_collect` deletes it. Freeing it would make the unchanged objects inside it fail to resolve (`test_incremental_save_keeps_object_streams_that_hold_unchanged_objects`). A container whose members have all changed or disappeared is freed. The source's xref stream object is also freed if GC drops it, which has no effect because the reader finds xref sections by byte offset.
  - **Maintainer decision (2026-09-24, during #25 implementation)**: the exception above. The earlier "copied and then gone" decision was made without seeing this case — lens and assay in the check step reproduced `object stream 8 is not a stream` after `set_info`/`delete_page` + `garbage_collect`. Alternatives offered: re-append the live members as plain objects (in a compressed document most objects are inside ObjStms, which defeats writing only the changes), or reject when combined with GC (MuPDF `pdf-write.c`'s "Can't do incremental writes with garbage collection").
  - The free entry is the "second method" of ISO 32000-1 §7.5.4 (generation 65535, points at 0, not linked into the list, not reusable). The default method (generation + 1, linked into the list — the Annex H.7.3 example rewrites even object 0 in the incremental section) would have to follow the source generation and the existing free list. MuPDF `pdf-write.c` also writes incremental deletion as 65535 (`FIXME: would be better to link to existing free list`). justpdf always hands out new numbers above the source's highest number, so being non-reusable costs nothing.
- With no changes and no deletions, it returns the original bytes as they are (without even appending a newline). MuPDF does the same early return (`pdf_has_unsaved_changes`).
- The comparison baseline is the source document at save time. The modifier holds no copy of the source — `from_document` is shared by every editing feature (compress, annotations, forms and so on), so holding a copy would double memory for callers that never use incremental save. Whether `doc` is the document the modifier was built from is not checked (PDFs without a file ID are common, so there is no reliable way to identify it).
  - **Maintainer decision (2026-09-24, #25 triage)**: the four points above (baseline = source document at save time, deletion scope = copied objects that are gone, 65535 free entries, no changes = original as is) and no mismatch check. Alternatives offered: for change detection, a modifier snapshot, an incremental-only constructor, dirty flags, or a hash snapshot; for deletion, not recording it or basing it on the whole source xref; for the free format, generation + 1 linking; for no changes, appending an empty section; for mismatch, rejecting by comparing catalog/`/ID`. Facts offered as grounds: compress's direct edits to `writer().objects`, `from_document` being shared, the texts of ISO 32000-1:2008 §7.5.4, §7.5.6 and Annex H.7, and of MuPDF `pdf-write.c` and `pdf-xref.c`. Not checked against the ISO 32000-2 text.
- The new trailer is built with `incremental_trailer` — it carries over the source trailer's keys ([Incremental trailer](../invariant/incremental-trailer.md)). `/Root` and `/Info` point at the generation the writer writes that object at (`reference_to`, #110).
- If the source is encrypted, appended objects are run through `encrypt_object` with the file key of `doc`'s `SecurityState` (the `/Encrypt` object is neither copied nor compared). The key comes from `doc` alone — `DocumentModifier` does not hold a `SecurityState` (#25, maintainer decision). A modifier cannot be built from an unauthenticated encrypted document (`from_document` in [Document modifier](document-modifier.md) rejects it). `incremental_save`'s own check looks at `doc`, so passing a `doc` that reopened the same bytes without authenticating is caught.
  - **Maintainer decision (2026-09-23, #26)**: incremental save supports encrypted input and signing rejects it. The alternatives "reject both" and "support both (add a password argument to signing)" were offered alongside.
- Appended objects are written with the generation `PdfWriter` holds (the source generation, 0 for new objects) in the header and xref entry, and the encryption key is derived from that generation (#72, [Document modifier](document-modifier.md)). Before #72 changed objects were appended as `N 0 obj`, so qpdf read the source's `N 1 R` as the old object in the earlier section — the edit was invisible (measured 2026-09-29). Free entries are written as 65535, so they do not depend on the source generation.
  - **Maintainer decision (2026-09-24, #25)**: do #25 before #72, independently. At first (triage round 1) it was "#72 first" — on the premise that free entries need source generation + 1. After the comparison baseline was set to `doc` at save time (`doc`'s xref knows the source generation), and after the 65535 free format was chosen, that premise was gone, so the question was asked again.

## Reference behaviour
MuPDF `pdf-write.c` (the `pdf_xref_is_incremental` filter in `dowriteobject`, `gen_list[num] = 65535` for incremental deletion, the no-changes early return). Clause to compare against: ISO 32000-2 §7.5.6 (the text check was done against ISO 32000-1:2008 §7.5.4 and §7.5.6).

## Blast radius
- [Xref](xref.md) — the side that reads the appended section.
- [Signing](signing.md) — a second implementation of the same approach. When fixing one, check whether the other has the same defect.
- [Object serialization](object-serialization.md) — the correct path is `serialize_object`.
- [Redaction](redaction.md) — incremental save by design leaves the original bytes (including the removed text) in place.
