# Incremental save

## What it is
A way of saving that leaves the original bytes untouched and appends the changed objects, a new xref table and a trailer carrying `/Prev` to the end of the file (inferred, `writer/modify.rs — incremental_save`). Signing needs the original bytes preserved too, so it appends the same way, but with its own implementation that shares only `incremental_trailer` ([Signing](signing.md)).

## Governing decisions
- [ADR 0004](../../adr/0004-redaction-never-under-erases.md) — "Incremental save of a document with applied redactions is refused: it appends to the original revision, which still holds what was erased." The code does not follow this rule at HEAD: `incremental_save` has no check for applied redactions (inferred). Tracked: #213
- The rest of the model was decided on issues (#25, #26), attributed below.

## Design model
- Appended objects are written with `serialize_object` (inferred). Before #26 they went through Display, so streams broke into a debug format (the serialization part of #25).
- **What is appended.** `incremental_save(doc, modifier)` writes only the changes (#25). It resolves the original `doc` again through `source_objects` and compares each object with the modifier's by value (`PdfObject: PartialEq`) and by **generation** (the source xref's `defined_generation` against the writer's `generation`) (inferred). It appends every number where either differs or that the source did not have. Generation is compared because of an object the writer did not hold, put back at that number with the same value as the source (generation 0): compared by value alone it was not appended, so the file kept it at source generation g while the trailer pointed at it at writer generation 0, and it became `Null` (found and reproduced while implementing #110). Changes are not tracked through `set_object`/`add_object` calls, because the compress pipeline and others edit `writer().objects` directly (inferred; `test_incremental_save_appends_an_object_edited_in_place`).
- **Deletion.** Of the objects `from_document` copied (`source_objects`: resolve succeeded, `/Encrypt` excluded), those missing from the modifier are written to the new xref as `0000000000 65535 f` (inferred). Objects that failed to resolve, and the `/Encrypt` object, were never copied and are not freed, because copying and the deletion check share `source_objects` (inferred; `test_incremental_save_keeps_an_object_that_does_not_resolve`).
  - Exception: an object stream container that an **unchanged** object points at as `Compressed` in the source xref is not freed, even when it is missing from the modifier (inferred, `live_object_streams`). A container is not referenced as `N 0 R` and is reached only through xref entries, so `garbage_collect` deletes it. Freeing it would make the unchanged objects inside it fail to resolve (`test_incremental_save_keeps_object_streams_that_hold_unchanged_objects`). A container whose members have all changed or disappeared is freed. The source's xref stream object is also freed if GC drops it, which has no effect, because the reader finds xref sections by byte offset (inferred).
  - **Maintainer decision (2026-09-24, during #25 implementation)**: the exception above. The earlier "copied and then gone" decision was made without seeing this case; lens and assay in the check step reproduced `object stream 8 is not a stream` after `set_info`/`delete_page` + `garbage_collect` (#25). Alternatives offered: re-append the live members as plain objects (in a compressed document most objects are inside object streams, which defeats writing only the changes), or reject when combined with GC (MuPDF `pdf-write.c`'s "Can't do incremental writes with garbage collection").
  - The free entry is the "second method" of ISO 32000-1 §7.5.4: generation 65535, pointing at 0, not linked into the free list, not reusable. The default method (generation + 1, linked into the list; the Annex H.7.3 example rewrites even object 0 in the incremental section) would have to follow the source generation and the existing free list. MuPDF `pdf-write.c` also writes incremental deletion as 65535 (`FIXME: would be better to link to existing free list`) (#25). justpdf always hands out new numbers above the source's highest number, so being non-reusable costs nothing (inferred, `from_document`).
- With no changes and no deletions, it returns the original bytes as they are, without even appending a newline (inferred; `test_incremental_save_without_changes_returns_the_original`). MuPDF returns early the same way (`pdf_has_unsaved_changes`, #25).
- **Baseline.** The comparison baseline is the source document at save time. The modifier holds no copy of the source: `from_document` is shared by every editing feature (compress, annotations, forms and so on), so a copy would double memory for callers that never use incremental save (#25). Whether `doc` is the document the modifier was built from is not checked (inferred); PDFs without a file ID are common, so there is no reliable way to identify it (#25).
  - **Maintainer decision (2026-09-24, #25 triage)**: the four points above (baseline = source document at save time, deletion scope = copied objects that are gone, 65535 free entries, no changes = original as is) and no mismatch check. Alternatives offered: for change detection, a modifier snapshot, an incremental-only constructor, dirty flags or a hash snapshot; for deletion, not recording it or basing it on the whole source xref; for the free format, generation + 1 linking; for no changes, appending an empty section; for a mismatch, rejecting by comparing the catalog or `/ID`. Facts offered as grounds: compress's direct edits to `writer().objects`, `from_document` being shared, the texts of ISO 32000-1:2008 §7.5.4, §7.5.6 and Annex H.7, and MuPDF `pdf-write.c` and `pdf-xref.c`. Not checked against the ISO 32000-2 text.
- **Trailer.** The new trailer is built with `incremental_trailer`, which carries over the source trailer's keys ([Incremental trailer](../invariant/incremental-trailer.md)). `/Root` and `/Info` point at the generation the writer writes that object at (`reference_to`, #110) (inferred). `/ID` is carried over unchanged, both elements (inferred).
- **Encrypted sources.** If the source is encrypted, appended objects go through `encrypt_object_for_writing` with the file key of `doc`'s `SecurityState`; the `/Encrypt` object is neither copied nor compared (inferred). The key comes from `doc` alone: `DocumentModifier` holds no key for this (#25, maintainer decision). A modifier cannot be built from an unauthenticated encrypted document (`from_document` in [Document modifier](document-modifier.md) rejects it). `incremental_save` checks `doc` itself, so a `doc` that reopened the same bytes without authenticating returns `EncryptionError` (inferred). The catalog `/Metadata` under `/EncryptMetadata false` is found with `document_metadata_num` and written plain behind an Identity filter, as in a full write (inferred; `test_incremental_save_keeps_changed_document_metadata_plain`).
  - **Maintainer decision (2026-09-23, #26)**: incremental save supports encrypted input and signing rejects it. The alternatives "reject both" and "support both (add a password argument to signing)" were offered alongside.
- `set_encryption` on the modifier is refused with `UnsupportedEncryption`; `preserve_encryption` is accepted, since the save follows the source's encryption anyway (inferred; [Document modifier](document-modifier.md)).
- **Generations.** Appended objects are written with the generation `PdfWriter` holds (the source generation, 0 for new objects) in the header and xref entry, and the encryption key is derived from that generation (inferred; #72, [Document modifier](document-modifier.md)). Before #72, changed objects were appended as `N 0 obj`, so qpdf read the source's `N 1 R` as the old object in the earlier section and the edit was invisible (measured 2026-09-29, #72). Free entries are written as 65535, so they do not depend on the source generation.
  - **Maintainer decision (2026-09-24, #25)**: do #25 before #72, independently. At first (triage round 1) it was "#72 first", on the premise that free entries need source generation + 1. Once the baseline was set to `doc` at save time (`doc`'s xref knows the source generation) and the 65535 free format was chosen, that premise was gone, so the question was asked again.
- The appended section is always a classic xref table, also after a source whose last section is an xref stream (inferred; `test_incremental_save_after_xref_stream_section`). Each entry gets its own one-line subsection (`N 1`) (inferred).
- **Input size**: bounded by the source document and the modifier. The whole original is copied into the output buffer, and every source object is resolved again for the comparison (inferred).

## Blast radius
- [Xref](xref.md) — reads the appended section. It assumes the newest trailer restates every document-level key and that a 65535 free entry hides the earlier object.
- [Signing](signing.md) — a second implementation of the same approach, sharing only `incremental_trailer`. Both assume the original bytes and trailer keys are carried; when fixing one, check whether the other has the same defect.
- [Document modifier](document-modifier.md) — shares `source_objects` as the definition of what was copied, and the guarantee that new numbers never reuse a source number (the 65535 free format depends on it).
- [Object encryption](object-encryption.md) — appended objects are encrypted with the source key at the writer's generation; a change in how either side derives the object key breaks the appended section.
- [Redaction](redaction.md) — an incremental save leaves the original bytes, including erased content, in place. ADR 0004 requires refusing it after redactions (Known holes).
- [Compress pipeline](compress-pipeline.md) — edits `writer().objects` directly; change detection by value comparison exists because of it.

## Known holes / open
- There are no callers in product code: no CLI command or binding calls `incremental_save` (inferred, `grep -rl incremental_save justpdf justpdf-cli justpdf-ffi justpdf-python justpdf-node justpdf-wasm justpdf-compress-wasm` finds nothing outside `target/`).
- `incremental_save` does not refuse a modifier that applied redactions, against ADR 0004 (inferred). Tracked: #213
- `/ID` is carried over unchanged. The maintainer decided on 2026-10-10 that an incremental save keeps the first element and replaces the second, and adds an `/ID` when the previous trailer has none (#77). Tracked: #77
