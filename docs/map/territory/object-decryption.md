# Object decryption

## What it is
When an object is loaded from an authenticated document, decrypts its strings and stream data with the per-object key (inferred, `crypto/decrypt.rs — decrypt_object`). Handles a stream's own `/Crypt` filter and its `DecodeParms /Name`, the catalog `/Metadata` exception, and the cross-reference stream exception.

## Governing decisions
**None.** No ADR covers decryption. The rules below follow ISO 32000-1 clauses checked against the spec text, cited where they apply.

## Design model
- **Hooks.** Decryption runs in `load_object` (ordinary objects) and in `load_compressed_object` (the whole object stream) of [Document access](document-access.md) (inferred, `parser.rs`). `load_object_raw` loads without decryption; the `/Encrypt` dictionary is read through it, and `decrypt_object` also skips the object whose number is `encrypt_obj_num` (inferred).
- **Objects inside an object stream are decrypted once, together with the stream.** `load_compressed_object` decrypts the whole stream under the stream's number at generation 0, and `load_object` returns objects from xref type 2 entries without decrypting them again (inferred). ISO 32000-1 §7.5.7: "strings occurring anywhere in an object stream shall not be separately encrypted". MuPDF `pdf_cache_object` also calls `pdf_crypt_obj` only for type `n` entries.
- **Stream dictionary strings** are decrypted with the string method, separately from the stream data's method (the `/Crypt` filter, Identity included) (inferred, `decrypt_strings_or_keep`). MuPDF `pdf_crypt_obj` also uses `strf` for dictionary strings. A stream dictionary string that does not decrypt (an AES length or padding error) is kept as written, so that one string does not stop a whole content, font or image stream from opening; MuPDF also only warns and keeps the original string. A string of an ordinary object that does not decrypt makes the load fail (inferred, the `PdfObject::String` arm of `decrypt_object`). The exceptions in ISO 32000-1 §7.6.1 (checked against the spec text, 2026-09-24) are only the trailer `/ID`, strings in the `/Encrypt` dictionary, and strings **inside** a stream.
- **Cross-reference streams** (`/Type /XRef`) are decrypted in neither data nor dictionary (inferred, `is_xref_stream`). ISO 32000-1 §7.5.8.2: "The cross-reference stream shall not be encrypted and strings appearing in the cross-reference stream dictionary shall not be encrypted". That dictionary holds `/ID`.
- **Per-stream crypt filters.** If a stream's `/Filter` names `/Crypt`, the `/Name` in its `DecodeParms` picks the method (`stream_crypt_method`, `extract_crypt_filter_name`); with no `/Name` it is Identity and the data is not decrypted (inferred). ISO 32000-1 Table 14: "Default value: Identity". MuPDF also applies no default method to a stream with `/Crypt` and leaves the data as is when there is no `/Name` (`pdf-stream.c`), and qpdf `interpretCF` also treats a missing name as Identity. If the `/Name` is neither in `/CF` nor Identity, it decrypts with the document's default stream method; qpdf does the same (`e_unknown` → `/StmF`).
- **The catalog `/Metadata` stream.** With `/EncryptMetadata false` (`/V` 4 and 5), if that stream is `/Type /Metadata /Subtype /XML` and has no `/Crypt` filter of its own, only its dictionary strings are decrypted and its data is kept (inferred, `is_plain_document_metadata`, `metadata_stream_left_plain`, `decrypt_stream_dict`). Other XML metadata streams (pages and so on) are decrypted. ISO 32000-1 Table 21 (standard security handler) and Table 27 say the flag is about the "document-level metadata stream" (checked against the spec text, 2026-09-27), and qpdf applies this exception only to the root metadata (`QPDF_encryption.cc`, `isRootMetadata`). MuPDF's reading side has no such exception: across its whole source, `encrypt_metadata` is used only in key derivation and writing (2026-09-27), so MuPDF decrypts, and so corrupts, the XMP of a file qpdf wrote with `metadata=False`.
- **No crypt filter remains on a decrypted object.** A stream whose `/Crypt` filter is Identity also has `/Crypt` removed from `/Filter` (and its `DecodeParms` entry) after loading (inferred, `remove_crypt_filter`). If it stayed, re-encrypting and writing would put an Identity marker on top of ciphertext.
- Before commit 2d3dc30 (2026-09-24), justpdf wrote stream dictionary strings as plaintext. Reading an encrypted file written that way now reads those strings (for example `/ModDate` and `/CheckSum` in an embedded file's `/Params`) as garbage; qpdf reads them the same way.
- A signature's `/Contents` is decrypted on its way through `resolve` like any string (inferred, `decrypt_object` has no exception for it) — [Signature detection](signature-detection.md).
- **Input size**: decryption handles whatever the object loader parsed. `decrypt_object` recurses once per array or dictionary level, and nothing here bounds the depth; each string or stream is decrypted into a new buffer of its own size (inferred).

## Blast radius
- [Object streams](object-streams.md) — decrypting the object stream is the only decryption the objects inside it get; both sides assume type 2 objects are never decrypted again.
- [Object encryption](object-encryption.md) — the writing-side counterpart. Both must agree on which values are encrypted (stream dictionary strings, the xref stream, the catalog metadata, the `/Encrypt` dictionary by number), or justpdf's own files stop reading back.
- [Encryption model](encryption-model.md) — supplies the string and stream methods and `/EncryptMetadata`.
- [Key derivation](key-derivation.md) — per-object keys depend on the number and generation passed here.
- [Signature detection](signature-detection.md), [Signature verification](signature-verification.md) — read `/Contents` after it went through decryption.
- [Document modifier](document-modifier.md) — copies decrypted objects; with `/Crypt` removed on read, a rewrite cannot tell which streams the source left plain.

## Known holes / open
- No test checks dictionary strings in a file whose `/StrF` and `/StmF` differ (for example an Identity stream filter): changing dictionary strings to decrypt with the stream method would still pass every current test (inferred).
- Whether strings of **non-stream** objects in ordinary (type 1) entries are decrypted is checked only by round-trip tests on files justpdf wrote (the encryption tests in `writer::modify`). The third-party fixtures have no such object: in object stream mode everything is type 2, and otherwise their strings sit only in stream dictionaries (inferred).
- `decrypt_object` has no exception for a signature dictionary's `/Contents`, so in an encrypted signed file the signature bytes would be "decrypted" into garbage before [Signature detection](signature-detection.md) reads them (inferred, reported by the 2026-10-30 rewrite). Whether ISO 32000-2 §7.6.1 exempts it has not been checked against the spec text.
