# Object decryption

## What it is
When an object is loaded from an authenticated document, decrypts its strings and stream data with the per-object key. Handles per-stream `/Crypt` filters and `DecodeParms /Name`.

## Governing decisions
**None.**

## Design model
- The hooks sit in `load_object` (ordinary objects) and `load_compressed_object` (the whole ObjStm) of [Document access](document-access.md).
- **Objects inside an ObjStm are decrypted once, together with the ObjStm.** `load_compressed_object` decrypts the whole stream under the stream's number, and `load_object` does not apply per-object decryption to objects that come from xref type 2 entries — ISO 32000-1 §7.5.7 "strings occurring anywhere in an object stream shall not be separately encrypted". MuPDF `pdf_cache_object` also calls `pdf_crypt_obj` only for type `n` entries.
- Strings inside a stream dict are decrypted with the string method — separately from the method for the stream data (the `/Crypt` filter, including Identity) (MuPDF `pdf_crypt_obj` also uses `strf` for dict strings). A string that does not decrypt (AES length or padding error) is kept as written (`decrypt_strings_or_keep`) — so that one dict string does not stop a whole content, font or image stream from opening; MuPDF also only warns and keeps the original string. The exceptions in ISO 32000-1 §7.6.1 (checked against the spec text) are only the trailer `/ID`, strings in the `/Encrypt` dict, and strings **inside** a stream.
- `/Type /XRef` streams are decrypted in neither data nor dict (`is_xref_stream`) — §7.5.8.2 "The cross-reference stream shall not be encrypted and strings appearing in the cross-reference stream dictionary shall not be encrypted". That dict contains `/ID`.
- If a stream's `/Filter` has `/Crypt`, the `/Name` in its `DecodeParms` picks the method (`stream_crypt_method`), and with no `/Name` it is Identity (not decrypted) — ISO 32000-1 Table 14 "Default value: Identity". MuPDF also applies no default method to a stream with `/Crypt` and leaves the data as is when there is no `/Name` (`pdf-stream.c`), and qpdf `interpretCF` also treats a missing name as Identity. If the `/Name` is neither in `/CF` nor Identity, it decrypts with the document's default stream method — qpdf does the same (`e_unknown` → `/StmF`).
- **The catalog `/Metadata` stream**: with `/EncryptMetadata false` (V 4 and 5), if that stream is `/Type /Metadata /Subtype /XML` and has no `/Crypt` filter of its own, its data is not decrypted and only its dict strings are (`is_plain_document_metadata`, `metadata_stream_left_plain`, `decrypt_stream_dict`). Other XML metadata streams (pages and so on) are decrypted. ISO 32000-1 Table 21 (standard security handler) and Table 27 say the flag is about the "document-level metadata stream" (checked against the spec text, 2026-09-27), and qpdf applies this exception only to the root metadata (`QPDF_encryption.cc`, `isRootMetadata`). MuPDF's reading side has no such exception (across the whole source `encrypt_metadata` is used only in key derivation and writing, 2026-09-27) — MuPDF decrypts, and so corrupts, the XMP of a file qpdf wrote with `metadata=False`.
- A stream whose `/Crypt` filter is Identity also has `/Crypt` removed from `/Filter` after decryption — no crypt filter remains on a decrypted object. If it stayed, re-encrypting and writing would put an Identity marker on top of ciphertext.
- Before this rule, justpdf wrote stream dict strings as plaintext. Reading an encrypted file written that way now reads those strings (for example `/ModDate` and `/CheckSum` in an embedded file's `/Params`) as garbage — qpdf reads them the same way.
- A signature's `/Contents` is not encrypted per the spec, but it is decrypted on its way through `resolve` (inferred) — [Signature detection](signature-detection.md).

## Reference behaviour
Checked against the ISO 32000-1:2008 text (Adobe's free copy, 2026-09-24): the encryption exception list in §7.6.1 (trailer `/ID`, strings in the `/Encrypt` dict, strings inside a stream) and the xref stream rule in §7.5.8.2 — stream dict string handling and xref stream handling follow them. Stream dict string decryption is confirmed with R3, R4 and R6 files made by qpdf 12.3.2 (the fixtures under Known holes). Checked against the object stream rule in ISO 32000-1 §7.5.7 (spec text, 2026-09-27) and MuPDF `pdf_cache_object` (`source/pdf/pdf-xref.c`, master source, 2026-09-27) — decrypting objects inside an ObjStm once follows them, confirmed with R3, R4 and R6 files made by qpdf 12.4.1 (the fixtures under Known holes). Checked against ISO 32000-1 Table 14 (the default of the `/Crypt` filter's `/Name` is Identity, spec text 2026-09-27), MuPDF `source/pdf/pdf-stream.c` and qpdf `libqpdf/QPDF_encryption.cc` (each master/main source, 2026-09-27) — handling of `/Crypt` without `/Name` follows them. Clauses not yet checked: the same rule in ISO 32000-2 (§7.5.7), §7.6.2.

## Cross-cutting invariants
**None.**

## Blast radius
- [Object streams](object-streams.md) — decrypting the ObjStm stream is the only decryption the objects inside it get.
- [Object encryption](object-encryption.md) — the writing-side counterpart. The two must share the rule for which values are encrypted.
- [Encryption model](encryption-model.md) — cipher choice.
- [Signature detection](signature-detection.md), [Signature verification](signature-verification.md) — `/Contents`.

## Known holes / open
- **Stream dict string fixtures** (`justpdf-core/tests/fixtures/`): R3 (RC4-128), R4 (AES-128) and R6 (AES-256) files made with qpdf 12.3.2 (pikepdf 10.13.0). User `user`, owner `owner`. The catalog's `/Probe` is a stream with `/Note (hello-note)` in its dict (data `stream body`), and the plaintext `hello-note` is not in the file bytes. A judge independent of our code.
  - `stream_dict_string_r3.pdf` (sha256 `18fd03e9d81951eb9e0e8e91790c1b3cb81537ab489c833949e88e462b413e4a`), `stream_dict_string_r4.pdf` (`8b6205dac67f48caabc4dc339a9305747f96f1e9769e0259a0fe36696b4abacc`), `stream_dict_string_r6.pdf` (`0d6b1cd4b230bb1276da294b5ebf51374ba7f5ffffa43dd7befd35449fce9e74`)
  - To regenerate: `pdf = pikepdf.new(); pdf.add_blank_page(); st = pikepdf.Stream(pdf, b"stream body"); st.Note = pikepdf.String("hello-note"); pdf.Root.Probe = pdf.make_indirect(st); pdf.save(path, encryption=pikepdf.Encryption(user="user", owner="owner", R=R, aes=R>=4, metadata=R>=4), object_stream_mode=pikepdf.ObjectStreamMode.disable)`. Keys and IVs are random, so the bytes differ every time.
- **Metadata fixtures** (`justpdf-core/tests/fixtures/`): files made with qpdf 12.4.1 (pikepdf 10.14.0). User `user`, owner `owner`. The catalog `/Metadata` is XMP whose `dc:title` is `hello-xmp`; `/Probe` is another `/Type /Metadata /Subtype /XML` stream holding `probe body`.
  - `metadata_plain_r4.pdf` (AES-128, `/EncryptMetadata false`; sha256 `2ec90e73a8dc4df5c3b8bc7d7839a8ae3a5ba5bd9e1b6b2d481eae535ca7458d`), `metadata_plain_r6.pdf` (AES-256, false; `e027a3183d2d6250c250e89cf60aae921e13d0d404f37115fddf36f1732d585d`), `metadata_encrypted_r4.pdf` (AES-128, no flag; `73c6fe3f5d3240c1011e52c28c103f8e227a0b62cbe1ee9381c2b8f782e50777`). In the first two, the plaintext `hello-xmp` is in the file bytes and `probe body` is not.
  - To regenerate: `pdf = pikepdf.new(); pdf.add_blank_page(); with pdf.open_metadata(set_pikepdf_as_editor=False) as m: m["dc:title"] = "hello-xmp"`; `/Probe` as an indirect object from `pikepdf.Stream(pdf, b"probe body")` with `Type` and `Subtype` set; `pdf.save(path, encryption=pikepdf.Encryption(user="user", owner="owner", R=R, aes=True, metadata=M), object_stream_mode=pikepdf.ObjectStreamMode.disable, compress_streams=False)`.
- No test checks dict strings in a file whose `/StrF` and `/StmF` differ (for example an Identity stream filter) — changing dict strings to decrypt with the stream method would still pass every current test.
- **Object stream string fixtures** (`justpdf-core/tests/fixtures/`): R3 (RC4-128), R4 (AES-128) and R6 (AES-256) files made with qpdf 12.4.1 (pikepdf 10.14.0). User `user`, owner `owner`. The catalog's `/Probe` dict (`/Note (hello-objstm)`) and `/Info` (`/Title (hello-title)`) are inside an object stream (the test asserts they are type 2 entries), and neither plaintext is in the file bytes.

Keys and IVs are random, so the bytes differ every time.
