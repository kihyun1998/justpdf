# Facade (the `justpdf` crate)

## What it is
The user-facing API over `justpdf-core` and `justpdf-render`: `Document` (open, authenticate, pages, metadata, text, search, outlines, page labels, annotations, forms, attachments, signature detection, render), `Page`, `Modifier`, `merge`, plus re-exports of both crates (`justpdf::core`, `justpdf::render`) and of the builder/writer types. It is the entry point consumed from crates.io under the name `justpdf` (published, 0.1.2 on crates.io, measured 2026-10-30).

## Governing decisions
- [ADR-0001](../../adr/0001-crates-split-by-dependency-layer.md) — this crate integrates only core + render and **deliberately excludes** formats/special. `justpdf/Cargo.toml` depends on `justpdf-core`, `justpdf-render` and optional `tokio` only (inferred, read 2026-10-30).
- [ADR-0006](../../adr/0006-breaking-changes-are-allowed-before-1-0.md) — before 1.0 a design fix may break this crate's public API, recorded under Changed. The facade re-exports `justpdf_render` as `justpdf::render`, so a break in a render `pub mod` is a break here too.

## Design model
Status: only from reading the source; no record decides the facade's shape beyond ADR-0001.
- No crate in the repository depends on `justpdf`: no manifest under the repo lists it as a dependency (`grep -n 'justpdf = \|^justpdf ' */Cargo.toml` hits only package and binary names; inferred). The four bindings and the CLI call core/render directly. ADR-0006 records that crates.io had no reverse dependency on `justpdf` either (measured there, 2026-10-24).
- There is no `Metadata` type — metadata is string getters (`title` … `modification_date`) and `metadata() -> Vec<(String, String)>`, all through `Document::metadata_string`. It decodes a UTF-16BE string with a BOM and reads anything else byte-by-byte as Latin-1, which is not PDFDocEncoding (they differ in 0x80–0x9F); the bindings and the CLI decode the same `/Info` values differently (lossy UTF-8) — see [Text string encoding](../invariant/text-string-encoding.md) (inferred).
- `Document` collects all pages at construction (`collect_pages` into `Document::pages`) and answers `page_count`, `page`, `pages`, `annotations` and `text` from that list. `Page` carries a cloned `PageInfo`. `Page::render_png`, `render_jpeg` and `render` pass the cached `PageInfo` (`render_page_info`); `Page::render_svg` and `render_raw` pass only the index (`render_page_to_svg`, `render_page_to_pixmap`), so render collects the page again (inferred, read 2026-10-30).
- `open`, `from_bytes` and `open_mmap` collect pages during construction, so on an encrypted file with a user password they fail with `Core(EncryptedDocument)`. Such files are opened with the `*_with_password` constructors, which call core `authenticate` before collecting pages (`Document::authenticated`). Core `PdfDocument::authenticate` returns `Ok(())` without checking the password when the document is already authenticated — true for a file whose user password is empty, so such a file opens with any password. The facade's own `Document::authenticate` (re-collects pages afterwards) is therefore reached only on files that opened, i.e. files with an empty user password (inferred from `parser.rs — PdfDocument::authenticate`). Adding password constructors instead of lazy page collection is the maintainer's choice: lazy collection changes meaning, `page_count()` would be 0 before authentication (#99, 2026-09-28).
- `Document::modify` passes `&self.inner` to `DocumentModifier::from_document`, so the authentication state carries over. Saving an encrypted document through `modify()` writes a file without `/Encrypt` by default (measured 2026-09-28 on `aes256_r5_empty_user.pdf`, #102). `Modifier::preserve_encryption` writes with the source's encryption (keep-source in [Document modifier](document-modifier.md)); a new password is set through `Modifier::inner_mut` and `DocumentModifier::set_encryption` (#102; the doc comment on `Document::modify` says the same).
- Feature flags (`justpdf/Cargo.toml`): `mmap` → `justpdf-core/mmap` (gates `open_mmap`, `open_mmap_with_password`); `parallel` → `justpdf-render/parallel` (gates `render_all_png`, `render_all_parallel`); `async` → `tokio` (gates `open_async`, which reads the file with `tokio::fs::read` and parses synchronously, and `render_to_file_async`, which renders synchronously and writes asynchronously). `arena` is passed through to core; the facade gates nothing on it (inferred).
- `Error::PageOutOfRange { index, count }` has the same name, fields and message as core `JustPdfError::PageOutOfRange` (`justpdf/src/error.rs`, `justpdf-core/src/error.rs`, read 2026-10-30). The facade checks an index against its own collected pages (`Document::page`, `Document::annotations`), so it never meets the core variant there (inferred). Keeping both is the maintainer's judgement (#134, 2026-09-30): shown that the two are one concept with no behavioural difference and that folding the facade's into `Core(..)` changes the facade's public API; chosen: keep both.
- Outside input: a path or a byte vector from the caller. The facade adds no size or count bound of its own; what core's parser and page-tree walk enforce applies ([Document access](document-access.md), [Page tree](page-tree.md)). `merge` and `merge_bytes` take any number of documents and hold all of them in memory (`merge_bytes` clones each input) (inferred).

**None.**

## Cross-cutting invariants
- [Text string encoding](../invariant/text-string-encoding.md) — `Document::metadata_string` decodes `/Info` text strings (UTF-16BE or Latin-1, not PDFDocEncoding).

## Blast radius
- [Document access](document-access.md), [Page tree](page-tree.md) — the facade fixes the page list at construction; a change to what `collect_pages` or `authenticate` returns changes which files `Document::open` accepts and what `page_count` reports.
- [Text extraction](text-extraction.md), [Text search](text-search.md), [Render API](render-api.md), [Document modifier](document-modifier.md) — the facade returns their types and errors directly (`Error::Core`, `Error::Render`, re-exported `RenderOptions`, `DocumentModifier`); a signature or error-kind change there is a facade API change (ADR-0006: a Changed entry).
- [Outlines](outlines.md), [Annotations](annotations.md), [AcroForm](acroform.md), [Embedded files](embedded-files.md), [Signature detection](signature-detection.md), [Page labels](page-labels.md), [Linearization](linearization.md) — their core types are returned unwrapped, so a change to those types is visible to facade users.
- [Crate layering](crate-layering.md) — the facade must not depend on formats/special; adding a dependency here breaks ADR-0001's promise.
- [Published docs](published-docs.md) — the Rust examples in the README and mdBook call this API and nothing compiles them; a renamed method leaves them wrong with CI green.
- [Language bindings](language-bindings.md) — the bindings read the same `/Info` strings and page sizes on their own; a change to how the facade decodes or measures does not reach them.

## Known holes / open
- No test exercises the `mmap`, `parallel` or `async` code: the crate's tests are the `#[cfg(test)]` module in `lib.rs`, none behind a feature. The CI all-features run only compiles the facade with all three (`justpdf/mmap` since #187).
- `Page::rotation` returns the raw `/Rotate` (`PageInfo::rotate`, not normalised in `page/mod.rs`), while its doc comment says "(0, 90, 180, 270)" and the renderer normalises with `normalize_rotation` (inferred). The #263 decision normalises Python's `rotation` and adds normalised accessors to the bindings; whether the facade's `rotation` follows is not in that decision (open question for the maintainer).
- Constructing a `Document` runs `collect_pages`, which copies an inherited direct `/Resources` into every `PageInfo`: quadratic in file size. Tracked: #351
- On a shared-node page tree `Document::open` fails with `LimitExceeded` (it uses `collect_pages`) while the bindings' `get_page` finds the page on the same file. Tracked: #133
- `metadata_string` decodes non-UTF-16 strings as Latin-1, not PDFDocEncoding. Tracked: #33
