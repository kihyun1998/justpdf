# Glyph rendering

## What it is
Turns the character codes of text-showing operators into glyph IDs, takes outlines from the embedded font and draws them, and caches the outlines.

## Governing decisions
**None.**

## Design model
- Font data is looked up in the order FontFile2 → FontFile3 → FontFile and parsed as a `GlyphSource`: an sfnt (`ttf_parser::Face`), else a bare CFF (`ttf_parser::cff::Table`, #224), else a Type1 program (`hayro_font::type1::Table`, #225). A simple font whose program is none of these is drawn from its substitute, like a font with no program (#227); a Type0 or Type3 font draws a **placeholder box**. Core's [CFF parser](cff.md) is not used. `GlyphSource` takes font bytes plus an encoding, not a `/FontFile3`, so #227's bundled substitutes can go through it.
- A bare CFF simple font (`/Type1C`) picks its glyph by name: `font::encoding_glyph_name` — the `/Differences` name, else the base encoding the PDF names (an encoding name or `/BaseEncoding`) — then `glyph_index_by_name`; with neither, the font's built-in encoding (`cff::Table::glyph_index`, which itself falls back to StandardEncoding), because ISO 32000-2 §9.6.5.1 makes the built-in encoding the implicit base of an embedded font program (derived; `FontInfo::encoding` defaults to Standard there, so the renderer keeps the explicit base separately). A name the font lacks draws nothing. A CID-keyed CFF (`/CIDFontType0C`) maps CID → GID through a reverse of `glyph_cid`, built once when the font is resolved; a CID the charset lacks draws nothing. Outlines are scaled by the CFF `FontMatrix` (`GlyphSource::font_matrix`; an sfnt's is `1/unitsPerEm`). Until #224 every glyph of a bare CFF was a box: `H` at 100 pt filled its counters (measured 2026-10-07, URW NimbusSans `/Type1C`); measured since in `tests/render_cff.rs`. On `interest_free_loans_brochure.pdf` page 1 its two `/Type1C` fonts drew thin boxes; they now draw nothing (504 pixels changed, measured).
- A Type1 program (`/FontFile`: cleartext + eexec, as a PDF holds it, or PFB) goes through the `hayro-font` crate — maintainer's call in #225 (2026-10-07), chosen over writing a Type1 module (hayro-font's Type1 part is 1,725 lines) and over converting Type1 to CFF as pdf.js does (that needs the same parsing plus charstring translation). `hayro-font` 0.4 (Apache-2.0 OR MIT, `forbid(unsafe_code)`, runtime deps `log` and `phf`) is a dependency of `justpdf-render` only. Glyph choice is the bare-CFF rule (`encoding_glyph_name`, else the font's built-in encoding through `code_to_string`); Type1 glyphs are addressed by name, so `GlyphSource` hands out a `GlyphRef` (an ID for sfnt/CFF, a name for Type1) and a name's glyph-cache key is the program hash XOR the name's `font_hash`, with glyph ID `u16::MAX` (`GlyphRef::cache_key`). Outlines are scaled by the Type1 `FontMatrix`. Until #225 every Type1 glyph was a box (measured in `tests/render_type1.rs` on AMS `cmr10`, and on an arXiv pdfTeX paper, page 3: from rows of boxes to drawn text).
- A simple font with no embedded program it can read (no `/FontFile*`, one that does not decode, or one `GlyphSource::parse` rejects — MuPDF also falls back to a substitute when loading the embedded font fails) is drawn from a bundled URW base-14 substitute (#227): `font::recovery::find_substitute(BaseFont)` names a Standard 14 font, and `substitute::base14_program` gives its bare CFF — Helvetica → NimbusSans, Times → NimbusRoman, Courier → NimbusMonoPS (each in four styles), Symbol → StandardSymbolsPS, ZapfDingbats → Dingbats. It then goes through `GlyphSource` like an embedded bare CFF, with the PDF's explicit base and `/Differences`; with no explicit base the substitute's built-in encoding applies, which is StandardEncoding for the text faces (inferred: §9.6.5's implicit base for a non-embedded non-symbolic font) and the font's own for Symbol and Dingbats (`0x61` is `alpha` / `a60`, measured 2026-10-08 with `cff::Table::glyph_index`). Glyphs advance by `/Widths` (or the Standard 14 tables), never the substitute's own advance; the outline is not scaled to the width. A Type0 or Type3 font is never substituted: a CID is not a glyph name, and Type3 glyphs come from `/CharProcs` (#226). The fourteen files are vendored unmodified from MuPDF `resources/fonts/urw/` at `25695609` (`justpdf-render/fonts/urw/`, SIL OFL 1.1, `OFL.txt` beside them, 608,233 bytes) and compiled in with `include_bytes!` behind the default-on `base14-fonts` feature; without it a non-embedded font draws boxes as before. MuPDF made the text faces with `tx -cff` subset to MES-2 (`tocff.sh`), so glyph names outside it (`uni0410`; Cyrillic is there as `afii10017`) draw nothing (measured). Feature name and directory are the maintainer's call in #227 (2026-10-08), chosen over `urw-fonts` under `resources/fonts/urw/`. `FontProgram::data` is a `Cow<'static, [u8]>` so a substitute is borrowed, not copied, per text operator; its glyph-cache key is the program hash, so every PDF font using one substitute shares entries.
- `ttf_parser::cff::Table::matrix` is the Top DICT `FontMatrix` only; an FDArray font dictionary's `FontMatrix` in a CID-keyed CFF is not applied (read from ttf-parser 0.25.1). A font that puts its scale there instead of in the Top DICT draws at the wrong size (inferred; no such fixture).
- Code → GID for a simple font: the first of `font::truetype_glyph_candidates(face, code, encoding, differences, symbolic)` returns a simple TrueType code's candidate GIDs, most preferred first: the §9.6.6.4 choice pdf.js makes (`src/core/fonts.js`, read raw 2026-10-07) — one cmap subtable (non-symbolic: (3,1), else (1,0); symbolic: (3,0), else (1,0); a (0,x) Unicode table is a candidate too); for a non-symbolic font with an `/Encoding` and a (3,1) or (1,0) table, the code's glyph name (`/Differences`, else a MacRoman/WinAnsi base, else Standard) read as Unicode through the AGL or as its MacRoman code; for (3,0), the code in `0xF0xx`; otherwise the code itself; then `post` by name (`/Differences` or a MacRoman/WinAnsi base name; forced first for a (0,x) table) — then fallbacks: every subtable with the code and its `0xF000`/`0xF100`/`0xF200` prefixes, the names through any Unicode subtable and `post`, the code's WinAnsi character, and the code as a GID. `encoding` is `None` when the font has no `/Encoding`: then even (3,1) is read with the raw code, as pdf.js does. One function, two callers — maintainer's call in #223 (2026-10-07). The code → glyph name tables (`STANDARD_GLYPH_NAMES`, `MAC_ROMAN_GLYPH_NAMES`, `WIN_ANSI_GLYPH_NAMES`) come from the same generator as the Annex D tables. The renderer resolves an indirect `/Encoding`, reads `symbolic` from the font descriptor (direct or indirect, bit 3 of `/Flags`), and computes the glyphs once per string. No candidate draws nothing (measured, `tests/render_encoding.rs`). Until #223 the byte was looked up as a Unicode scalar, then taken as a GID: `/Differences [65 /B]` drew exactly "A" and MacRoman `8E` did not draw é (measured 2026-10-07, NotoSans pixel hashes); `glyph::char_code_to_glyph_id` is removed.
- When the face parses and a glyph is chosen but has no outline (a space), nothing is drawn. Until #223 that fell through to the placeholder box: one space at 60 pt was 1,728 dark pixels (measured). The box remains for a Type0 or Type3 font with no program it can read, and for a simple font with none when `base14-fonts` is off.
- Where the encoding's glyph name has no glyph, the first candidate is a fallback (the raw code in another subtable, or the code as a GID), so a glyph is drawn where pdf.js draws nothing; `/Differences [65 /g123]` on Noto draws "A" (measured). Maintainer's call in #223 (2026-10-07): keep drawing the first candidate, fallbacks included, chosen over stopping after the §9.6.6.4 part as pdf.js does — a file with a broken encoding still shows something.
- `justpdf-core` re-exports `ttf_parser` and the renderer uses it from there; the renderer has no `ttf-parser` dependency of its own, so there is one version.
- CID fonts use `/CIDToGIDMap`, and advance by the descendant's `/W` and `/DW` read in core ([CID fonts](cid-fonts.md)).
- Text is not filled with patterns (`fill_color_rgba` only — inferred).
- The cache key is `font_hash` + GID, with a default capacity of 4096. `font_hash` (core `font::font_hash`, re-exported as `glyph_cache::font_hash`) is FNV-1a over the font program's length and all of its bytes. It is not keyed by the address of the font data: until #240 `render_text_string` cloned that data on every call and dropped it, so one address named different fonts over time — keyed that way, alternating two same-size fonts drew the other font's glyph on 99–100 of 200 lookups (measured 2026-10-02). Nor by a prefix: two programs can agree in length and in their first 256 bytes and differ only further in (`justpdf-render/tests/render_glyphs.rs` builds such a pair from Noto Sans, measured). Byte-identical programs share entries, which is sound because the outline depends only on the program and the GID (inferred). The maintainer kept the whole-program hash after seeing its cost (2026-10-06, a judgement, not a derivation; #163); #240 changed only how often it runs.
- An embedded font program is decoded and hashed **once per document** (#240): `extract_font_data` asks core `PdfDocument::font_program(stream_ref)` ([Document access](document-access.md)), which returns a shared `Arc<FontProgramData>` (`data: Arc<[u8]>`, `hash`). `ResolvedFont::font_program` holds that `Arc`, so `render_text_string` takes a reference-count copy instead of the program, and parses the `GlyphSource` once per call for all its glyphs (until #240, once per glyph in `render_glyph`). A font-file stream given as a direct object (not valid PDF) is decoded on its own, uncached. A bundled substitute (#227) is built once per process (`substitute::base14_program`, a `OnceLock` per file). The decision to cache on `PdfDocument` rather than in the renderer is the maintainer's (#240 triage), so `render_page`, the CLI page loop and parallel rendering share it without an API change.
- Costs, measured 2026-10-08 on Windows x86_64 (release, best of 5–20 runs) for Noto Sans (431 KB) and a 20 MiB program (Noto Sans padded with zeros, so its Flate decode is fast): Flate decode 2.9 ms / 31.5 ms, `font_hash` 0.73 ms / 37.8 ms, a `Vec` copy 0.022 ms / 7.5 ms, `Face::parse` 0.3 µs / 0.4 µs (it reads only the table directory). Rendering pages that share the font, 40 `Tj` of 11 glyphs per page at 36 dpi: 10.08 → 3.16 ms per page for 431 KB (50 pages) and 598 → 2.27 ms per page for 20 MiB (10 pages), before → after #240. The after figures are the best of three runs over one `PdfDocument`, so they exclude the one decode and hash each document pays on its first page. The 2026-10-06 figures in #240 (Apple silicon: 1.4 ms / 69 ms decode, 0.9 ms / 27 ms hash) were taken on another machine.

## Known holes / open
- Type3 (#226) and a Type0 font with no program are drawn as boxes. Until #227 so was every non-embedded font: Standard-14 Helvetica rendered as one black box per glyph (measured 2026-10-06, `render_page` at 150 dpi, #184). The bundled set is the maintainer's call in #227 (2026-10-07), made on licences and package size: MuPDF's URW CFF files are the only OFL source; the `.otf`/`.ttf` set in `urw-base35-fonts` is AGPLv3 and not usable here; pdf.js ships Foxit `.pfb` (BSD) plus Liberation Sans 1.07 (GPLv2 + font exception). The call did not cover the bindings: every binding and `justpdf-wasm` depends on `justpdf-render` with default features, so each carries the 608 KB unless it turns the feature off.
- `tests/render_resources.rs` tells which font object a name selected by the width of its placeholder box, so its `font` helper is a Type3 font with no `/CharProcs`; until #227 it was a non-embedded Type1, whose box the substitute replaced. Drawing Type3 glyphs (#226) removes that box too, and the helper needs another probe then.
