# PDF functions

## What it is
Parser and evaluator for PDF function objects: sampled (Type 0), exponential (Type 2), stitching (Type 3), PostScript calculator (Type 4), and an array of functions. Shadings, Separation/DeviceN tint transforms and the soft-mask transfer function `/TR` evaluate through it.

## Governing decisions
**None.** Decided at #47's triage (2026-10-06): resolving references and decoding streams belongs in core, not in each caller. Decided at #437's triage (maintainer, 2026-10-31, shown MuPDF's `pdf-function.c` and a node-count cap as the alternative): a referenced function is read once per `resolve` call and shared, MuPDF's per-object store; a stitching function fails when a sub-function fails or it lists none or more than 256, and an array of functions may not hold an array, as in MuPDF.

## Design model
Rules read from the code (*inferred* unless marked).
- **An array of functions is `PdfFunction::Array`** (#233): `resolve` and `parse` read an array of functions, and `evaluate` concatenates their outputs for the same inputs (a shading's `/Function` given as one 1-out function per colour component, ISO 32000-2 §8.7.4.5). An empty array is no function, and an array is a function only at the top: an array inside an array, or as a stitching sub-function, makes the whole function absent (#437).
- **Sub-functions are `Arc<PdfFunction>`, shared per reference** (#437). `resolve` keeps one `Resolver` per call: the object numbers of the references being read (the ancestors) and every reference read so far with the height of its sub-function tree. A reference read before is reused, and is refused when its height would put a descendant past the depth cap from where it is met again, so sharing gives the result an unshared read would. Only successes are kept: a failure makes the whole function absent, so it is never met twice. A reference to an ancestor is no function, the ancestor-chain rule of [Tree traversal cycles](../invariant/tree-traversal-cycles.md) (shared is not a cycle); with the depth cap and the strict stitching rule a cycle already ends, so removing the ancestor check changes no result (*measured* by mutation 2026-10-31) — it decides on its own only if the cap changes. The cache is per call: two calls on the same object read it twice.
- **Stitching (Type 3)** reads `/Functions` (a direct array) strictly: no entries, more than 256 (MuPDF `MAX_STITCHING`), or one entry that does not read, and the function is absent. Before #437 a failing entry was dropped (`filter_map`) and the rest kept, which let a function listing itself 20 times be read about 20^8 times: the process was killed before it finished (*measured* 2026-10-31, release); an acyclic chain of 8 arrays each listing the next 6 times took 0.92 s. After: 0.3 ms to refuse the first, and 0.3 ms to read seven stitching levels each listing the next 20 times (3 ms at 256) (*measured* 2026-10-31, release).
- **`PdfFunction::resolve(obj, doc)` reads a document's function** (#47): it resolves references, decodes stream data through `PdfDocument::decode_stream` (filters; decryption is already applied by `resolve`), and reads array members and stitching `/Functions` entries the same way, to depth 8 (`MAX_DEPTH`), so a function that names itself stops instead of overflowing the stack (*measured* for #47 by mutation: removing the cap overflows `a_stitching_function_naming_itself_stops`, which since #437 expects no function). `parse(obj)` reads a function as given, without following references or decoding. Product callers use `resolve`: tint transforms in `ColorSpace::resolve`, `/TR` in the renderer's `transfer_table`, and shading `/Function` in the raster renderer. `parse` is reached from `ColorSpace::from_pdf_object`.
- **Type 0 (sampled)** follows ISO 32000-1 §7.10.2 (read raw for #47): each input clipped to its `/Domain` pair, mapped through `/Encode` (default `[0, Size_i − 1]`) and clipped to the table, the surrounding samples interpolated multilinearly (2^m corners, the first input varying fastest), each output mapped from `[0, 2^BitsPerSample − 1]` through `/Decode` (default `/Range`) and clipped to `/Range`. Samples form one bit stream with no padding; `/BitsPerSample` 1, 2, 4, 8, 12, 16, 24 or 32, else no function. A `/Size` entry below 1 reads as 1. Bits past the end read as 0, so a truncated table does not panic. `/Order 3` is interpolated linearly. More than 16 inputs return zeros.
- **Evaluation never panics** on malformed input: each PostScript input is clamped to its own `/Domain` pair or `[0, 1]`, and every clamp orders its bounds and ignores a NaN bound (`clamp_between`; a reversed `[1 0]` made `f64::clamp` panic). Division and modulo by zero push 0. Until #47 an input past the `/Domain` pairs panicked (`range end index 2 out of range for slice of length 1`, *measured* 2026-10-06), Type 0 did not parse, a Flate-filtered Type 4 did not parse, and a referenced stitching sub-function was dropped.
- Real files (*measured* 2026-10-25, 18 local PDFs, 100 pages): pixel-identical to master after #47; none uses these functions.
- Pinned by `justpdf-core/tests/pdf_function.rs` and `justpdf-render/tests/render_pdf_functions.rs`; mutations dropping decoding, sub-function resolution, interpolation, bit reading, `/Encode`, `/Decode`, bound ordering, the per-input domain or the depth cap each failed a named test (#47).
- **Input bound:** nesting of `resolve` is capped at 8, each referenced function is read once per call, and a stitching function lists at most 256 sub-functions, so the work is proportional to the distinct objects named. A Type 0 table is read by index with saturating arithmetic and never allocated by `/Size`. The PostScript parser recurses per `{ }` block (`parse_ps_block`) with no depth limit, and the operand stack has no size limit: `copy` pushes as many values as its operand names, so each `copy` can double the stack (inferred, not run).

## Reference behaviour
- ISO 32000-1 §7.10.2 for Type 0 (read raw for #47, 2026-10-06). The other types follow the code's own reading of §7.10; not compared.
- Loading (read raw 2026-10-31, #437): MuPDF `pdf_load_function_imp` (`source/pdf/pdf-function.c` @ `b487eef`) keeps an ancestor list (`pdf_cycle`, "recursive function"), caches each loaded function per object (`pdf_find_item` / `pdf_store_item`), and `load_stitching_func` throws on no sub-functions, more than `MAX_STITCHING` (256), or a sub-function that fails to load. It has no depth cap. It also throws on a `/Bounds` count or order that does not fit the sub-functions, and resolves a `/Functions` reference; justpdf checks neither (holes). pdf.js (`src/core/function.js` @ `22f5df1`, read raw 2026-10-31): `PDFFunctionFactory.create` caches the top function per reference across calls (`LocalFunctionCache`), but `constructStitched` and `parseArray` read sub-functions with `parse` directly — no sub-function cache, no ancestor check, no depth cap and no 256 limit, so the shapes #437 measured are exponential or unbounded there too (inferred, not run); it throws when a stitching sub-function does not take one input or its output count differs from the first's, which justpdf does not check (holes).

## Cross-cutting invariants
- [Tree traversal cycles](../invariant/tree-traversal-cycles.md) — `Resolver` keeps the ancestor chain; shared sub-functions are reused, not budgeted (#437).
- [Bit widths](../invariant/bit-widths.md) — `/BitsPerSample` outside its set fails the function.

## Blast radius
- [Render shading](render-shading.md) — every shading type evaluates its `/Function` through `PdfFunction` (#233); a change to output count or clamping changes every shaded colour.
- [Color spaces](color-spaces.md) — Separation and DeviceN convert through their tint transform; a function that stops parsing turns the tint into gray.
- [Render transparency](render-transparency.md) — a soft mask's `/TR` is evaluated into a 256-entry table (`transfer_table`); a function that stops parsing is treated as identity.
- [Stream filters](stream-filters.md) — Type 0 and Type 4 data is decoded there; a decode failure makes the function absent.

## Known holes / open
- A stitching sub-function's input and output counts are not checked; pdf.js refuses a mismatch and MuPDF warns (Reference behaviour). Tracked: #445
- The derived `Debug` of a `PdfFunction` follows every shared `Arc`, so printing a function whose tree shares sub-functions prints the unshared tree, exponential in the depth (inferred, not run; no product code prints one).
- `ColorSpace::resolve` calls `PdfFunction::resolve` once per Separation or DeviceN it meets, so the per-call cache is not shared between them: 256 nested colour spaces naming one function read it 256 times (linear; inferred). A cache across calls is outside #437.
- A stitching `/Functions` given as a reference is not followed (`get_array` reads only a direct array), so the function is absent; MuPDF resolves it (inferred). Tracked: #445
- A stitching `/Bounds` whose count or order does not fit the sub-functions is accepted; MuPDF refuses it (inferred). Tracked: #445
- The PostScript calculator parser has no depth limit on nested blocks (inferred). #122's brief lists it among the recursive parsers to check under the 256 limit. Tracked: #122
- The PostScript operand stack has no size limit (inferred above). No issue tracks it.
