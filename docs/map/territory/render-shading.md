# Render shading

## What it is
Rasterizes type 1–7 shadings (function-based, axial, radial, mesh) for the `sh` operator and shading patterns.

## Governing decisions
**None.**

## Design model
- **Function-based shading gets its function from the interpreter** (#47): `render_shading` takes `function: Option<&PdfFunction>`, read with `PdfFunction::resolve`, so Type 0 and filtered Type 4 functions paint their colours. Until #47 `shading.rs` parsed `/Function` itself without decoding: a sampled function fell back to gray (127,127,127) and a Flate Type 4 came out garbled (129,125,0) where red was right (measured 2026-10-25).
- **Every shading type evaluates `/Function` through core `PdfFunction`** (#233), read once by the interpreter with `PdfFunction::resolve` (a single function, or an array of 1-out functions concatenated) and passed to `render_shading`. Axial and radial sample it at 64 points across `/Domain` (default `[0 1]`) into gradient stops (`function_stops`); without a function they fall back to black → white. Meshes (4–7) with a function read one component `t` per vertex in the last `/Decode` pair; `mesh_colours` puts t's index (0–255) in the first colour channel and builds a 256-entry table from the function, and the rasterizer interpolates the index and looks the colour up, so `t` is interpolated before the function is applied (ISO 32000-2 §8.7.4.5.5). Without a function a vertex's colour is its components in the colour space, as before.
  - Until #233 (measured 2026-10-07): an array of three 1-out functions drew black instead of green, a Type 2 `/N 2` ramp was linear (129 where 64 is right), a stitching function with referenced sub-functions fell back to a gray ramp, `/Encode [1 0]` was ignored, and a mesh with `/Function` drew nothing. Pinned by `tests/render_shading_functions.rs`; mutations dropping arrays, the function sampling, the stop count, the one-component read or the `t` table each fail a named test.
- **Free-form (type 4) edge flags follow ISO 32000-1 §8.7.4.5.5** (read raw): a flag-0 vertex starts a triangle and the next two vertices complete it whatever their flags; then flag 1 continues from side (vb, vc) and flag 2 from (va, vc). Until #233 every flag-0 vertex cleared the pending vertices, so a mesh written the usual way (each triangle's vertices flagged 0) drew nothing at all (measured 2026-10-25: a blue triangle drew white). Found while working #233; fixed there because its tests could not draw a type-4 mesh otherwise.
  - The rasterizer still truncates interpolated colours (an RGB 255 can come out 254).
- **Mesh triangles paint through the mask they are given** (#383): `rasterize_triangle` writes pixels itself rather than through tiny-skia, so it reads the mask's coverage `m` per pixel — skip at 0, overwrite at 255, and in between `mask_over` mixes premultiplied `src · m + dst · (1 − m)`, what a masked `fill_path` gives one pixel. The mask is the clip, the soft mask or their product (`draw_mask`, [Render clipping](render-clipping.md)); a mask of another size than the pixmap draws nothing, as tiny-skia does. Until #383 it discarded the mask (`let _ = clip;`), so meshes and patches painted outside the clip and ignored the soft mask (measured 2026-10-26: a red mesh under `0 0 50 100 re W n` painted x = 75 red, and over blue it painted the blue half red). Pinned by `tests/render_mesh_clip.rs`.
  - **A pixel centre on an edge two triangles share belongs to exactly one of them** (a top-left rule: `owns_edge`, with `shared_edge_function` evaluating the edge with its endpoints in a fixed order so both triangles get exactly opposite values). With the inclusive `w >= 0` test both painted it, which overwriting hid but blending does not: under a half soft mask the shared diagonal came out (255, 64, 64) where a plain fill under the same mask gives (255, 128, 128) (measured 2026-10-26). Mutations making every triangle own the edge, none own it, or ignoring the winding each fail a named test. Evaluating the edge in the given order instead changed no pixel in 5 CTMs at 300 dpi (0 doubly painted pixels either way, measured), so the fixed order is unpinned.
- Patch meshes ignore the Bézier control points ("approximation").
- **Axial shadings paint only the region `/Extend` allows** (#384; radial ones did too until #389, below, ISO 32000-2 §8.7.4.5.3–4). tiny-skia 0.11 has no spread mode that leaves the outside transparent (`Pad`, `Reflect`, `Repeat` only), so the gradient keeps `SpreadMode::Pad` and the *filled path* is the region: axial fills the band between the lines through its ends perpendicular to the axis, reaching `FAR` past an end it extends (`axial_region`); radial filled the convex hull of its two disks (`disks_hull`) until #389 drew it per pixel. The region is the shape, so it composes with the clip mask the fill already takes. Until #384 both filled a fixed −10000…20000 square, so `/Extend [false false]` (the default) painted the end colours across the whole clip (measured 2026-10-26: an axial 25→75 shading painted red at x = 10 and blue at x = 90). Pinned by `tests/render_shading_extend.rs`; mutations dropping or swapping the flags, filling the square for radial, dropping the start disk or the upper hull chain, or using an axis-aligned strip for the band each fail a named test.
- **A radial shading is drawn pixel by pixel** (#389, ISO 32000-2 §8.7.4.5.4): `render_radial` maps each pixel centre back to shading space and `radial_s` takes the largest `s` whose circle — centre and radius interpolated from the start (`s` = 0) to the end (`s` = 1) — passes through it, among the roots of the squared equation with a radius of at least 0, in [0, 1], and past 0 or 1 where `/Extend` says; a pixel with none is left as it is. The colour comes from `radial_table`, 256 steps of `s` through the function across `/Domain` (black to white without one), and the mask's coverage is read per pixel through `mask_over`, as for meshes. The circle edges are not antialiased (the maintainer's call, #389, 2026-10-26, shown that cost against (A) moving to tiny-skia 0.12; theirs to reverse). Until #389 tiny-skia 0.11's `RadialGradient` (a two-point conical gradient with the start radius fixed at 0) filled the hull of the two disks (`disks_hull`, #384), so `r0` was ignored and `Extend[0]` painted nothing (measured 2026-10-26 on master: start radius 10 to end radius 30 about one centre gave (123, 0, 131) at pixel x = 65 (radius 15.5) where (185, 0, 70) is right, and painted the centre, which no circle reaches). tiny-skia 0.12 takes a start radius (tried: one compile error, all render suites green) but kept both wrongs this cannot express: the centre inside the hull was painted, and where two circles overlap Skia takes the larger root whatever the range, so start (30, 50) r 10 to (70, 50) r 20 gave blue at x = 65 where `s` = 0.5 is right. Pinned by `tests/render_shading_radial.rs` (with `tests/render_shading_extend.rs`); mutations taking the smallest root, dropping the radius check, always extending either end, ignoring the mask, or sampling pixel corners each fail a named test.
  - Measured 2026-10-26, release, a 612 × 792 pt page at 300 dpi, 50 radial `sh` (`[306 396 0 306 396 400]`, both ends extended), best of 3, one round: the whole page 7429.4 ms on master → 6149.9 ms; each in a 100 pt clip 447.1 → 412.4 ms.
- **Colours convert through the shading's resolved `/ColorSpace`** (#231): `render_shading` takes a `&ColorSpace` that the interpreter resolves with `ColorSpace::resolve` (name, array or reference; DeviceRGB without one), for `sh` and shading patterns alike. `components_to_color` converts through `Color::to_rgb` and truncates each channel as before, so device spaces are unchanged (the DeviceGray control keeps its pixels), and a mesh vertex carries `num_components` values. Until #231 `/ColorSpace` was read with `as_name` only and anything but Gray/CMYK was taken as RGB (measured 2026-10-06: a Separation and an ICCBased gray shading both came out red, (27,0,0) → (231,0,0)). Pinned by `tests/render_colour_spaces.rs`.
- **`sh` paints with the fill alpha `ca` and the blend mode** (#391, ISO 32000-2 §8.7.4.2). Unless it is opaque and Normal, the interpreter's `render_shading` draws the shading into a pixmap of its own, unmasked, which is composited once with `draw_pixmap` (alpha, blend mode, `draw_mask`), as a transparency group is; the pixmap covers the mask's nonzero pixels only (#394, below). The whole shading is one object, so mesh triangles that overlap take the alpha once, and blend modes are tiny-skia's rather than written into `mask_over`. A shading pattern takes `ca` (fill) or `CA` (stroke) when its pixmap is painted, as a tiling pattern does since #393 ([Render tiling patterns](render-tiling-patterns.md)). Until #391 both were ignored (measured 2026-10-26: `ca 0.5` red over white stayed (255, 0, 0) for an axial `sh`, a mesh `sh` and a shading-pattern fill, and `CA 0.5` for a shading-pattern stroke, where a plain fill gives (255, 128, 128); Multiply over blue stayed red for `sh`, where a fill gives (0, 0, 0)). Pinned by `tests/render_shading_alpha.rs`; mutations compositing without the mask, masking twice, taking `CA` for `sh`, compositing at alpha 1 or Normal, keeping the direct path for any blend mode, swapping fill and stroke alpha on patterns, or dropping the stroke's alpha in the device each fail a named test. Always taking the pixmap path changes no test (it is the same picture), so the direct path is unpinned.
  - Over blue, the composited `sh` and a plain fill at `ca 0.5` differ by a unit (128, 0, 128) against (127, 0, 128): the fill's colour carries the alpha truncated to 127/255 (`fill_color_rgba`), the composite takes 0.5 (measured).
- **A shading is drawn over the pixels its paint can change, not the page** (#394). tiny-skia shades every pixel a path covers before the mask cuts it, so until #394 a 100 pt clip or a 100 pt shading-pattern fill cost as much as a full-page shading. `draw_area` cuts the page to the paint's device bounds (grown by a pixel) and to the nonzero pixels of `draw_mask` (`mask_bounds`, a scan of the mask); `sh` and `render_shading_pattern` shade a pixmap of that size, with the page transform moved by its corner, and it is painted back at that corner. An empty area paints nothing. `sh` keeps the direct path, through the mask, when it is opaque and Normal and the area is half the page or more, where cutting saves less than the scan and the composite cost.
  - Measured 2026-10-26, release, a 612 × 792 pt page at 300 dpi, 50 axial shadings, best of 3, two alternating rounds (master → #394): each in a 100 pt clip 6793.0 / 6972.2 → 390.0 / 373.3 ms; the same at `ca 0.5` 8872.7 / 8822.0 → 395.5 / 489.4 ms; 100 pt shading-pattern fills 7442.4 / 7302.0 → 219.1 / 261.0 ms; a clip of 40 % of the page 7424.1 / 7375.4 → 4264.4 / 4432.0 ms; 70 % 7743.2 / 7700.4 → 7865.6 / 7793.8 ms; the whole page clipped 8089.3 / 8080.1 → 8163.8 / 8034.7 ms; unclipped 6871.9 / 6821.6 → 7128.7 / 6973.5 ms. With the direct path kept only for 3/4 of the page, a 70 % clip measured 8451.9 against 8020.5 ms, so the threshold is a half. Pinned for colour by `tests/render_shading_bounds.rs` (a clipped `sh`, mesh, translucent `sh` and shading-pattern fill or stroke against the same pixels drawn whole); mutations moving the pixmap the wrong way, dropping its offset or the y offset, losing the last row or column of the mask, not growing the paint's bounds, or not reaching a miter tip each fail a named test. Cutting to neither the paint nor the mask changes no pixel, so the cut itself is pinned only by these timings.
  - A mesh drawn into the smaller pixmap can differ by a unit from the same mesh drawn whole: its vertices move with the pixmap and the rasterizer truncates interpolated colours (measured: (51, 150, 55) against (50, 149, 54)).
- **A shading pattern's pixmap is placed once** (#394): it is shaded in device space, and tiny-skia applies the paint's transform to the pattern shader too, so the shader transform is that transform's inverse moved to the pixmap's corner. Until #394 it was the identity, so the pixmap went through the CTM and page transform twice (measured 2026-10-26 on master: at 72 dpi a vertical ramp was flipped, green 205 where `sh` gives 49 at user y = 20; at 144 dpi a horizontal ramp was stretched twofold, red 152 where `sh` gives 50 at user x = 80). Pinned by `a_shading_pattern_fill_keeps_its_colours_across_y` and `a_shading_pattern_fill_is_placed_once_at_any_resolution`. The pixmap is rendered unmasked; the clip and soft mask apply once, when it is painted.
- An unknown type is ignored as "unsupported".

## Known holes / open

The branch that picks `c1` is identical for both types, which clippy flags as `if_same_then_else`; it is allowed at the site rather than merged so the selection stays visible. Tracked: #196
