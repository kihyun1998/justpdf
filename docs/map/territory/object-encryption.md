# Object encryption (writing)

## What it is
Encrypts each object's strings and stream data just before serialization (inferred, `crypto/encrypt.rs — encrypt_object`, `encrypt_object_for_writing`). `EncryptionConfig` builds the per-revision `/Encrypt` dictionary and file key; `serialize_pdf_impl` and `incremental_save` call `encrypt_object_for_writing` for each object. Generating IVs, file keys, salts, the random `/Perms` bytes and file IDs also lives here.

## Governing decisions
No ADR covers encryption. Three maintainer decisions recorded on issues; being decisions, only the maintainer overturns them:
- A rewrite keeps the source `/ID` first element (Design model below; since #75 [Document modifier](document-modifier.md) holds the rule) (2026-09-24, #31). Shown: MuPDF `pdf-write.c`'s keeping behaviour, ISO's rule for the permanent identifier, and the result that R3/R4 re-encryption with the same source, passwords and permissions gets the same file key. Alternative declined: always fresh random.
- R6 `/Perms` bytes 12–15 are filled with random bytes (2026-09-24, #31). Shown: the spec requires randomness and MuPDF fills them with `fz_memrnd`. Alternative declined: leave it out of that change.
- When writing with `/EncryptMetadata false`, the catalog `/Metadata` stream keeps its data in plaintext and gets an **explicit Identity crypt filter**: `/Crypt` as the first filter in `/Filter`, `/DecodeParms << /Type /CryptFilterDecodeParms /Name /Identity >>` (2026-09-27, commit fbbe1f2). Shown: the ISO 32000-1 §7.6.5 example marks plaintext metadata this way; qpdf writes plaintext with no filter and reads it through a root-metadata exception; MuPDF's read side has no such exception and breaks plaintext with no filter (whole-source search). Alternatives declined: plaintext with no filter as qpdf does; leaving the write side out.

## Design model
- **All randomness is OS entropy.** IVs (`generate_iv`), the R6 file key (`generate_random_key`), the four R6 salts (`generate_random_salt`), R6 `/Perms` bytes 12–15 and new file IDs (`random_file_id`) all go through `fill_random` → `getrandom` 0.2 (inferred). Without a randomness source it fails with `EncryptionError` and substitutes no other value. MuPDF fills the same places (IVs, salts, R6 key, `/Perms` 12–15, new `/ID`) with `fz_memrnd` (checked against the `pdf-crypt.c` and `pdf-write.c` source, 2026-09-24, #31).
- **Why `getrandom`.** 0.2 was already in core's normal dependency graph through `rand_core` 0.6 (from `pkcs8`, `rsa` and `signature`), so making it a direct dependency added no crate (measured 2026-10-30, `cargo tree -p justpdf-core -i getrandom@0.2.17 -e normal`). A wasm32-unknown-unknown build needs its `js` feature, which `justpdf-compress-wasm` turns on (inferred, its `Cargo.toml`). Bumping `getrandom`'s major version changes this condition.
- **Methods.** `EncryptionConfig` writes RC4-128 as `/V 2 /R 3`, AES-128 as `/V 4 /R 4` with crypt filter `StdCF` (AESV2), and AES-256 as `/V 5 /R 6` with `StdCF` (AESV3) (inferred, `build_r3`, `build_r4`, `build_r6`). Every stream's data is encrypted with the document's stream method; the writer puts no per-stream crypt filter on any stream except the catalog metadata below (inferred, `encrypt_object`).
- **File ID.** `build` in [Document builder](document-builder.md) makes 16 bytes with `random_file_id` and writes both `/ID` elements as the same value, for a newly written file (inferred). `build` in [Document modifier](document-modifier.md), which encrypts and rewrites an existing document after `set_encryption` ([CLI](cli.md) `encrypt` takes this path), keeps the source trailer's `/ID` first element as the permanent identifier and writes a new `random_file_id` as the second (inferred). If the source has no `/ID`, or its first element is an empty string or not a string, it is treated as a newly written file and one `random_file_id` goes into both elements (inferred, `extract_file_id` returns empty; `test_build_with_encryption_treats_empty_id_as_absent`); an empty ID would contribute nothing to key derivation. The file key is derived from the permanent identifier (inferred, `serialize_writer_encrypted`). The source first element is read with the same `extract_file_id` as the read side, because it is the document's permanent identifier; MuPDF also keeps the source first element and derives the key from it. So two R3/R4 re-encryptions with the same source, passwords and permissions get the same file key (#31). The second-element rule was not covered by the #31 decision; it was derived from ISO 32000-1 §14.4 and MuPDF `change_identity` (#75).
- `random_file_id` is the only file ID generator. There is no public accessor for the source `/ID` first element: `extract_file_id` stays `pub(crate)`, called by the parser's key derivation and by `DocumentModifier::from_document`, and outside callers read `PdfDocument::trailer()` (maintainer decision, 2026-10-11, #76: no consumer outside core).
- **Source preservation** in [Document modifier](document-modifier.md) (`preserve_encryption`) does not go through `EncryptionConfig`. It hands the source `/Encrypt` dictionary and `SecurityState` (with the file key) to `serialize_writer_with_state`, and the `/ID` first element is the `state.file_id` the key was derived from (inferred, `build_with_source_encryption`).
- **Object keys** are derived from the generation the object is written at: objects [Document modifier](document-modifier.md) copied use the source generation, the rest 0 (#72). R3 and R4 keys depend on the generation; R6 (AES-256) depends on neither number nor generation (inferred, `encrypt_bytes`).
- **The `/Encrypt` dictionary** is left unencrypted by number: `encrypt_object` skips `state.encrypt_obj_num`, and `serialize_pdf_impl` skips `encrypt_ref.obj_num` (inferred).
- **Catalog `/Metadata` stream.** With `/EncryptMetadata false` at `/V` 4 and 5 (the AES methods), `encrypt_object_for_writing` puts the Identity filter first per the decision above (dropping any existing `/Crypt`, `with_identity_crypt_filter`) and encrypts only the dictionary's strings (inferred). The two writers, `serialize_pdf_impl` (full writes) and `incremental_save`, find that object with `document_metadata_num` (inferred). RC4 (`/V` 2) encrypts it regardless of the flag, although `to_pdf_dict` still writes `/EncryptMetadata false` into the RC4 dictionary (inferred). ISO 32000-1 §7.4.10: "The Crypt filter shall be the first filter in the Filter array entry."
- **Stream dictionary strings** are encrypted with the string method (`string_method`). `/Type /XRef` streams get neither data nor dictionary encrypted (inferred, `is_xref_stream`), the same rule as [Object decryption](object-decryption.md), checked against ISO 32000-1 §7.6.1 and §7.5.8.2 (2026-09-24).
- Ciphertext strings contain high bytes, so they take the hex path of [Object serialization](object-serialization.md); this is where the cause of #20 surfaced (commit 7be23c0).
- **Input size**: the passwords and objects come from the caller. Nothing bounds a password's length (R3/R4 use 32 bytes of it, R6 127) or an object's size; each string and stream is encrypted into a new buffer (inferred).

## Reference behaviour
- MuPDF source (`source/pdf/pdf-crypt.c`, `source/pdf/pdf-write.c`, master, read 2026-09-24, #31): IVs, R6 salts, the R6 file key, `/Perms` 12–15 and a new `/ID` are all filled with `fz_memrnd` (ChaCha20 seeded from OS entropy), as in justpdf. A new `/ID` splits 32 random bytes in half, so MuPDF's two elements **differ**; if the source has an `/ID`, it keeps the first element and replaces only the second. justpdf differs on a new file ([Document builder](document-builder.md) writes the two elements the same, as ISO asks for a first write) and matches MuPDF on a rewrite since #75 (measured 2026-09-30: `test_encrypted_builds_get_distinct_file_ids`, `test_build_with_encryption_keeps_permanent_id_and_changes_the_other` and `justpdf-cli/tests/encrypt.rs` pass).
- ISO 32000-1:2008 §14.4 (Adobe's free copy, read 2026-09-24): `/ID` is "optional but should be used"; the first element is a permanent identifier that does not change on incremental updates, and the second a changing identifier based on the content at the last update. "When a file is first written, both identifiers shall be set to the same value", which [Document builder](document-builder.md) follows. "If only the first identifier matches, a different version of the correct file has been found": a file the CLI rewrote is a different version, so its second element should differ, and since #75 it does (measured 2026-09-30, `justpdf-cli/tests/encrypt.rs`). The clause recommends (should) an MD5 of time, path, size and Info values, but a NOTE says "all that matters is that the identifier is likely to be unique", so 16 random bytes meet its purpose.
- ISO 32000-2: `/ID` is required in PDF 2.0 (Arlington PDF Model `FileTrailer.tsv`, read on #77, 2026-10-10). The ISO 32000-2 text itself has not been read.

## Blast radius
- [File serialization](file-serialization.md) — the call site for full writes. Both sides identify the `/Encrypt` dictionary by object number; the xref stream path has no encryption.
- [Key derivation](key-derivation.md) — generates `/O`, `/U`, `/OE`, `/UE` and `/Perms` from the same file ID and permissions written here.
- [Object decryption](object-decryption.md) — the symmetric rule. A change to which values are encrypted (dictionary strings, xref streams, catalog metadata) must be made on both sides, or justpdf's own output stops reading back.
- [Document builder](document-builder.md), [Document modifier](document-modifier.md) — the two places that decide the file ID. Both write through `serialize_writer_encrypted` in [File serialization](file-serialization.md); the `/ID[0]` written must be the one the key was derived from.
- [Compress WASM](compress-wasm.md) — turns on `getrandom`'s wasm `js` feature; without it the wasm build has no randomness source.
- [Incremental save](incremental-save.md) — copies the source's `/Encrypt` and `/ID` into the new trailer and encrypts appended objects with the source file key at the writer's generation ([Incremental trailer](../invariant/incremental-trailer.md)).

## Known holes / open
- The `/ID` array `EncryptionConfig::build` returns (`make_id_array`, both elements the same) is not used by core's writers: `serialize_writer_encrypted` builds its own from the permanent and changing identifiers (inferred).
- The key, salt and IV tests only check "differs per build". Predictability cannot be observed from outside, so they pass even if the generator is reverted to a time-based one (measured 2026-09-24, #31: with the earlier code, 2000 IVs from the macOS nanosecond clock were 2000 distinct values). They only catch a regression to constant or reused values.
- The #20 regression sweep (`test_encrypt_roundtrip_across_password_combinations`) runs only RC4-128 and AES-128 and checks only that the user password authenticates (inferred). The commit 7be23c0 message says #20 reproduced on AES-256 too. `test_build_with_encryption_roundtrip` covers all three methods with both passwords and compares the page text and `/Info` (inferred), but with one password pair.
