# Object encryption (writing)

## What it is
Encrypts each object's string and stream data just before serialization. `EncryptionConfig` builds the per-revision `/Encrypt` dictionary and key, and `serialize_pdf_encrypted` calls `encrypt_object` for each object. Generating IVs, file keys, salts, the random `/Perms` bytes and file IDs also lives here.

## Governing decisions
There is no decision record (ADR). Three maintainer decisions — being decisions, only the maintainer overturns them, not a better argument:
- CLI `encrypt` keeps the source `/ID` first element (Design model below — since #75 [Document modifier](document-modifier.md) holds this rule). Shown: MuPDF `pdf-write.c`'s keeping behaviour, ISO's rule for the permanent identifier, and the result that R3/R4 re-encryption with the same source, passwords and permissions gets the same file key. Alternative: always fresh random.
- R6 `/Perms` bytes 12–15 are filled with random bytes (2026-09-24, #31). Shown: the spec requires randomness and MuPDF fills them with `fz_memrnd`. Alternative: leave it out of this change.
- When writing with `/EncryptMetadata false`, the catalog `/Metadata` stream keeps its data in plaintext and gets an **explicit Identity crypt filter** (`/Crypt` as the first filter in `/Filter`, `/DecodeParms << /Type /CryptFilterDecodeParms /Name /Identity >>`) (2026-09-27). Shown: the ISO 32000-1 §7.6.5 example marks plaintext metadata this way; qpdf writes only plaintext with no filter and reads it through a root-metadata exception; MuPDF's read side has no such exception and breaks plaintext with no filter (whole-source search). Alternatives: plaintext with no filter as qpdf does; leave the write side out this time.

## Design model
- **All randomness is OS entropy**: IVs (`generate_iv`), the R6 file key (`generate_random_key`), the four R6 salts (`generate_random_salt`), R6 `/Perms` bytes 12–15 and new file IDs (`random_file_id`) all go through `fill_random` → `getrandom` 0.2. Without a randomness source it fails with `EncryptionError` and substitutes no other value. MuPDF also fills the same spots (IVs, salts, R6 key, `/Perms` 12–15, new `/ID`) with `fz_memrnd` (checked against the `pdf-crypt.c` and `pdf-write.c` source, 2026-09-24).
- **Why `getrandom`**: 0.2 was already in core's normal dependency graph (`rsa`/`pkcs8`/`signature` → `rand_core` → `getrandom`). Promoting it to a direct dependency adds no new crate, and the condition that a wasm32-unknown-unknown build needs the `js` feature is the same as before (compress-wasm already turns it on). Bumping `getrandom`'s major version changes this condition.
- **File ID**: `build` in [Document builder](document-builder.md) makes 16 bytes with `random_file_id` and writes both `/ID` elements as the same value (a newly written file). `build` in [Document modifier](document-modifier.md), which encrypts and rewrites an existing document (after `set_encryption` — [CLI](cli.md) `encrypt` takes this path), keeps the source trailer's `/ID` first element as the permanent identifier and writes the second element as a new `random_file_id`. If the source has no `/ID`, or its first element is an empty string or not a string, it is treated as a newly written file and one `random_file_id` goes into both elements (an empty ID contributes nothing to key derivation). The file key is derived from the permanent identifier. The source first element is read with the same `extract_file_id` (parser, `pub(crate)`) as the read side — because the first element is the document's permanent identifier (MuPDF also keeps the source first element and derives the key from it). So two R3/R4 re-encryptions with the same source, passwords and permissions get the same file key. This choice is a maintainer decision (2026-09-24, #31): chosen over "always fresh random" after seeing MuPDF, ISO's permanent-identifier rule and this same-key result. The second-element rule was not covered by that decision; it was derived from ISO 32000-1 §14.4 and MuPDF `change_identity` (#75).
- `generate_file_id(title, timestamp)` is still public API, but nothing in core or the CLI calls it. The same input gives the same ID.
- Source preservation in [Document modifier](document-modifier.md) (`preserve_encryption`) does not go through `EncryptionConfig` — it hands the source `/Encrypt` dictionary and `SecurityState` (file key) straight to `serialize_pdf_encrypted`, and the `/ID` first element is the `state.file_id` the key was derived from.
- Object keys are derived from the generation the object is written at: objects [Document modifier](document-modifier.md) copied use the source generation, the rest 0 (#72). R2–R4 keys depend on the generation; R6 (AES-256) is independent of number and generation.
- **Catalog `/Metadata` stream**: with `/EncryptMetadata false` (V 4 and 5 — the AES methods), `encrypt_object_for_writing` prepends the Identity filter per the decision above (dropping any existing `/Crypt`) and encrypts only the dictionary's strings. The two writers — `serialize_pdf_impl` (fresh writes) and `incremental_save` — find that object with `document_metadata_num`. RC4 (V 2) encrypts it regardless of the flag. ISO 32000-1 §7.4.10: "The Crypt filter shall be the first filter in the Filter array entry."
- Strings inside stream dictionaries are also encrypted with the string method (`string_method`). `/Type /XRef` streams get neither data nor dictionary encrypted (the same rule as [Object decryption](object-decryption.md), checked against the spec text of ISO 32000-1 §7.6.1 and §7.5.8.2).
- Ciphertext strings contain high bytes, so they take the hex path of [Object serialization](object-serialization.md) — this is where the cause of #20 surfaced.

## Reference behaviour
Checked against the MuPDF source (`source/pdf/pdf-crypt.c`, `source/pdf/pdf-write.c`, master, 2026-09-24): IVs, R6 salts, the R6 file key, `/Perms` 12–15 and a new `/ID` are all filled with `fz_memrnd` (ChaCha20 seeded from OS entropy) — the same as justpdf. A new `/ID` splits 32 random bytes in half, so the two elements **differ**, and if the source has an `/ID` it keeps the first element and replaces only the second with new random bytes. justpdf differs on a new file — [Document builder](document-builder.md) writes the two elements the same, as ISO asks for a first write (below) — and matches MuPDF on a rewrite since #75: [Document modifier](document-modifier.md) keeps the first element and writes a new second (measured 2026-09-30: `test_encrypted_builds_get_distinct_file_ids`, `test_build_with_encryption_keeps_permanent_id_and_changes_the_other` and `justpdf-cli/tests/encrypt.rs` pass).

Checked against the ISO 32000-1:2008 §14.4 text (Adobe's free copy, 2026-09-24): `/ID` is "optional but should be used"; the first element is a permanent identifier that does not change on incremental updates, and the second is a changing identifier based on the content at the last update. "When a file is first written, both identifiers shall be set to the same value" — [Document builder](document-builder.md), which writes both elements the same for a new document, follows this. "If only the first identifier matches, a different version of the correct file has been found" — a file the CLI rewrote is a different version, so its second element should differ, and since #75 it does (measured 2026-09-30, `justpdf-cli/tests/encrypt.rs`). The computation recommends (should) an MD5 of time, path, size and Info values, but a NOTE says "all that matters is that the identifier is likely to be unique", so 16 random bytes meet the clause's purpose. Not checked against the ISO 32000-2 text — whether `/ID` is required in PDF 2.0 is an unconfirmed gap.

## Cross-cutting invariants
- [Object syntax roundtrip](../invariant/object-syntax-roundtrip.md) — ciphertext must stay in the file byte for byte.

## Blast radius
- [File serialization](file-serialization.md) — the call site. The xref stream path has no encryption.
- [Key derivation](key-derivation.md) — generating `/O` and `/U`.
- [Object decryption](object-decryption.md) — the symmetric rule.
- [Document builder](document-builder.md), [Document modifier](document-modifier.md) — the two sites that decide the file ID. Both write through `serialize_writer_encrypted` in [File serialization](file-serialization.md).
- [Compress WASM](compress-wasm.md) — where `getrandom`'s wasm `js` feature is turned on.
- [Incremental save](incremental-save.md) — copies the source's `/Encrypt` and `/ID` into the new trailer and encrypts appended objects with the source file key ([Incremental trailer](../invariant/incremental-trailer.md)).

## Known holes / open
- `generate_file_id` is public and unused. There is no public accessor that reads the source `/ID` first element (`extract_file_id` is `pub(crate)`). Tracked: #76.
- The `/ID` array `EncryptionConfig::build` returns (`make_id_array`, both elements the same) is not used by core's two writers — `serialize_writer_encrypted` builds the array separately from the permanent and changing identifiers.
- The key, salt and IV tests only check "differs per build". Predictability cannot be observed from outside, so these tests pass even if the generator is reverted to a time-based one (measured 2026-09-24: with the earlier code, 2000 IVs from the macOS nanosecond clock → 2000 distinct). They only catch a regression to constant or reused values.
- The #20 regression test runs only RC4-128 and AES-128; AES-256 is missing. The commit 7be23c0 message says it reproduced on AES-256 too. The round-trip tests only check the page count and do not compare decrypted content with the source.
