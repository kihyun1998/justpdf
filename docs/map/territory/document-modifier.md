# Document modifier (DocumentModifier)

## What it is
Unpacks every object of an existing document into a `PdfWriter` (`from_document`), deletes, inserts and reorders pages, sets Info, merges and garbage-collects, then writes the whole thing again. Almost every feature that "changes an existing file" — annotations, forms, OCG, outlines, page labels, attachments, compression and so on — runs on top of this.

## Governing decisions
There is no decision record (ADR). The maintainer's decision (2026-09-24, #75 triage): encrypted saving of an existing document is the job of core's `DocumentModifier`, and CLI `encrypt` only calls it. Shown: the reproduction in which the CLI assembled the trailer by hand, lost `/Info` and copied the second `/ID` element. Alternative: a local fix that only adds an `info_ref` accessor for the CLI.

## Design model
- `from_document` rejects an unauthenticated encrypted document with an `EncryptedDocument` error. Before the rejection, almost every object failed to resolve and was silently dropped, and CLI `encrypt` wrote a broken file as a success.
- Any other object that fails to resolve is still silently skipped. The copy rule (resolve succeeded, `/Encrypt` excluded) lives in the single `source_objects`, and the deletion check of [Incremental save](incremental-save.md) uses the same function.
- New object numbers start above **every** number the source uses (including skipped ones). Handing out a skipped number again would give a new object the old `/Encrypt` number, because the encryption exclusion is decided by number alone ([File serialization](file-serialization.md)), and it would go out in plaintext in an incremental save — `test_incremental_save_keeps_encryption` catches this.
- `build` does not GC. GC needs a separate `garbage_collect` call — which is why the old content streams [Redaction](redaction.md) removed stay in the file.
- **Generation numbers**: `from_document` puts the source xref's generation numbers (only non-zero ones) into the `PdfWriter`'s `generations`, and `build` (plain, `set_encryption`, source preservation), `build_with_xref_stream` and [Incremental save](incremental-save.md) write the object header (`N g obj`), the xref entry and the object encryption key with that generation (#72). References `N g R` inside the document are copied from the source as they are, so dropping the generation leaves the object a reference points at missing from the file. Reading the pre-#72 output with qpdf 12.4.1 (pikepdf 10.15.0), the trailer `/Info N 1 R` of full-rewrite and xref-stream output was null, and in incremental-save output the old object of the earlier section (the value before the change) was read (2026-09-29, generation 1 and 300 fixtures, plain, RC4, AES-128). After the fix qpdf reads the same 13 outputs as `(N, 1)`/`(N, 300)` without warnings.
- Before #98 the justpdf reader did not look at a reference's generation, so its own round-trip tests could not reveal generation defects. Now a reference with the wrong generation is `Null` ([Document access](document-access.md)), so assertions that resolve trailer and in-document references (`info_title`) catch generation defects. Assertions that walk `object_refs()` (`assert_all_objects_resolve`) use the xref generation, so they still miss them. The test (`assert_info_at_generation`) checks the header as bytes and the xref entry through the parse result too, and the key through RC4 and AES-128 round trips. R6 (AES-256) is no evidence, because its object key does not depend on number or generation. The fixture (`with_info_at_generation`) is written by justpdf itself, so the qpdf verdict above is the independent judge.
- A generation is kept only while the writer holds the object at that number: replacing a held object with `set_object` keeps the generation, and putting an object at a number it does not hold (a number GC deleted, a number not copied because resolve failed, the source `/Encrypt` number) gives generation 0. `add_object` also gives 0. `set_object` returns no reference, so the reference a caller uses to point at the new object is `N 0 R`. Generation + 1 on number reuse (ISO 32000-1 §7.5.4, MuPDF `gen_list[num]++`) is not done — new numbers are handed out above the source's highest number, so no caller in the crate reuses one.
- `generations` is a separate map next to `objects`. Changing the type of the public field `objects: Vec<(u32, PdfObject)>` would break the public API, and many places in the crate, such as compress, edit it directly (technical decision, #72). The cost: code that renumbers references has to fix up the generation too — [Source generation](../invariant/source-generation.md).
- **Trailer references**: the modifier holds catalog and info only by number (`catalog_num`, `info_num`) — it drops the generation received from the source (#112). `build`, `build_with_xref_stream` and [Incremental save](incremental-save.md) write trailer `/Root` and `/Info` with the generation the writer writes the object at that number (`PdfWriter::reference_to`) (#110). Using the source generation as is made the trailer point with the source generation at an `/Info` or catalog put back at a number the writer did not hold (written at generation 0), and it read as `Null` (reproduced: in a generation 1 fixture, `set_info`/`set_object` after removing `/Info` and the catalog from the writer). The public `catalog_ref()` accessor takes its generation from the same source and returns the same value (`IndirectRef`) as trailer `/Root` (#112). Synchronizing a stored reference does not work — callers edit the writer directly through `writer()`, so the modifier cannot see the change. Changing the return type from `&IndirectRef` to a value is a technical decision, and the maintainer confirmed it (2026-09-29, #112 — alternative: a new method + deprecating the old one). Every caller in the repo used only `.obj_num` and `.clone()`.
  - **Maintainer decision (2026-09-29, #72)**: keeping generation ≠ 0 objects out of object streams was left out of this change (ISO 32000-1 §7.5.7: an object inside an object stream has generation 0). Shown: the only packer in the crate, `pack_into_object_streams`, is inactive (`#[allow(dead_code)]`, its call site commented out), and the public `pack_object_streams` takes only numbers and objects without generation information, so filtering out generations would mean changing its public signature. Alternatives: fix only the inactive internal function, or change the public API too. This decision covered packing only — not the renumbering sites below. #106, reported separately, settled it with a `pack_object_streams` method and a serialization guard ([object streams](object-streams.md)).
- `set_info` shares the [Text string encoding](../invariant/text-string-encoding.md) problem with [Document builder](document-builder.md).
- **Encrypted saving**: `build` after `set_encryption(EncryptionConfig)` writes an encrypted file through `serialize_writer_encrypted` in [File serialization](file-serialization.md). `/Info` is carried over as it is, and `/ID` follows the file ID rule of [Object encryption](object-encryption.md) (keep the source's first element and a new random second; if the source has no `/ID`, two equal new random elements). `from_document` takes the source `/ID` first element with `extract_file_id` and keeps it.
- `build`'s encryption is one of three states (`Encryption`): none (the default), new settings (`set_encryption`), source preservation (`preserve_encryption`). Of the two methods, whichever is called later wins (maintainer confirmation, 2026-09-28, #102). A `build` with neither called writes plaintext even for a modifier made from an authenticated encrypted source, and CLI `decrypt` relies on this behaviour. Not changing the default to preservation is a maintainer decision (#102 — shown: the measurement that pikepdf `save()`'s default also removes encryption; alternative: preserve by default).
- **Source preservation**: `from_document` keeps the source `SecurityState` (including the file key) and the trailer's `/Encrypt` dictionary as written (`source_encrypt_dict`). `build` adds that dictionary as an object at a new number, changes `encrypt_obj_num` to that number (because the encryption exclusion is decided by number) and writes with `serialize_pdf_encrypted`. It derives no new key, so no password is needed, and both the source user and owner passwords still open it — the same approach as qpdf's encryption preservation (pikepdf `save(encryption=True)`, measured 2026-09-28: the output of an R5 file opened only with the user password opens with both passwords). `/ID` is [`state.file_id`, the value the key was derived from, new random] — R2–R4 key derivation uses the first element. If the source was not encrypted, it writes plaintext. A stream that was plaintext in the source through the Identity crypt filter loses its `/Crypt` when read, so in source-preservation output it is encrypted with the default method (inferred).
- [Incremental save](incremental-save.md) takes the source `PdfDocument` and uses its key (#25), so it allows the source-preservation state.
- `build_with_xref_stream` and `incremental_save` after `set_encryption`, and `build_with_xref_stream` after `preserve_encryption` on an encrypted source, are `UnsupportedEncryption` errors — the former because the xref stream path has no encryption implementation, the latter because it follows the source's encryption (or plaintext); both are blocked so the setting is not silently ignored (a technical decision made in #75).
- `from_document` does not copy the trailer's `/Encrypt` dictionary object. Copying it would leave an unreferenced object in the rewritten file, and in a plaintext rewrite (CLI `decrypt`) the old `/O` and `/U` (`/OE` and `/UE`) would go out in plaintext, material for an offline attack on the old password. Incremental save keeps the source bytes and the trailer's `/Encrypt` reference as they are, so it is unaffected.
- Merging (`merge_documents`) copies pages and their dependent objects with `graft_page`/`deep_copy_object` and handles resource name collisions.

## Known holes / open
- Objects that fail to resolve are dropped without a warning.
- `graft_page` follows the source page's `/Parent` through `deep_copy_object`, copies the whole source page tree, then overwrites `/Parent` and leaves the copy orphaned — about N copies for an N-page merge (inferred).
- Tracked: #33 (text string encoding), #121 (graft_page copies the tree)
