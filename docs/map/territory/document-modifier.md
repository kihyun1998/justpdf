# Document modifier (DocumentModifier)

## What it is
Copies every readable object of an existing document into a `PdfWriter` (`from_document`); deletes, inserts and reorders pages; sets Info; garbage-collects; and writes the whole document again (inferred, `writer/modify.rs — DocumentModifier`). `merge_documents` in the same file builds a new document from the pages of several. Almost every feature that changes an existing file (annotations, forms, OCG, outlines, page labels, attachments, compression and so on) runs on top of this, and so do CLI `split`, `encrypt`, `decrypt`, `clean` and the decrypt step of `compress` (inferred, `justpdf-cli/src/main.rs`).

## Governing decisions
No ADR decides the modifier's model. [ADR 0006](../../adr/0006-breaking-changes-are-allowed-before-1-0.md) sits adjacent: it removes "do not break the public API" as a reason, and the separate `generations` map below was kept for that reason (#72, before the ADR).

Decisions recorded on issues:
- Encrypted saving of an existing document is the job of core's `DocumentModifier`; CLI `encrypt` only calls it (maintainer, 2026-09-24, #75 triage). Shown: the reproduction in which the CLI assembled the trailer by hand, lost `/Info` and copied the second `/ID` element. Alternative declined: a local fix that only adds an `info_ref` accessor for the CLI. The code follows it: `cmd_encrypt` calls `set_encryption` and `build` (inferred).
- The encryption states and their default (#102, below).

## Design model
- **Encrypted sources.** `from_document` rejects an unauthenticated encrypted document with `EncryptedDocument` (inferred; `test_from_document_requires_authentication`). Before the rejection, almost every object failed to resolve and was silently dropped, and CLI `encrypt` wrote a broken file as a success (#75).
- **Unreadable objects.** Any other object that fails to resolve is skipped without a message (inferred, `source_objects`). Measured 2026-10-07 (#97): `justpdf clean` on a catalog whose `/Probe` points into a corrupt object stream exits 0 with no message, and the output's `/Probe` resolves to `Null`. qpdf leaves such an object out the same way but warns (`Objects::resolve`, #97). The copy rule (resolve succeeded, `/Encrypt` excluded) lives in the single `source_objects`, and the deletion check of [Incremental save](incremental-save.md) uses the same function (inferred).
- **Object numbers.** New object numbers start above **every** number the source's xref uses, including skipped ones (inferred, `from_document` sets `next_obj_num` from `object_refs()`). Handing out a skipped number again could give a new object the old `/Encrypt` number. Encryption exclusion is decided by number alone ([File serialization](file-serialization.md)), so that object would go out in plaintext in an incremental save; `test_incremental_save_keeps_encryption` catches this.
- `build` does not garbage-collect. GC needs a separate `garbage_collect` call (inferred), which is why the old content streams [Redaction](redaction.md) removes stay in the file. `garbage_collect` keeps what is reachable from the catalog and Info numbers through references (inferred, `collect_references`).
- **Generation numbers.** `from_document` puts the source xref's non-zero generation numbers into the `PdfWriter`'s `generations`. `build` (plain, `set_encryption`, source preservation), `build_with_xref_stream` and [Incremental save](incremental-save.md) write the object header (`N g obj`), the xref entry and the object encryption key with that generation (inferred; #72). References `N g R` inside the document are copied from the source as they are, so dropping the generation leaves the object a reference points at missing from the file. Reading the pre-#72 output with qpdf 12.4.1 (pikepdf 10.15.0), the trailer `/Info N 1 R` of full-rewrite and xref-stream output was null, and in incremental-save output the old object of the earlier section (the value before the change) was read (2026-09-29, generation 1 and 300 fixtures, plain, RC4, AES-128; #72). After the fix qpdf read the same 13 outputs as `(N, 1)`/`(N, 300)` without warnings (#72).
- **Testing generations.** Before #98 the justpdf reader did not look at a reference's generation, so its own round-trip tests could not reveal generation defects. Now a reference with the wrong generation is `Null` ([Document access](document-access.md)), so assertions that resolve trailer and in-document references (`info_title`) catch generation defects. Assertions that walk `object_refs()` (`assert_all_objects_resolve`) use the xref generation, so they still miss them (inferred). `assert_info_at_generation` checks the header as bytes, the xref entry through the parse result, and the key through RC4 and AES-128 round trips (inferred). R6 (AES-256) is no evidence, because its object key depends on neither number nor generation (inferred, `decrypt_bytes`). The fixture (`with_info_at_generation`) is written by justpdf itself, so the qpdf verdict above is the independent judge.
- **Which generation an object gets.** A generation is kept only while the writer holds the object at that number. Replacing a held object with `set_object` keeps the generation; putting an object at a number the writer does not hold (a number GC deleted, a number not copied because resolve failed, the source `/Encrypt` number) gives generation 0. `add_object` also gives 0 (inferred, `PdfWriter::set_object`, `add_object`). `set_object` returns no reference, so the reference a caller writes to point at the new object is `N 0 R`. Generation + 1 on number reuse (ISO 32000-1 §7.5.4, MuPDF `gen_list[num]++`) is not done: new numbers are handed out above the source's highest number, so no caller in the crate reuses one (inferred).
- `generations` is a separate map next to `objects`, because changing the type of the public field `objects: Vec<(u32, PdfObject)>` would break the public API, and many places in the crate, such as compress, edit it directly (technical decision, #72). The cost: code that renumbers references has to fix up the generation too — [Source generation](../invariant/source-generation.md).
- **Trailer references.** The modifier holds the catalog and Info only by number (`catalog_num`, `info_num`) and drops the generation received from the source (inferred; #112). `build`, `build_with_xref_stream` and [Incremental save](incremental-save.md) write trailer `/Root` and `/Info` with the generation the writer writes the object at that number (`PdfWriter::reference_to`) (inferred; #110). Using the source generation as is made the trailer point with the source generation at an `/Info` or catalog put back at a number the writer did not hold (written at generation 0), and it read as `Null` (reproduced on #110: in a generation 1 fixture, `set_info`/`set_object` after removing `/Info` and the catalog from the writer). The public `catalog_ref()` takes its generation from the same source and returns the same value (`IndirectRef`) as trailer `/Root` (inferred; `test_catalog_ref_is_the_root_the_modifier_writes`). Keeping a stored reference in sync does not work: callers edit the writer directly through `writer()`, so the modifier cannot see the change. Changing the return type from `&IndirectRef` to a value was confirmed by the maintainer (2026-09-29, #112; alternative: a new method plus deprecating the old one); every caller in the repo used only `.obj_num` and `.clone()` at the time (#112).
  - **Maintainer decision (2026-09-29, #72)**: keeping generation ≠ 0 objects out of object streams was left out of #72 (ISO 32000-1 §7.5.7: an object inside an object stream has generation 0). #106 settled it later: `DocumentModifier::pack_object_streams` packs only generation-0 objects, and the serializer refuses a compressed object at generation ≠ 0 (inferred, `pack_object_streams`, `serialize_writer_with_xref_stream`; [Object streams](object-streams.md)).
- `set_info` shares the [Text string encoding](../invariant/text-string-encoding.md) problem with [Document builder](document-builder.md): it stores `value.as_bytes()` (inferred).
- **Encryption states.** `build`'s encryption is one of three states (`Encryption`): none (the default), new settings (`set_encryption`), and source preservation (`preserve_encryption`). Whichever of the two methods is called later wins (inferred; maintainer confirmation, 2026-09-28, #102). A `build` with neither called writes plaintext, even for a modifier made from an authenticated encrypted source, and CLI `decrypt` relies on this (inferred, `cmd_decrypt`). Not making preservation the default is a maintainer decision (#102; shown: the measurement that pikepdf `save()` also removes encryption by default; alternative declined: preserve by default).
- **New encryption.** `build` after `set_encryption(EncryptionConfig)` writes through `serialize_writer_encrypted` in [File serialization](file-serialization.md). `/Info` is carried over as it is. `/ID` keeps the source's first element (read with `extract_file_id` in `from_document`) and gets a new random second; a source with no usable `/ID` gets one new random value in both elements (inferred, `build`). The rule belongs to [Object encryption](object-encryption.md).
- **Source preservation.** `from_document` keeps the source `SecurityState` (including the file key) and the trailer's `/Encrypt` dictionary as written (`source_encrypt_dict`). `build` adds that dictionary as an object at a new number, points `encrypt_obj_num` at that number (encryption exclusion is decided by number) and writes with `serialize_writer_with_state` (inferred, `build_with_source_encryption`). It derives no new key, so no password is needed, and both the source user and owner passwords still open the output. qpdf preserves encryption the same way (pikepdf `save(encryption=True)`, measured 2026-09-28 on #102: the output of an R5 file opened only with the user password opens with both passwords). `/ID` is [`state.file_id`, the value the key was derived from; new random], because R2–R4 key derivation uses the first element (inferred). If the source was not encrypted, it writes plaintext (inferred; `test_preserve_encryption_on_an_unencrypted_source_writes_it_plain`). A stream that was plaintext in the source through the Identity crypt filter loses its `/Crypt` when read, so in preserved output it is encrypted with the default stream method; the catalog `/Metadata` under `/EncryptMetadata false` is the exception, because the writer adds an Identity filter back (inferred, `remove_crypt_filter`, `encrypt_object_for_writing`).
- [Incremental save](incremental-save.md) takes the source `PdfDocument` and uses its key (#25), so it accepts the source-preservation state (inferred; `test_incremental_save_accepts_preserved_encryption`).
- **Refused combinations.** `build_with_xref_stream` and `incremental_save` after `set_encryption`, and `build_with_xref_stream` after `preserve_encryption` on an encrypted source, return `UnsupportedEncryption` (inferred). The xref stream path has no encryption, and an incremental save follows the source's encryption; both are refused so that the setting is not silently ignored (technical decision, #75).
- `from_document` does not copy the trailer's `/Encrypt` dictionary object (inferred, `source_objects`; `test_rewrite_drops_the_source_encrypt_dictionary`). A copy would leave an unreferenced object in the rewritten file, and in a plaintext rewrite (CLI `decrypt`) the old `/O` and `/U` (`/OE` and `/UE`) would go out in plaintext, material for an offline attack on the old password. Incremental save keeps the source bytes and the trailer's `/Encrypt` reference as they are, so it is unaffected.
- **Fonts** (#173): `add_font`, `add_font_with` and `add_standard_font` register `Font` handles in the modifier's own `FontRegistry`; `insert_page` returns `FontError` for a page drawn with another document's `Font` (inferred). The embedded fonts are written at their reserved numbers before `build`, `pack_object_streams`, `build_with_xref_stream` and `incremental_save` (the private `write_fonts`), and only when they drew something new since the last write — [CJK font embedding](cjk-font-embedding.md). No font object is in the writer before the first output, so a `garbage_collect` before it cannot remove one (measured, #173); after an output it can ([CJK font embedding](cjk-font-embedding.md), Known holes). `missing_chars()` reports what the registered fonts could not draw.
- **Merging.** `merge_documents` copies each page with `graft_page`, which follows every reference with `deep_copy_object` and a fresh number map per page, then serializes a new writer with the public `serialize_pdf` at version 1.7, with no `/Info` and no `/ID` (inferred). Each page keeps its own copied `/Resources`, so resource names cannot collide across documents; there is no collision handling because none is needed (inferred).
- **Page tree fallbacks.** Without a catalog reference in the source, `catalog_num` is 1; without `/Pages` in the catalog, page operations act on object 2 (inferred, `from_document`, `find_pages_ref`).
- **Input size**: the source document bounds what is copied. `from_document` resolves every object in the xref into memory at once (inferred, `source_objects`); nothing bounds the count or total size.

## Reference behaviour
- qpdf's encryption preservation (pikepdf `save(encryption=True)`): justpdf's `preserve_encryption` matches it (measured 2026-09-28, #102).
- pikepdf `save()` removes encryption by default, as `build` does (measured on #102).
- qpdf `Objects::resolve` drops an unreadable object as justpdf does, but warns (#97, 2026-10-07).
- MuPDF `pdf_delete_page`/`pdf_insert_page` and `pdf_graft_mapped_page` are the models chosen for #80 and #121 (Known holes).

## Blast radius
- [File serialization](file-serialization.md) — `build`'s output path. Both sides assume trailer `/Root` and `/Info` are passed as numbers and written at the writer's generation.
- [Object encryption](object-encryption.md) — owns the file ID rule `build` applies, and encrypts each object at the generation the modifier holds. A change to either side's assumption about `/ID[0]` or the generation breaks R2–R4 key derivation.
- [Page tree](page-tree.md) — page operations assume a flat root `/Kids` (Known holes); a change in how the tree is read or written has to match.
- Features built on this modifier — [Annotations](annotations.md), [Redaction](redaction.md), [Form fill](form-fill.md), [Form flatten](form-flatten.md), [Optional content](optional-content.md), [Outlines](outlines.md), [Page labels](page-labels.md), [Embedded files](embedded-files.md), [Compress pipeline](compress-pipeline.md). They assume `from_document` copies every readable object at its source number and that `build` writes what they put in `writer().objects` without GC.
- [CLI](cli.md) — `split`, `encrypt`, `decrypt`, `clean`, `merge` and `compress` rely on the default states (plaintext `build`, `reorder_pages` taking a list of indices). [Facade](facade.md) — the `Modifier` wrapper re-exposes `preserve_encryption` and the inner modifier.
- [CJK font embedding](cjk-font-embedding.md) — a new output path has to call `write_fonts` first, or the registered fonts are missing from the file.
- [Incremental save](incremental-save.md) — shares `source_objects` as the definition of what was copied, and assumes new numbers never reuse a source number.

## Known holes / open
- Objects that fail to resolve are dropped without a warning. The maintainer decided on 2026-10-07 to keep leaving them out (they resolve to `Null`, ISO 32000 §7.3.10), record them on the modifier, and have the CLI print one warning per object and exit 3 (#97). Not built at HEAD: the modifier has no record of them (inferred). Tracked: #97
- `delete_page`, `insert_page` and `reorder_pages` treat the root `/Kids` as the page list and set the root `/Count` to its length (inferred). Measured 2026-10-07 on `testpdf.pdf` (392 pages under 20 intermediate nodes, #80): `delete_page(391)` is a silent no-op, `delete_page(0)` removes 20 pages (a whole node), and a full reverse `reorder_pages` only reverses the 20 nodes. CLI `split` calls `reorder_pages`. Decided on 2026-10-07 (#80): locate pages through the tree and adjust ancestor counts as MuPDF `pdf_delete_page`/`pdf_insert_page` do; out-of-range indices are `PageOutOfRange`; `reorder_pages` takes only a permutation, pushes inherited attributes into each page and rebuilds a flat root `/Kids`. Tracked: #80
- `graft_page` follows the source page's `/Parent` through `deep_copy_object`, copies the whole source page tree, then overwrites `/Parent` and leaves the copy orphaned (inferred). Measured 2026-10-07 (#121): 20 pages under 4 intermediate nodes merge from 105 KB to 2.1 MB with 101 `/Pages` nodes; 40 pages to 4.3 MB. A fresh `remap` per page also copies shared fonts and images once per page, and after `/Parent` is overwritten a page that inherited `/MediaBox` and `/Resources` loses both (300×400 becomes the 612×792 default; images and fonts unreachable). Decided on 2026-10-07 (#121): MuPDF `pdf_graft_mapped_page`'s allowlist (`Contents`, `Resources`, the five boxes, `Rotate`, `UserUnit`, read with inheritance), one object map per source document, `/Annots` not carried. Tracked: #121
- Rewrites from a source drop its `/ID` when not encrypting, and `merge_documents` writes none. The maintainer decided on 2026-10-10 that output written from a source keeps the source's first element with a fresh second, and that `merge` follows the first input (#77). Tracked: #77
- Info values are written as BOM-less UTF-8. Tracked: #33
- Should the separate `generations` map stay, now that ADR 0006 says avoiding a public API break is no reason to keep a worse design? Only the maintainer can answer.
- `merge_documents` writes a catalog holding only `/Pages`, so the inputs' outlines, page labels, AcroForm and `/Names` are dropped; `delete_page`, `insert_page` and `reorder_pages` leave `/Outlines` and `/PageLabels` pointing at the old pages (inferred, reported by the 2026-10-30 rewrite; see [Outlines](outlines.md), [Page labels](page-labels.md)).
