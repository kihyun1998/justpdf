# Tree traversal cycles

## The fact
Code that walks the PDF object graph as a tree (`/Kids`, `/First`/`/Next`) carries an **ancestor chain** as it walks: the references above the node being walked. Meeting an ancestor again is a cycle. Meeting a non-ancestor node twice (a shared node, the same kid listed twice) is not a cycle, and it is walked twice. Only indirect references can be ancestors — a direct dict cannot point at itself.

On a cycle:
- **Document structure trees** (page tree, AcroForm field tree, signature detection's field tree, outlines) — fail with `JustPdfError::CircularReference` (the number of the ancestor returned to).
- **Lookup table trees** (page label number tree, attachment name tree, named destination name tree) — skip just that kid and return the rest. If the root is an indirect reference, the caller puts the root in the ancestors first (so a kid leading back to the root does not yield the root's entries again).

Shared nodes are not cycles but they multiply visits — listing the same kid twice on every level walks it 2^k times at level k. So each walk carries a `VisitBudget` (`justpdf-core/src/tree_walk.rs`). A visit is charged the **size** of the node it reads (the node itself plus the number of array elements and dictionary values it holds directly or nested — for a stream, only the dictionary), and a visit that would push the total charge past **4 times the sum of the sizes of the distinct nodes resolved so far** is refused. It counts size rather than visits because, counting only visits, N distinct nodes each listing one M-entry leaf three times stay within a ratio of 4 while yielding N×M results (the square of the file size). For a real tree the total charge equals the size sum, so it never goes over whatever the size, and the work of a walk inflated by shared nodes is proportional to the size sum of the distinct objects the file holds. A revisit of an already resolved node is judged by its recorded size **before resolving it** — resolving (a cache hit is a clone too) and computing the size on every refusal would make the refusals quadratic again. A refused visit is not charged. A refusal follows the same split as a cycle: document structure trees fail with `JustPdfError::LimitExceeded` (the number of the refused node), lookup table trees skip that kid. The root of a lookup table tree is not counted — it is visited only once. The budget does not look at `/Count`, so a `get_page` whose pruning a false `/Count` switched off also stops.

The error/skip split for cycles is a **maintainer decision** (2026-09-29, #52). Grounds looked at: the MuPDF source — `pdf-page.c` (`pdf_load_page_tree_imp`, throws "cycle in page tree"), `pdf-form.c` (`pdf_lookup_field_imp`, throws "cycle in fields"), `pdf-outline.c` (`pdf_test_outline`, throws "Cycle detected in outlines"), `pdf-nametree.c` (`pdf_lookup_name_imp`, `pdf_load_name_tree_imp`, `pdf_lookup_number_imp`, stop quietly on a cyclic branch). The ancestor chain approach is a **derivation** from MuPDF's `pdf_cycle` (a linked list on the parent side) — only MuPDF's outlines use global mark bits.

Making the visit budget a **ratio** is also a **maintainer decision** (2026-09-29, #120). Grounds looked at: measurements (release, a 2KB file, at k=22 `collect_pages` 9.3 s, `parse_acroform` 14.9 s, `read_page_labels` 17.2 s, 4 million results — `justpdf::Document::open` calls `collect_pages`; `get_page` with a false `/Count` 9.1 s; outlines at k=20 4.8 s), a reading of ISO 32000-1 (§7.7.3 a page node has one `/Parent`, §12.7.3.1 "a field shall be in at most one Kids array" — shared nodes are non-conforming), pdf.js throwing on shared nodes, and four options (a fixed visit cap, a ratio budget, a global visited set, documentation only) with the tests each one turns red. A fixed cap rejects normal documents larger than the cap, and a global visited set was rejected because it overturns the shared node decision above (#52). Reporting the overrun as a new variant was decided the same day — chosen after seeing that `JustPdfError` is not `#[non_exhaustive]`, so it is a semver break. The factor 4 is a **derivation**: a real tree is 1, the `*_shared_kid_*` tests reach about 1.7 at most, and a tree that splits in two passes it within 5 levels. Across the 82 PDFs on this computer (71 walks) there was not a single revisit (2026-09-29, highest ratio 1.0).

Counting the budget by **node size** rather than by visits is also a **maintainer decision** (2026-09-29, #120). Grounds looked at: the quadratic measured on top of the visit-count budget — on a 102KB file (1000 nodes each listing a 1000-entry leaf three times) `read_page_labels` gave 3 million results in 11–17 s, and on a 195KB file (a node holding 20,000 integers listed 15,000 times, with 5,000 undefined references eating the budget) `read_named_destinations` took 17.9 s — and two options (size weighting / keep the visit-count budget and open a follow-up issue). What this decision does not cover: string and stream **byte** payloads (a 20KB `/Contents` copied on every visit — size is an element count, so one string counts as 1), the copying done for every result even in an honest tree with no shared nodes (inherited `/Resources`, field `full_name`), resolving leaf values that are not tree nodes (Tracked: #135).

## Why it is cross-cutting
There are eight tree walkers and none calls another: `walk_page_tree`, `walk_page_tree_find`, `walk_field_tree`, `collect_sig_fields`, `read_outline_siblings`, `parse_number_tree`, `collect_name_tree_values`, `parse_name_tree`. #52 listed five, and grep found the other three (attachment and destination name trees, signature detection). All eight, which had no guard, killed the process with a stack overflow on cyclic input (reproduced 2026-09-29, `tests/tree_cycles.rs`) — a failure a `Result` cannot catch.

## Territories it holds in
- [Page tree](../territory/page-tree.md) — `walk_page_tree`, `walk_page_tree_find`: record `/Pages` nodes as ancestors. Error.
- [AcroForm](../territory/acroform.md) — `walk_field_tree`: records fields that have `/Kids` as ancestors. Error.
- [Signature detection](../territory/signature-detection.md) — `collect_sig_fields`: the same rule. Error.
- [Outlines](../territory/outlines.md) — `read_outline_siblings`: records the item as an ancestor while reading its children. Error. A `/Next` loop within one level still stops quietly as before (a neighbour the #52 decision did not cover).
- [Page labels](../territory/page-labels.md) — `parse_number_tree`: skip.
- [Embedded files](../territory/embedded-files.md) — `collect_name_tree_values`: skip.
- [Outlines](../territory/outlines.md) — `parse_name_tree` (named destinations): skip.

## What a violation looks like
- (Before #52) on a page tree whose `/Kids` pointed at an ancestor, `collect_pages` killed the process with a stack overflow. Thanks to `/Count` pruning, `get_page` did not die at small indices but returned **the same page under a different index** (index 3 → object 4, the same as index 0).
- Using a global visited set instead of the ancestor chain misjudges shared nodes as cycles — the `*_shared_kid_*` tests catch it.
- (Before #120) opening a 2KB file that listed the kid twice on every level took seconds and gave 2^k results (measurements above). On the same file with every `/Count` inflated, `get_page` walked all 2^k leaves and reported "not found", and a negative `/Count` caused an addition overflow panic in debug builds. With the budget, the same file gives `LimitExceeded` or a truncated result within a few hundred µs — the `*_stops_at_visit_limit` tests catch it.
- Counting only visits, the 102KB file above gives 3 million results — the `*_is_charged_by_leaf_size` tests catch it, and `collect_pages_reads_the_wide_shared_leaf_fixture` shows the same shape stays within budget when the leaf is small. With size weighting, the 102KB file takes 16 ms with 4,000 results, the 195KB file 32 ms, and a 504KB file listing 20,000 inline `/Nums` pairs 15,000 times 425 ms with 80,000 results (release).
- Refusing a node already seen only after resolving it clones and computes the size on every refusal, and the 504KB file takes 136 s — `a_refused_revisit_does_not_resolve_the_node` (a unit test in `tree_walk.rs`) catches it.
- Replacing the ratio budget with a fixed cap blocks large normal trees — `collect_pages_reads_a_large_unshared_tree` (about 5,100 nodes) catches a cap lower than that. It cannot catch a fixed cap above it.

## Discovery history
Found by reading code on 2026-09-23 while writing the map (#52, inferred). On 2026-09-29 all eight sites were reproduced by running them and fixed. The same day, during #52, the exponential revisiting of shared nodes was written down as inferred (#120), then reproduced by measurement and the visit budget added — outlines, which the issue had left out saying "a per-level visited set blocks it", were also 2^k when two siblings shared a `/First`. Two separate completeness reads reviewing the visit-count budget found the same quadratic (the per-visit work was not counted), which led to size weighting, and a probe caught the first version of that change making the refusal path quadratic again.

## Where it will recur
**Any new code that recurses or loops along `/Kids`, `/First`, `/Next` or `/Parent` is subject to this invariant.** Command to find it: `rg -n 'b"Kids"|b"First"|b"Next"' --type rust justpdf-*/src` — the writing side (`writer/` and `outline/builder.rs`, which **build** trees) is not subject to it. A new walker carries a `VisitBudget`, and adds to `tests/tree_cycles.rs` an ancestor cycle case, a shared node case, a tree that splits in two, and a case sharing a large leaf widely.

What this invariant does not cover: extreme depth without a cycle (the ancestor chain does not limit depth). Measured 2026-10-07 on Windows' 1 MB main-thread stack: a `/Kids` chain overflows `collect_pages` at depth 500 in debug (400 ok) and 900 in release (850 ok), far shallower than first inferred; the object parser overflows at 500 nested `[` in debug and 2,000 in release. Decided in #122: one core depth limit of 256 (MuPDF `MAX_CYCLE_STACK_DEPTH`; qpdf's parser limit 499 would overflow a debug build here) for every recursive walker and the object parser, returning `LimitExceeded`; the renderer caps pattern tiles and soft-mask `/G` at the Form XObject depth of 10 and skips past it. The constant assumes the main thread's stack, and the case where `get_page` and `collect_pages` answer differently for the same file — with an honest `/Count`, `get_page` prunes the shared subtree and finds the page without spending the budget, while `collect_pages` on the same file is `LimitExceeded` (a neighbour the #120 decision did not cover; decided in #133 to be the intended contract: `get_page` follows `/Count`, `collect_pages` expands and may refuse). The renderer's content stream recursion (`Do` → Form XObject, pattern tiles, SMask `/G`) is not subject to this invariant either — the command above does not catch it, and it recurses by resource name, not by tree links (maintainer decision, 2026-09-29). That recursion is covered by [Content stream recursion](content-stream-recursion.md). As of 2026-09-29 no tree walker reads by following `/Parent` upward (every use of `b"Parent"` is on the writing side). Code that copies objects by reachability does follow `/Parent` too — `graft_page` copies the source's whole page tree (Tracked: #121).
