# Source generation

## The fact
An object taken from the source document must be written **at the generation number of the source xref** — in all three of the object header (`N g obj`), the xref entry, and the object encryption key (R2–R4). This is because references `N g R` inside the document are copied as they are. If the three disagree, the reference is null (an undefined object) under ISO 32000-1 §7.3.10. Code that rewrites a reference's **number** must also rewrite its generation to the new target's generation. Objects inside an object stream must be generation 0 (§7.5.7).

The writer-side rule lives in `PdfWriter`'s `generations` (non-zero generations only): `from_document` in [Document modifier](../territory/document-modifier.md) fills it, and the serialization functions that take a writer read it. Public functions that take only number/object slices do not know the generation, so they write 0 ([File serialization](../territory/file-serialization.md)).

## Why it is cross-cutting
A generation appears separately in the reference (a copied value) and in the definition (the header, xref and key the writer creates anew), and the code that keeps the two in step is scattered across several modules: full rewrite, incremental save, xref streams, duplicate merging, number compaction, linearization, object stream packing. None calls another. Before #98 the justpdf reader did not look at a reference's generation, so its own round-trip tests passed even when they disagreed — a write defect was hidden by read tolerance. The reader now reads a reference with the wrong generation as `Null` ([Document access](../territory/document-access.md)). But references obtained from `object_refs()` use the xref generation, so only an assertion that follows a reference written inside the document sees a mismatch.

## Territories it holds in
- [Document modifier](../territory/document-modifier.md) — `from_document` holds the generations, and `build` (plain, `set_encryption`, keep-source) and `build_with_xref_stream` write with them. Holds (#72).
- `merge_documents` in [Document modifier](../territory/document-modifier.md) — `deep_copy_object` puts another document's objects at a number newly taken from the writer at generation 0, and writes references with the new number and generation 0 too. Holds (inferred — code reading, #106 check step).
- [Incremental save](../territory/incremental-save.md) — header, xref entry and key of appended objects. Holds (#72).
- [File serialization](../territory/file-serialization.md) — functions that take a writer write at the source generation; public slice functions write 0.
- [Compress dedup](../territory/compress-dedup.md) — `merge_duplicates` gives merged references the generation of the kept object. Holds (#72).
- [Clean](../territory/clean.md) — `compact_object_numbers` renumbers and writes every reference to an object in the list at generation 0. That is the generation of the public slice serialization function that writes the result. Holds (#106).
- [Linearization](../territory/linearization.md) — writes source objects at their xref generation in the header and main xref entry, and copies trailer `/Root` and `/Info` from the source as they are. Holds (#106).
- [Object streams](../territory/object-streams.md) — `DocumentModifier::pack_object_streams` leaves out objects with generation ≠ 0 and takes container numbers anew from the writer. The public slice `pack_object_streams` treats every object as generation 0. Writer-side xref stream serialization rejects compressed objects or containers with generation ≠ 0 as an error. Holds (#106).

## What a violation looks like
- (Before #72) `DocumentModifier` dropped generations and wrote every object with `N 0 obj`, a generation-0 xref and a generation-0 key. Rewriting a file whose source `/Info` is `6 1 obj` (generation 1 and 300 fixtures, plain, RC4, AES-128) made qpdf 12.4.1 read trailer `/Info 6 1 R` as null (full rewrite, xref stream). In incremental save, `6 0` in the new section did not shadow `6 1` in the source section, so qpdf read the object **before** the change — the edit silently vanishes (measured 2026-09-29). For RC4 and AES-128 files, justpdf itself decrypted with the wrong key and produced garbage and padding errors.
- If duplicate merging changes only the number, the kept object is `K 1 obj` while the merged reference is `K 0 R` (found in code during the #72 check step, reproduced with a test).

## Discovery history
2026-09-24, while working on #26 (incremental trailer), found in the code that `DocumentModifier` drops generations, and filed it as #72. On 2026-09-29, while fixing #72, reproduced it with tests and a qpdf check, and assay and lens in the check step found the duplicate-merging site. The remaining violating sites (number compaction, linearization, packing) were gathered the same day by grep and code reading, and reproduced with tests and fixed in #106.

## Where it will recur
**Any code that writes objects from the source document, or rewrites the number of a reference, is subject to this invariant.** Write objects from the source through `PdfWriter` with a writer-side serialization function. When changing a reference's number, change its generation to the new target's generation too (`rewrite_references` in `merge_duplicates`). For references the writer holds separately (the modifier's `catalog_ref` and `info_ref`), do not trust their generation; get it from the writer (`PdfWriter::reference_to`, #110). Verification: look directly at the header and xref entry with a generation ≠ 0 fixture (`with_info_at_generation`, tests in `writer/modify.rs`), check the key with an RC4 and AES-128 round trip (R6 is not evidence), and for an external check look at `pdf.trailer.Info.objgen` and `check_pdf_syntax()` with pikepdf. A justpdf reader round trip is evidence only when it resolves references written inside the document (trailer or dictionary values) — not a round trip that walks `object_refs()`. The half a tool can see: `rg '\{\} 0 obj|obj_num = new|r\.obj_num =' justpdf-core/src` — it finds `rewrite_references` in `clean.rs`, and also hits the linearization dict and hint stream that only write new numbers, `sign_pdf`, and the xref stream itself (not subject). The half a tool cannot see: the assumption that public functions taking only number/object slices (`pack_object_streams`, `clean_objects`, `serialize_pdf*`) treat every object as generation 0 — callers that pass the writer's objects to these functions, and callers that change numbers in `writer().objects` directly.
